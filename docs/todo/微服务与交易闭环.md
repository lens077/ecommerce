## 目标态（TECH.md §5 摘要）

服务按 **DDD 限界上下文**划分，不按数据库表拆。核心交易链路走
**Order Service 内置 Saga 编排器**（同步、强一致），派生副作用走事件编舞（最终一致）。

关键不变量（TECH.md §4.3）：
- **绝对防超卖**：库存扣减必须在单条语句内完成「检查余额足够 + 扣减」，任何情况下 `available >= 0`
- **状态机约束**：非法逆向跃迁禁止（如 `CANCELLED` 绝不可迁移至 `PAID`）
- 同一幂等键只能创建一个订单

## P0 · 假成功与越权

> 这批的共同点是**调用会「成功」但结果是错的**，或**任何登录用户都能越权**。
> 比「未实现」更危险：不会在联调时暴露，只在上量后以超卖、丢单、数据泄露的形式爆发。
> `payment` 显式返回 `Unimplemented` 是本仓的正确示范，下面几处应向它看齐。
> 双模型独立评审 + 逐条代码核实，全文见
> [`ADVERSARIAL_REVIEW_20260806.md`](../progress-archive/ADVERSARIAL_REVIEW_20260806.md)。

- [ ] **库存 `Reserve` 静默无操作**（`inventory/internal/data/inventory.go:52`）：四处叠加——
      ①传 `Version: stock.Version+1` 而 SQL 是 `AND version = @version`，WHERE 比对未来版本号
      → **永远命中 0 行**；②execrows 为 0 时不返回冲突错误；③扣减量语义错；④错误分支传错变量。
      修法：传当前 version、execrows=0 返回冲突、修正扣减量、错误分支传对变量、整段包进 `ExecTx`。

- [ ] **库存 `ReleaseReserve` 是 panic 桩**（同文件 :88）：实现，或至少改成显式 `Unimplemented`。

- [ ] **`CreateOrder` 返回假成功**（`order/internal/service/order.go:31`、`application/order.go:61`）：
      service 层把 `req` 整个注释掉、硬编码 `CartItemIDs: nil, AddressID: 0`。
      **立即改成显式 `CodeUnimplemented` 止血**——结算页已接线，当前用户会看到「下单成功」但无订单。

- [ ] **`CompleteOrder` 不落库**（`order/internal/data/order.go:83`）：实现 `SaveOrder`；
      持久化成功前不得发布 `OrderCompleted`。

- [ ] **地址服务全线越权**（`address/internal/service/address.go:26,71,84,95`）：
      `Get/Update/Delete/SetDefault` 的 SQL 只按 `address_id` 过滤、无 user 归属校验。
      修法：user 取自网关身份头、所有查询加 `AND user_id = ?`、
      网关策略从 `AddressService/*` 整段放行收敛到 RPC 粒度。

- [ ] **商家审批全表 UPDATE**（`merchant/internal/data/queries/merchant.sql:23`）：
      补 `WHERE application_id = @application_id`，repo 层把 `ApplicationId` 传下去。

- [ ] **登录 token 落日志**（`user/internal/data/user.go:39`）：删掉 `u.l.Debug(token.AccessToken)`。

- [ ] **`AddProductToCart` 必然失败**（`cart/internal/data/queries/cart.sql:3` vs `schema/cart.sql:17`）：
      INSERT 补 `shop_name`（proto/biz/data 一路补字段）或给 schema 默认值——需先定契约。

- [ ] **商家 `RejectApplication`/`ActivateMerchant` 是 panic 桩**（`merchant_service.go:57,98`）。

- [ ] **给上述路径补测试**：本轮 22 条发现**全部位于零覆盖路径**上，而 `go test ./...` 是全绿的——
      不补测试，修完还会重演。

## P1 · 交易闭环打通

- [ ] **建单全链路**：cart 补「按 CartItemIds 取选中项」RPC → 取商品/地址快照 → 拆单 →
      事务落库 group/order/item → 同步 `Reserve` → 清空购物车。

- [ ] **订单服务补 RPC 与状态机**：`GetOrder` / `ListOrders` / `CancelOrder`，
      带守卫的状态迁移 + `order_log`。

- [ ] **库存联动**：下单同步 `Reserve`（TCC-Try），支付成功确认扣减，取消/超时 `ReleaseReserve`。

- [ ] **支付闭环**：`payment/result` 接支付状态查询 + 回调后订单状态同步（订单订阅 `OrderPaid`）。

- [ ] **商品服务 `ListProducts`**（设计已定，见 [`docs/design/product/listing.md`](../design/product/listing.md)）：
      首页无限滚动 + 游标(keyset)分页、无总数；`ProductCard` 含 brand/价格区间(min~max)。
      落地：`product.proto` → `make api` → `query.sql` → `make sqlc` → biz/data/service 样板 →
      前端 `useInfiniteQuery` 接首页。
      ⚠️ **这条卡着 consumer-next 扩页**（分类/首页无列表数据源）。

- [ ] **下单防重的 `requestId` 一直是假的**：旧代码
      `client.createOrder(message as Parameters<...>[0])` 在假装 proto 有这个字段，
      而 `CreateOrderRequest` 只有 `cartItemIds`/`addressId`/`remark` 三个，
      那个 UUID 运行时直接被丢掉 —— **防重从来没生效过**。
      要真生效得先补 proto 字段再 `make api`。

- [ ] **cart 条目契约迁回 `cart_item_id`**（2026-08-26 宪法裁决，checkout v2 依赖）。

- [ ] **订单缺陷修复**：金额改 `decimal`（现为 `float64`）、修 `AddressPostalCode` 空指针、
      统一 `merchant_id` 类型（UUID）、`Complete()` 应要求已发货。
