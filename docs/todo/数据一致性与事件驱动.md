## 目标态（TECH.md §4 摘要）

业务写与事件投递绑定在**同一 PostgreSQL 本地事务**（Transactional Outbox），
Relay 异步投递到 **Kafka（非 K8s 独立集群）**，消费端用 **Inbox 幂等表**去重。

| 机制 | 约束 |
|---|---|
| Outbox 保证 | Relay 仅在收到 Kafka `acks=all` 后才更新 Outbox 为 `published` |
| Inbox 幂等 | `inbox_events` 主键 `(consumer_group, event_id)`，重复消费靠唯一键冲突忽略 |
| DLQ | 连续失败 >5 次转投 DLQ Topic + 触发 Alertmanager，禁止无休止重试阻塞 Partition |
| Topic 规划 | 按限界上下文划分，`aggregate_id` 作 Partition Key 保证同聚合根有序 |
| 事件 Schema | Protobuf + Buf Schema Registry；envelope 含 `event_id`/`aggregate_id`/`tenant_id`/`trace_id`/`schema_version`/`occurred_at` |

## P1 · 编舞 Saga 四项治理

> 必须随事件驱动一起落，否则流程失控。方案本体见
> [`docs/design/order/consistency.md`](../design/order/consistency.md)。

- [ ] **幂等消费**：consumer 以 `order_no`/事件 ID 去重（至少投递一次语义）
- [ ] **显式补偿事件**：`StockReserveFailed → 订单自动取消` 等补偿作为一等公民设计，不散落
- [ ] **状态即真相**：`order_status` 作为「这单走到哪」的唯一可见状态
- [ ] **超时兜底 job**：扫 `pay_deadline` / 卡在中间态的订单做补偿或告警（编舞无中心，必须有 backstop）
- [ ] **全链路 trace_id**：事件贯穿 `trace_id`（Kafka Header 传 W3C `traceparent`），靠 OTel/VictoriaTraces 定位

## P1 · 事件工程 E0–E4

- [ ] **E0 容量与拓扑**：为每个 Kafka topic 声明 owner、partition（key=`aggregate_id`）、
      replication、retention、最长积压和恢复 SLO；用真实 payload 压测吞吐、磁盘和成本。
- [ ] **E1 producer 正确性**：Product/Order 业务写与 outbox 同 transaction；
      relay 只在 broker ack（`acks=all`）后标记 published；
      补 ack 后崩溃、落库前崩溃、积压恢复三类测试。
- [ ] **E2 consumer 治理**：Inbox 幂等（`(consumer_group,event_id)` 唯一键）、retry/backoff、
      max deliver、DLQ（连续失败 >5 次转投并告警）、poison message 分类、重放权限与审计。
      **业务副作用不得依赖 broker exactly-once。**
- [ ] **E3 搜索恢复**：固定真实商品数据集，验证 projection count/checksum/query diff、
      全量 rebuild、水位补偿、积压恢复和 alias 原子切换。Elasticsearch 代码路径已实现，仍缺目标网络通路上的恢复演练；存量 Meilisearch 只作切流对照。
- [ ] **E4 交易事件演练**：Order/Inventory/Payment 完成重复投递、乱序、超时、依赖断连、积压、人工重放；
      **没有 Inbox 与补偿证据前禁止产生支付/库存副作用。**

## P2 · DuckDB 试点落地（TECH.md B 表 2026-08-28 采纳，至今零执行）

> 定位与红线见 [`docs/TECH.md`](../TECH.md) B 表「嵌入式分析」行，评估见
> [`2026-08-28-duckdb-evaluation.md`](../reports/2026-08-28-duckdb-evaluation.md)。
> **采纳的是能力不是排期**——该行写「采纳（试点待执行）」但从未进过任何待办文件，本节补上。
> 与本分类的关系：DuckDB 只查**已提交**的 Parquet 归档，不参与 outbox/inbox 语义，
> 不做 consumer checkpoint（<30s 新鲜度归流处理触发项）。

- [ ] **D0 先答「第一个真实分析问题」再动手**：DuckDB 的触发条款是 TECH-RADAR §3.2 的
      ①真实分析需求 ②`behaviors.events` 千万行级。**先确认哪一条已成立**——
      当前分析消费者为 0，若两条都不成立，本节整体保持未排期，不要为了用而用。
      候选首题按评估报告排序：支付渠道账单对账（P0/P1 反复出现且至今无工具形态）
      → `behaviors.events` 漏斗分析 → 经营报表 ad-hoc 维度切片。

- [ ] **D1 落一条最小跑批链**：`PG 增量导出 → Parquet 落 Silo → DuckDB CLI 子进程扫描`。
      集成形态按评估结论**只用 CLI 子进程**（`exec.Command` + 固定 SQL 模板文件，
      绝不接受用户任意 SQL——CLI 元命令是攻击面）；大结果走
      `COPY … TO … (FORMAT PARQUET)`，Go 只读状态与 manifest。
      **业务服务 `CGO_ENABLED=0` 一字不改，duckdb-go 不进 10 个微服务**（STACK §2.6 硬事实）。
      归档目录按 `event_date=`/`sale_date=` Hive 分区，单文件目标 ≥100MB，
      新批次先写临时 prefix、校验后原子发布 manifest。

- [ ] **D2 版本选型复核（v2.0 预览版发布后新增）**：评估报告的两条前提是
      **v1.5.5** 与 **「Quack 是 Beta，不为绕 cgo 引入生产」**。DuckDB Labs 已发布
      **v2.0 预览版「Cyanoptera」**（自 1.5 起逾 10000 次提交，正式版计划 2026 秋），
      其中两项直接冲击上述前提：
      ①**quack 协议转正**为原生 client/server（`CALL quack_serve` / `ATTACH 'quack:…'` / `CONNECT`），
      「不用 Quack」的理由从「它是 Beta」变成需要重新论证的**架构选择**；
      ②**版本化 C API + 稳定 ABI**（YAML 规范 + C++ 抽象层，Rust 绑定在路上），
      社区讨论明确指向它解决 Go 的 CGO 开销与并发监控痛点。
      **判据**：正式版发布前**不改选型**，D1 继续按 v1.5.5 CLI 形态落地；
      正式版发布后复核两问——CLI 子进程是否仍优于 quack daemon（后者引入常驻进程，
      与「零常驻」这一**采纳理由本身**直接冲突）、稳定 ABI 是否让 `CGO_ENABLED=0` 破例变得可接受。
      结论回写 TECH.md B 表与评估报告，**不在本文件维护选型**。

- [ ] **D3 顺带复核的 v2.0 增量**（同样等正式版，不改当前实现）：`VARIANT` 类型成熟
      （半结构化载荷自动列式分解，可能影响 `behaviors.events` 的 payload 归档方案）、
      异步 I/O（跨 S3 兼容对象存储，直接作用于 Silo 读取吞吐）、分区感知查询规划
      （对 D1 的 Hive 分区布局有效）、`DICT_FSST` 字典字符串压缩、去 ICU 依赖（二进制更小）。
      **不构成提前引入预览版的理由**——预览版不进任何跑批产物。
