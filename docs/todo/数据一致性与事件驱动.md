## 目标态（TECH.md §4 摘要）

业务写与事件投递绑定在**同一 PostgreSQL 本地事务**（Transactional Outbox），
Relay 异步投递到 **Kafka（非 K8s 独立集群）**，消费端用 **Inbox 幂等表**去重。

| 机制 | 约束 |
|---|---|
| Outbox 保证 | Relay 仅在收到 Kafka `acks=all` 后才更新 Outbox 为 `published` |
| Inbox 幂等 | `inbox_events` 主键 `(consumer_group, event_id)`，重复消费靠唯一键冲突忽略 |
| DLQ | 连续失败 >5 次转投 DLQ Topic + 触发 Alertmanager，禁止无休止重试阻塞 Partition |
| Topic 规划 | 按限界上下文划分，`aggregate_id` 作 Partition Key 保证同聚合根有序 |
| 事件 Schema | Protobuf + Buf Schema Registry；envelope 含 `event_id`/`aggregate_id`/`tenant_id`/`trace_id`/`schema_version`/`occurred_at` |

### 施工清单（按顺序，1–2 可提前做，3–4 必须与第一个业务生产者同批落地）

1. **outbox 表补 `aggregate_type` 列，去掉三列簿记**（一份 goose 迁移，可提前做，无副作用）
   - 加 `aggregate_type VARCHAR(64) NOT NULL`，取值为限界上下文名（`order`/`product`），Router 按它分 topic。
     现有列里 `type` 太细（每种事件一个值）、`source` 是服务名，都不能当路由键。
   - 删 `published_at`/`attempts`/`last_error` 与索引 `idx_products_outbox_unpublished`、`idx_products_outbox_published_at`。
     这三列是自写 relay 的记账本；换 Debezium 后「是否已发布」由 WAL 位点回答，留着会让人误以为 `NULL` = 未发出。
   - 清理改按 `occurred_at` 保留期。表注释同步改掉「由 relay 异步发布到 NATS JetStream」。
   - `pkg/outbox.Insert` 签名加 `aggregate_type`，去掉对三列的写入。
2. **Router connector**（pipeline 仓 `deploy/docker-node3/connectors/` 新增一份 JSON，独立 slot 与 publication）
   - `connector.class=io.debezium.connector.postgresql.PostgresConnector`，`table.include.list` 只含各域 outbox 表，
     `slot.name`/`publication.name` 与现有 `ecommerce_cdc` 分开——outbox 线卡住不拖搜索线，反之亦然。
   - `transforms=outbox`，`transforms.outbox.type=io.debezium.transforms.outbox.EventRouter`，列映射：
     `table.field.event.id=event_id`、`table.field.event.key=partition_key`、`table.field.event.type=type`、
     `table.field.event.payload=payload`、`table.field.event.timestamp=occurred_at`、`route.by.field=aggregate_type`、
     `route.topic.replacement=ecommerce.${routedByValue}.events`。
   - CloudEvents binary mode：`table.fields.additional.placement=type:header:ce_type,source:header:ce_source,subject:header:ce_subject,occurred_at:header:ce_time`；
     `traceparent` 若入列，同样放 header。不用 `CloudEventsConverter` 的 structured mode——它把属性塞进 value，消费者要多解一层。
   - `lsn.flush.mode=connector_and_driver`（idle slot 陷阱对新 slot 同样成立，见
     [`debezium-idle-slot-wal-retention.md`](../../context/project/ecommerce/events/experience/debezium-idle-slot-wal-retention.md)）。
   - `producer.override.acks=all`、`producer.override.enable.idempotence=true`；
     前提是 Connect worker 开了 `connector.client.config.override.policy=All`〔当前 worker 是否已开待确认〕。
   - Kafka topic 按 E0 先声明 owner/partition/retention 再建，不靠 auto-create。
3. **第一个业务生产者**：业务写与 `outbox.Insert` 同一 PostgreSQL transaction（E1）。
   payload 按 TECH.md 用 Protobuf 定义、进 buf；`partition_key` 用聚合标识（`order:<order_no>`）。
4. **第一个 franz-go + Inbox 消费者**（线 B 唯一保留的自写代码，TECH.md B 表已定不引入 Kafka Streams）
   - 订阅 `ecommerce.order.events`；每条消息在一个 PG transaction 内：
     `INSERT INTO inbox_events(consumer_group, event_id)` 冲突即视为已处理并跳过 → 按 `ce_type` 分发 handler → COMMIT → 提交 offset。
   - 连续失败 >5 次转投 DLQ topic 并触发 Alertmanager，offset 继续前进，不堵 partition（E2）。
   - 为什么不用 JDBC Sink 代替：handler 里有业务分支（按事件类型写不同表、触发补偿），Sink 只搬行。

### 未决选择（动手时再定，不要现在拍）

| 选择 | 选项 | 倾向与理由 |
|---|---|---|
| outbox 行发出后删不删 | ① insert 后同事务 `DELETE`，表恒空；② 保留 + 按 `occurred_at` 清理 | 倾向 ②：E2 要求重放权限与审计，行是审计材料。选 ① 需配 `tombstones.on.delete=false` |
| `payload` JSONB 是否展开 | `table.expand.json.payload=true/false` | 取决于 payload 最终是 JSON 还是 Protobuf bytes；Protobuf 则不展开 |
| 一个 Router connector 还是每域一个 | 单 connector 多表 / 每域独立 slot | 起步单 connector；某域事件量或故障域明显分化后再拆 |
| header 命名 | `ce_*` 前缀 / 裸属性名 | 沿用 CloudEvents Kafka binding 的 `ce_` 前缀，消费者 SDK 直接识别 |

### 验收锚点（对应 E1/E2/E4）

- 生产者：事务回滚后 outbox 无行；同事务写两次的重复测试；Connect 停机期间事件停留在 WAL/表中，恢复后按提交序投递。
- 消费者：同一 `event_id` 投递两次只产生一次副作用；毒消息 5 次后进 DLQ 且告警可见；崩溃重启后不重复不丢。
- 位点：`pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)` 持续回落；不要看 `*_lag` 时间指标。
- 告警：盯 slot 位点差、connector task 状态、consumer lag 三项，容器健康不算。

### 不要做的事

- 不重写自写 relay 的 Kafka 版。§1.8「零新组件」的前提（栈里没有 Connect）已不成立。
- 不把线 A 的表（`search_catalog` 等）放进 Router connector，也不把 outbox 表放进 CDC 线的 `ecommerce_cdc` publication。
- 不在业务 transaction 内直接发 Kafka，不为发事件而双写第二个 broker。
- 没有 Inbox 与补偿证据前，消费者不得产生支付/库存副作用（E4）。
