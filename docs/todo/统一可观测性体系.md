## P0

- [ ] **PII 脱敏形同虚设（安全）**：部署中 fluent-bit lua 手机号脱敏用 `(%d{3})%d{4}(%d{4})`，
      **Lua 模式不支持 `{n}` 量词**，匹配不上任何手机号 = 空操作；更严重的是
      `Merge_Log On` + `Keep_Log On` 保留原始 `log` 明文字段，连有效的 email 脱敏也被绕过——
      完整未脱敏 JSON 整条入库。且脱敏只碰顶层 `email`/`phone` 两键，漏掉
      `payment/internal/server/logging.go` dump 的 `form_data`（交易/回调数据）、
      RUM 的 `user_id`/`session_id`、debug 日志里的 bearer token。
      **按 TECH.md §9，脱敏最终统一在外置 OTel Collector 管道执行**——本项随
      Vector→VictoriaLogs 迁移收敛，不要在已退役的 fluent-bit 上修。
      〔全文见 [`OBSERVABILITY_REVIEW_20260806.md`](../progress-archive/OBSERVABILITY_REVIEW_20260806.md)〕

- [ ] **免鉴权入口身份可伪造（安全）**：网关 jwt 中间件命中白名单
      （`telemetry.v1/CollectWebVitals`、`behavior.v1/Track`）时直接 return，**不剥离入站头**；
      rewrite/remove-header 中间件在 config.yaml 全被注释掉；`behavior/identity()`
      又把 `x-md-global-user-id` 当可信源。攻击者带 `x-md-global-user-id:<受害者ID>`
      即可冒名上报，污染统一身份口径。补一条入站 `x-md-*` 剥离中间件。

- [ ] **可观测栈自身无独立存活证明（2026-08-29 新增）**：本次控制面故障中 Vector 与
      OTel Collector 同时 `0/1`，等于故障期间零可观测。需要一条**不依赖被观测集群**的
      黑盒探活（node3 侧 Gatus 已具备条件），并对「采集器 Ready 数 < 期望」单独告警。

## P1

- [ ] **网关 5xx 被记成成功**：`tracing.go:81-90` 只在 `err!=nil`（传输层错误）时
      `SetStatus(Error)`；后端返回 HTTP 503 但 `err==nil` → span 状态 OK、`logging.go`
      记成 `LevelInfo`。链路错误检索与日志 error 级告警都漏掉真实 5xx。
      改法：按 `reply.StatusCode>=500` 设 span 状态与日志级别。

- [ ] **网关采样口径与后端相反**：网关 `AlwaysSample()`（非 `ParentBased`），后端 `ParentBased`。
      网关是 trace 根，永远 100% 采样，设 `sample_ratio` 也压不住，高峰会压垮 collector。
      改 `ParentBased(TraceIDRatioBased)` 并统一读同一采样率；
      最终采样决策按 TECH.md §9 交由外置 OTel Collector 尾采样承担。

- [ ] **RUM 与后端 trace 无 join key**：前端 `packages/perf` 用 web-vitals + 手写 Connect-JSON，
      无 `@opentelemetry/*`、不透传 `traceparent`、后端不回 `Server-Timing`——慢
      `frontend.api.duration` 无法关联到后端 span；`anon_id`/`session_id` 只在日志不在 metric/span。
      且只有 consumer 一个前端调 `initPerf`，merchant/admin/config 三个没接。
      设计声称的「前端→网关→微服务全链路」，前端那段目前不存在。

- [ ] **10 个电商服务缺 Go 运行时指标**：goroutine / 堆 / 进程 CPU 内存全都没有。
      唯一在报的是独立仓 control-tower（它实现了 `internal/pkg/sysstat`）。
      把那套搬进 10 个服务或抽成共享埋点。附带：control-tower 未装 OTel ErrorHandler，
      导出失败无任何日志（本仓 10 个服务已在 2026-08-06 补上，可照抄）。

- [ ] **日志限流（方案已定稿，待实现）**：防「基础设施故障 → 周期性错误日志」风暴。
      真实暴露面：PG 挂时 behavior `flush()` 每 2s 一条 ERROR、Consul 断连时 11 个服务的
      `TtlCheckPinger` 各每 10s 一条，且都经 otelzap 走网络——故障时恰是网络最脆弱时。
      **机制**：zap 内置 Sampler Core 包在 `newLogger` 的 Tee 外层（stdout + otelzap 两条通路都受管），
      按 message 键控。**分级**：FATAL/PANIC 永不限；ERROR/WARN 每秒同消息前 3 条放行、之后 1/100；
      INFO 前 10 条。**压制必须可见**：丢弃钩子打 OTel counter `logs_suppressed_total`（带 level 标签）——
      压制速率突增本身就是故障信号，静默压制是最大反模式。
      **铺开**：`internal/pkg/log/log.go` 10 份复制关系全改。
      待定：阈值 3/100 可调；INFO 是否纳管。

- [ ] **VMAgent 尚未部署**：TECH.md §9 的采集层要求 `Vector + VMAgent + OTel SDK` 三件套，
      当前集群只有 Vector 与 OTel Collector，**VMAgent 缺位**，指标采集路径与目标态不符。

- [ ] **kubeletstats 待启用**：`k8s_cluster` + `k8sobjects` 已落地（VM 有 27 个 `k8s.*` 指标、
      VL 可查真实 Event），但**节点/Pod 实际 CPU/内存**仍需 kubeletstats receiver。
      〔2026-08-29 故障中正因缺这层，node101 内存耗尽只能靠 `free`/`vmstat` 手工发现〕

- [ ] **恢复网关时延看板**：control-tower 网关已带 otelhttp meter（ParentBased 与后端对齐）
      且已切流，原「网关指标未实现」条按其自述条件关闭；把旧网关无指标时删掉的
      「网关→上游 HTTP 时延」图加回 `docs/observability/grafana/` 看板脚本。

      **实测动机〔实测 2026-08-29〕**：端到端验证中，直连网关 RPC
      `product.v1.ProductService/GetProductDetail` 首次耗时 **2.16s**，
      而经 consumer-next SSR 的同类取数只要 **0.42s**、网关 `/healthz` 仅 **50ms**——
      相差一个量级。合理猜测是冷连接建立（网关→product 的 H2C 连接池，
      或 product→PG 连接池首次拨号），SSR 路径快是因为 consumer-next 已持有热连接。
      **但这只是猜测，当前无任何时延指标可证实**——10 个服务连 Go 运行时指标都没有
      （见本文件 P1「10 个电商服务缺 Go 运行时指标」），网关时延图也还没加回来。
      看板恢复后应能直接回答「这是冷启动还是常态」。
      复验：`curl -sSk -o /dev/null -w '%{time_total}\n' -X POST https://gateway.dev.test/product.v1.ProductService/GetProductDetail -H 'Content-Type: application/json' -d '{"spuCode":"estee-lauder-anr"}'`

- [ ] **补一次 P95 时延基线**：上条的 2.16s 是**单次采样，不能当结论**。
      需固定数据集连打 N 次取 P50/P95/P99，并区分冷启动与稳态。
      属 k6 容量基线的一部分，与 VPA 观测窗口合并做
      （见 [`基础设施与部署模型.md`](基础设施与部署模型.md)）。

- [ ] **看板两处口径错**：①`build_infrastructure.py:133-139`「DB 错误率」=
      `(errors or count*0)`，画的是**错误/秒不是比率**，1 err/s 混在 10000 ops/s 里飘红误报，
      需除以操作总量；②`build_infrastructure.py:38-41` 节点覆盖 stat 阈值 ≥2 为绿、
      desc 说「node1 是 control-plane collector 不调度」——**实测已不成立**，
      应对齐 3 节点，否则掉 1 节点仍显绿。
