## CI 触发纪律（2026-08-29 变更）

**GitHub Actions 预算超支后，平台会直接拒绝运行。** 因此所有 GitHub workflow 已收敛为
**仅发布 tag 触发**（裸 semver `X.Y.Z`）：

| workflow | 触发 |
|---|---|
| `backend.yml` | tag `X.Y.Z` + 手动 |
| `context-gate.yml` | tag `X.Y.Z` + 手动（原每 PR/push） |
| `deploy-consistency.yml` | tag `X.Y.Z` + 手动（原 push main + PR） |
| `supply-chain-pr.yml` | tag `X.Y.Z` + 手动（原 PR） |
| `frontend.yml` | **仅手动**（原每日 cron，最贵的常驻消耗） |
| `service-ci.yml` | `workflow_call`（被调用，不自触发） |

⚠️ **per-push 覆盖没有丢**：`.gitlab-ci.yml` 的同名 `context-gate` job 仍挂在
`$CI_COMMIT_BRANCH` 与 MR 上，而 origin 就是 GitLab。本地
`scripts/verify-quick.sh` / `scripts/verify-context.sh` 仍是提交前锚点。

理由与验证方法见
[`evolution-log.md`](../../context/harness-framework/evolution-log.md) 2026-08-29 条目。

## P1

- [x] **签名前 Trivy image 扫描** —— 2026-08-29 已接入 `service-ci.yml`。
      步骤序列现为 **构建 → SBOM → 扫描 → 签名**（原先 SBOM 后直接签名，
      等于给未经检查的制品背书；且高危镜像会带着**有效签名**躺在仓库里，
      Kyverno `verifyImages` 也拦不住）。
      实现要点：
      - 扫的是 build 输出的**不可变 digest**，不是 tag——扫 tag 会出现
        「扫的是 A、签的是 B」的经典缺口
      - 阈值 `CRITICAL,HIGH` + `ignore-unfixed: true`：**只阻断有修复版本的**。
        把无修复漏洞算进阻断集会让流水线长期红着，最后被人加 `continue-on-error`
        绕过——那比没有扫描更糟。无修复项仍进 SARIF 上报，只是不阻断
      - SARIF 上传用 `if: always()`，扫描失败时也出报告（最需要看结果的正是那次）
      - `security-events: write` 在 `service-ci.yml` 与调用方 `backend.yml` **两处都加**
        ——reusable workflow 只能收窄不能放大调用方权限，只加一处会 403
      ✅ **2026-08-29 本机预演跑通了**（用 `--db-repository ghcr.io/aquasecurity/trivy-db:2`
      绕开 `mirror.gcr.io`——后者在境内只有 ~40 KiB/s，这也说明 workflow 里配
      `TRIVY_USERNAME/PASSWORD` 走 GHCR 是必要的，不只是提配额）。

- [ ] **🔴 首发会被 Trivy 拦住——发版前必须先修**（2026-08-29 实测，扫的是升级到
      `alpine:3.24.1` 之后的 `user` 镜像）：`exit=1`，**9 个 HIGH、0 个 CRITICAL，全部可修复**。
      分两组：

      | 来源 | 数量 | 代表 CVE | 修法 |
      |---|---|---|---|
      | OS（`libcrypto3`/`libssl3`） | 2 HIGH | CVE-2026-14456 | 升到 `3.5.7-r0`——Dockerfile 加 `apk upgrade --no-cache` 或等 alpine 基础镜像刷新 |
      | Go 二进制（`stdlib` + `golang.org/x/net`） | 8 HIGH | CVE-2026-33818、CVE-2026-56858/56859/56860/56862 | `stdlib` 需 Go **v1.26.5**（当前 `go.mod` 已是 1.26.5，说明构建镜像 `golang:1.26.5-alpine3.24` 里的工具链需刷新）；`golang.org/x/net` 当前 `v0.58.0` 需升级 |

      ⚠️ **注意这是升级到 alpine 3.24 之后的结果**——3.22 只会更多。
      门禁按设计工作（只拦可修复项），拦得对；但意味着**下次打 tag 会直接失败**。
      建议顺序：先 `go get -u golang.org/x/net` + 刷新构建镜像 → 重扫确认归零 → 再发版。

- [x] **运行基底对齐到 `alpine:3.24`** —— 2026-08-29 已完成。
      发现经过：本机预演 Trivy 时顺带查基底，发现 **10 个 Dockerfile 全部是 `FROM alpine:3.22`**
      （实测容器内 `VERSION_ID=3.22.5`），而构建阶段用的是 `golang:1.26.5-alpine3.24`
      ——**运行基底落后两个小版本，且 `STACK.md`/`docs/TECH.md` 都没记录过它**。
      为什么必须在首发前修：Trivy 门禁只阻断**可修复**的 CVE，基底越旧累积越多，
      **首发被拦的概率主要由这个版本差决定**；改 10 行远比发版被拦后回头改便宜。
      验证：`alpine:3.24.1` 可拉、`libc6-compat` 依赖齐全；升级后实测构建 EXIT=0；
      容器内 `VERSION_ID=3.24.1`、`gcompat` 已装；`/app/service --help` 正常输出 usage
      ——**动态链接完整，不是「构建过了但跑不起来」**。
      已把「构建镜像」与「运行基底」两行补进 `STACK.md` 版本锁定表，消除这个隐性依赖。
