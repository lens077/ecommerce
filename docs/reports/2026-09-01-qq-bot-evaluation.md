## 一、平台提供什么

| 维度 | 内容 |
|---|---|
| 场景 | QQ 群、消息列表单聊（C2C）、QQ 频道（含频道私信）。企业与个人开发者均可开通这三个场景 |
| 事件接入 | 二选一：**Webhook**（HTTPS 回调 + ed25519 签名校验，端口限 80/443/8080/8443）或 **WebSocket** 长连接（intents 位掩码订阅 + 分片负载均衡） |
| 事件覆盖 | 用户发消息、@机器人、加/删好友、机器人被拉群/踢群、按钮点击 `INTERACTION_CREATE`、主动消息开关被关闭、消息审核结果 |
| 消息能力 | 文本、Markdown（需申请模板权限）、富媒体、内嵌按钮键盘、C2C 流式消息、引用回复 |
| C 端交互面 | `/` 指令面板（上限 24 条）、机器人资料卡、快捷菜单（上限 12 条）、跳转 QQ 小程序或 OAuth H5 |
| 配套 | 沙箱环境（群/频道成员 ≤20 人）、Go SDK [botgo](https://github.com/tencent-connect/botgo)、兔小巢用户反馈 |

**频控与时效**（决定产品形态，不是运维细节）：

- **被动回复**（用户先说话）：单聊 60 分钟内可回 4 次；群聊 5 分钟内 5 次
- **主动消息**（机器人先说话）：企业/个人认证单聊 10 QPS、群 60 条/分钟；单关系 20 条/分钟；每日上限 1000 条/用户、1000 条/群；接口自身 100 QPS
- **互动召回**：用户主动对话后 30 天内分 4 个窗口（当天、1—3 天、3—7 天、7—30 天），每窗口各下发 1 条
- **用户可一键关闭主动消息**，关闭后主动消息一律失败并触发 `C2C_MSG_REJECT` / `GROUP_MSG_REJECT`——所以主动通知**不能作为唯一送达手段**

## 二、对本项目能带来什么

按**落地成本从低到高**排序，不是按价值排序。

### 1. 团队内部运维通知（最便宜的起步）

把部署结果与告警推到内部 QQ 群。不面向 C 端，因此不需要账号绑定、不需要备案域名、不需要提审用户可见文案，**沙箱环境即可完成全部验收**。

它还是唯一能在早期验证「主动消息」通道的手段——而主动消息是平台约束最多的一条路（配额分档、用户可关闭、有审核事件、频控多维叠加）。把它推迟到后期，等于把这一整组风险留到最后才第一次暴露。

### 2. 对话式购物入口

`/查订单`、`/搜商品`、`/物流` 指令 → qqbot 调既有的 order/search/product 能力 → Markdown + 按钮回复。单聊 60 分钟的被动回复窗口足够覆盖一次查询会话。

**前提**：核心交易路径可信。`TODO.md` 全局 P0 第 1—10 项记录了 `CreateOrder` 返回假成功、`CompleteOrder` 不落库、库存 `Reserve` 静默无操作、地址服务全线越权。QQ 是比网页更强的「确认」渠道——用户会把机器人的回复当作事实，**这会把后端缺陷放大成信任问题**。

### 3. 订单生命周期通知

支付成功、发货提醒走单聊主动消息（每用户日上限 1000 条对交易通知绰绰有余）；未回消息的用户用互动召回做复购提醒。

**这是 `ecommerce.events` 的第一个真实消费方候选**——但要清楚它是**新建**不是复用：`.service-matrix.yaml` 里 Kafka 与 NATS 的 `used_by` 均为空，`known_gaps` 记录 order 未导入 outbox producer、无 consumer Inbox 表、无 DLQ。这条链路是三段新建工作。

### 4. 客服与售后半自动化

群聊 @机器人答商品咨询；`FRIEND_ADD` 事件触发欢迎语与指令引导。

### 5. 账号打通

QQ 侧用户标识是 **`openid` 而不是 QQ 号**：它是 per-bot 维度的，换一个 AppID 就是另一套，且**无法反查 QQ 号**。因此不存在隐式识别路径——「单聊里查订单」必须先有一次显式绑定动作，把 `openid` 关联到 Casdoor 身份。绑定关系是领域真相，只能落 PostgreSQL（矩阵明确写了 Dragonfly 不得承载领域真相）。

## 三、落地前的硬约束

### IP 白名单：两种接入方式都躲不掉

新机器人默认启用 IP 白名单，只有白名单内的公网 IP 能**连 WebSocket**和**调 OpenAPI**（只作用于正式环境，沙箱不受限）。

发消息必然调 OpenAPI，所以**选 Webhook 不等于绕过白名单**——它只把需要解决的问题从两个减到一个，没有减到零。

本机所在局域网的公网出口是 `<operator-egress-ip-a>`（**实测 2026-09-01**，从 `192.168.3.220` 测得，与集群节点 `192.168.3.101-103` 同网段、同一路由器 NAT）。两点待确认：

- 集群 Pod 的出口是否与本机一致——需在集群内起临时 Pod 跑一次 `curl ifconfig.me` 比对〔待确认〕
- 该 IP 是否长期稳定——`192.168.3.0/24` 是带 DHCP 的家用网段，需隔天复测〔待确认〕

本仓已在企业微信告警上踩过同款坑，且**失败是静默的**（API 返回 `not allow to access from your ip`，只出现在日志里）。把「白名单没配」列进排查清单第一条。

### 备案与消息 URL 白名单

平台要求机器人下发消息里的链接域名先报备且需 ICP 备案（上限 20 条，每年可改 50 次）。

**2026-09-01 更新**：域名备案已由用户完成，此前记录在 `.service-matrix.yaml` 与 `context/team/pangolin-tunnel.md` 的「未备案」约束已删除。需注意本次未能独立验证备案状态——node2 的 80/443 无监听，行为复测不可判定〔待确认〕。这条不阻塞沙箱阶段。

### 接入方式：推荐 Webhook

初评倾向 WebSocket，理由是「只需出站、前置条件更少」。**该理由已被推翻**：取 AccessToken、发消息、调 OpenAPI 全是出站，两种模式都受白名单约束；而「与现有出网路径一致」这个前提恰恰指向不可承诺固定 IP 的那条路径（家用 DHCP 网段，出网还依赖开发机上的代理）。

改判 Webhook 的三条理由：

1. 入站复用本仓已走通多次的成熟通路——node1 Pangolin（固定公网 IP，对外 443）→ cilium-gateway → HTTPRoute，有逐字操作手册与三条验收判据（见 [`context/team/pangolin-tunnel.md`](../../context/team/pangolin-tunnel.md)）
2. 无状态，可多副本，直接满足集群 suite-wide 的打散约束
3. 不引入新的单活协调问题——WebSocket 的分片语义（群/单聊事件如何在多 shard 间分布）在本仓无法确定，且 `op=6` Resume 的 `session_id + seq` 必须持久化

完整论证与 13 条待验证见 [`wiring.md`](../../.scratch/qqbot-integration/wiring.md)。

### 审核、运营与凭据

- 机器人需提审上线；基本信息每月限改 5 次；指令面板上限 24 条
- 企业主体与个人主体在接口权限申请上有差异（企业需营业执照 + 对公打款验证）
- AppID / AppSecret / Access Token 按硬规则 4 只进 Config Center，仓库里只留键名

## 五、现在就能做的第一步

按成本从低到高，前两步不需要任何决策：

1. 集群内起临时 Pod 跑 `curl ifconfig.me`，与 `<operator-egress-ip-a>` 比对；隔天复测确认不漂
2. 个人主体注册机器人、配沙箱群（≤20 人），跑通一条被动回复——沙箱不受 IP 白名单约束，这两步互不阻塞
3. 上述跑通后，再按 [`issues/02`](../../.scratch/qqbot-integration/issues/02-qqbot-服务骨架与事件接入.md) 建服务骨架

前两步做完，才第一次有了「它能给本项目带来什么」的实证答案。在那之前，本文与 `.scratch/qqbot-integration/` 下的全部内容都是纸面推演。
