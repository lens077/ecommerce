## 分层论证

### §1 消息/事件流：NATS JetStream（单选）

- **高性能**：无 JVM、单二进制，资源脚印比 Redpanda（Seastar 按核预留内存）小一个量级，契合自建小集群。诚实说明：近两年**没有**可复现的 Redpanda vs JetStream 独立横评，厂商「10x」数字不可作横向依据；上线前按本项目负载（1KB protobuf、RF=3、fsync/ack 明确）自测 p50/p99 与积压恢复才算数。
- **Go 支持**：本体 Go；`nats-server` 20,547★/Apache-2.0/v2.14.5（2026-08-12），`nats.go` 6,725★ 活跃（[releases](https://github.com/nats-io/nats-server/releases)）。全 Go 同族，与 connect-go/OTel 零摩擦。
- **广泛使用**：CNCF incubating；2025 年 Synadia 治理风波以利好收尾（商标归 Linux 基金会、Apache-2.0 延续）。KEDA 有官方 [nats-jetstream scaler](https://keda.sh/docs/latest/scalers/nats-jetstream/)，ClickHouse 有[原生 NATS 表引擎](https://oneuptime.com/blog/post/2026-03-31-clickhouse-nats/view)——与 §7、§3 直接联动。
- **否决 Redpanda**：仓库为 [BSL 源可用许可](https://github.com/redpanda-data/redpanda/blob/dev/licenses/bsl.md)非 OSI（12,463★，v26.2.1）；本项目没有存量 Kafka 消费者，「Kafka 生态兼容」价值为零，却要吃 C++ thread-per-core 的资源账。franz-go 本身健康（3,013★，BSD-3，tags v1.21.x 持续更新），若未来走 Kafka 协议它仍是首选客户端。
- **配套**：
  - relay **自写**：复用 Config Center 的 pg_notify LISTEN/NOTIFY 全套生产经验，仅 6 类领域事件；[pgstream](https://github.com/xataio/pgstream)（1,177★，Apache-2.0，v1.4.1）作未来需要 WAL 断点续传时的升级件。
  - **Sequin ❌ 停更确认**：最后推送 2026-02-23，半年无活动，不能作为新依赖。
  - 配置式管道如需要，用 MIT 的 [Bento](https://github.com/warpstreamlabs/bento)（2,103★，v1.20.0，[fork 声明](https://www.warpstream.com/blog/announcing-bento-the-open-source-fork-of-the-project-formerly-known-as-benthos)）而非许可证混杂（无 SPDX、Apache/Enterprise 混合）的 Redpanda Connect。
  - **Numaflow 🟡 观察**：2,825★/Apache-2.0/v1.8.3 活跃，官方支持 JetStream source，但 Intuit 单厂商 + CRD/controller 处理面对单人集群过重。
  - WarpStream 已并入 Confluent 产品线，不作自建候选。

### §2 搜索：Typesense 主选 + pgvector 语义召回（组合）— 与雷达初判不同

雷达初判是 Meilisearch（2.2），本稿改推 **Typesense**（2.3）。分歧点只有一个但是硬的：**开源版 HA**。

- **高性能**：纯内存索引 + raft 集群，即时搜索延迟最低档；电商门面搜索挂了等于营收挂了。Typesense 开源版自带 [raft 3/5 节点集群与自动故障转移](https://typesense.org/docs/guide/high-availability.html)；Meilisearch 开源自托管是单机形态（HA 归 Cloud，见前文事实 2）。代价：Typesense 集群是全量副本不分片，内存 ×3，商品目录中等规模可承受，上线前按真实商品 schema（含 facet 倒排、同义词、typo 索引）压内存。
- **Go 支持**：官方 `typesense-go`（Apache-2.0，317★，v3.2.0 2025-03，仓库 2026-07 仍推送——SDK 节奏偏慢，接入前做 API 兼容 POC）；Meilisearch 的 `meilisearch-go`（678★，v0.36.3）更活跃，这一条 Meilisearch 占优。
- **广泛使用**：typesense 26,452★/GPL-3.0（服务端自用不修改分发，不触发义务）/v30.2（2026-04）；meilisearch 59,017★/CE=MIT。单看广度 Meilisearch 赢。
- **留给拍板的唯一二选一**：接受「单机 + 备份重建」的可用性模型 → 选 Meilisearch（社区最大、DX 最好、SDK 更活跃）；要求开源版内置 HA → 选 Typesense。本稿按「门面搜索 = 营收路径」取后者。
- **向量/语义召回**：**pgvector 起步**（22,677★，[Pigsty 原生打包](https://pigsty.io/docs/pgsql/ext/)，零新组件，pgx 直连，事务内原子更新 embedding）；embedding 达数百万级或 HNSW 内存挤压交易库时，迁 **Qdrant**（34,064★/Apache-2.0，官方 Go client 与服务端同版同日发布）。Milvus/Vald/LanceDB 均不优于此路线。
- **ParadeDB 修正一个事实**：Pigsty **确实打包了** [pg_search 0.25.2](https://pigsty.io/ext/e/pg_search)（依赖 pgvector，PG 15-18，需 `shared_preload_libraries`），「全并进 PG」路线技术上可行；但 AGPL-3.0 + 生产案例弱于 Typesense，作激进备选不作主选。
- **数据同步路径**：PG 为唯一事实源，商品写入事务同时写 `search_outbox`，独立 Go indexer（`FOR UPDATE SKIP LOCKED` + 幂等版本）批量 upsert 到搜索引擎；embedding 走异步 worker 写回 `product_embeddings`。不为搜索引 CDC 组件。
- Elasticsearch 按计划退役（去掉最后一个 JVM）；Quickwit 被 Datadog 收购后仍在发版（11,524★，v0.9.0）但定位是日志/大规模检索，不适合门面搜索，归 §8 备选。

### §3 数据层：保持 Pigsty，引进 ClickHouse — 修正雷达 3.1

- **CloudNativePG 不上（🟡 观察）**：雷达写 3.1 时未考虑 PG 实际由 Pigsty 托管在集群外（Patroni HA + pgBackRest PITR + pgbouncer 已有）。CNPG（9,155★，v1.30.0，2026-06-29；CNCF 尚在 [incubation 尽调阶段](https://github.com/cloudnative-pg/governance/milestone/1)未完成）的边际收益是「PG 进 K8s 声明式管理」，而迁移要搬数据、切连接、重做备份/监控/恢复 Runbook，还把关键库绑到本地盘 K8s 节点——当前为负收益。真正该做的是：pgBackRest 仓库异地化 + 季度 PITR 演练（Pigsty 单机仍是物理单点）。
- **ClickHouse ✅ 引进（单节点起步）**：埋点漏斗/GMV/实时报表的性能天花板；49,345★/Apache-2.0/v26.6 stable；官方 Go driver [clickhouse-go](https://github.com/ClickHouse/clickhouse-go)（3,330★，v2.48.0，2026-08）。摄入链路用原生 [NATS 表引擎](https://oneuptime.com/blog/post/2026-03-31-clickhouse-nats/view) + 物化视图直连 §1 的 JetStream，不需要 Kafka。单节点是 SPOF，对可重放的埋点数据可接受；资源起步预留 4C/8GiB、生产建议 16GiB 起，数据目录放 localPV SSD。
- **GreptimeDB/Databend ❌**：前者 2026 年才推进 v1.0 GA 且主轴偏时序；后者仓库许可证 NOASSERTION，未澄清前不进核心路径。
- **PeerDB 🟡 PoC 备选**：AGPL-3.0，3,243★，v0.37.4（2026-08-13）仍活跃；等 CH 基线稳定后再验证 PG→CH CDC（PG 版本/DDL/TOAST/断点恢复）。

### §4 身份/授权/凭据：三个「保持」+ 一组「引进」

- **授权：保持 Casbin，OpenFGA 新域试点**。
  - Casbin（20,330★/Apache-2.0，v3.10.0）在网关进程内做 check，零网络跳，是延迟最优解，现有 RBAC+继承够用。
  - OpenFGA [2025-11 已成 CNCF incubating](https://www.cncf.io/blog/2025/11/11/openfga-becomes-a-cncf-incubating-project)（5,625★/Apache-2.0，v1.18.3，官方 Go SDK 活跃）；「商家-店铺-商品-操作员」ReBAC 需求落地的**第一个新域**用它试点，不做全量迁移。注意其官方[生产指南](https://openfga.dev/docs/best-practices/running-in-production)明确 check 延迟依赖缓存与关系图形态，营销数字不当 SLA；双引擎期防策略漂移。
  - SpiceDB（6,975★/Apache-2.0，v1.56.0）能力相当、可自托管，输在 CNCF 中立治理；仅在需要 Watch/Operator 级运维工具时替代。Cerbos 是 ABAC/PDP 定位不解决关系图；Permify AGPL 排除。
- **IdP：保持 Casdoor，设迁移触发条件**。Casdoor 14,226★，v3.154.4（2026-08-18）活跃，健康度不支持盲迁；应订阅其 Security Advisories、锁版本、缩短升级窗口。Zitadel（14,788★，v4.17.1）工程质量高一档但 **AGPL-3.0**（v3 起）+ 换 IdP 动静最大；触发条件 = Casdoor 高危 CVE 响应不及时 / 企业 SSO 与治理能力缺口阻塞业务。Ory Hydra+Kratos 双组件对单人团队过重（且 2026-03 后 release 放缓）。
- **凭据管理（事故整改固化，本节价值最高）**：
  - 主链路：**external-secrets(ESO) + OpenBao**。OpenBao（7,091★/MPL-2.0，v2.6.2，Linux 基金会治理）作专职凭据后端，替代转 BSL 的 Vault；ESO（6,797★，chart v2.9.0）将其同步为 K8s Secret，ArgoCD 只部署 ExternalSecret/SecretStore。ESO 维护者危机已收尾（见前文事实 3），仍建议锁 chart/image digest。
  - 补位：**SOPS + ksops**（22,861★/MPL-2.0，v3.13.3）覆盖 bootstrap 与少量 GitOps 静态密文，兼作 ESO/OpenBao 故障时的应急恢复路径。
  - sealed-secrets 不作主选（只管静态密文、无轮换；Bitnami/Broadcom 2025 变故未直接波及该项目但供应链上游需锁 digest）。Infisical 会引入新供应商控制面，不选。
- **证书/工作负载身份**：**trust-manager ✅**（394★但属 cert-manager 官方家族，v0.24.0，低复杂度高收益——正面解决 CA bundle 挂载遮蔽系统 CA 的坑）；**SPIFFE/SPIRE 🟡 观察**（2,493★健康，但 attestation/信任域体系对 10 服务小集群过重，跨集群身份成硬需求再试点）。

### §5 网关与流量面：短期保持自研，做减法优先

- **南北向网关：保持自研 kratos-gateway fork（短期）**。
  - 理由：全 Go 本体天然拿满「Go 支持度」；含 11 个业务中间件（Casbin/JWT/BBR/transcoder），迁移即重写——Envoy Gateway 路线要把 Casbin 外置成 ext_authz 服务、aegis BBR 与 Connect 三协议特性重新验证；且当前没有任何数据面瓶颈实测证据。
  - **长期演进候选定 Envoy Gateway**（2,965★/Apache-2.0，v1.9.0 2026-08-15，JWT/ext_authz/限流/HTTP3/WASM 齐备）。触发条件：需要 Gateway API 生态位、WASM 插件体系、或压测证明自研数据面成为瓶颈。
  - 其余否决理由：APISIX（17,007★）性能口碑好但 NGINX+Lua 技术栈 + etcd 额外运维面，单人不值；Higress（9,143★）的 Go 插件实为编译到 WASM 而非原生 Go 进程扩展，且生态偏阿里系；Kgateway（5,665★）迁移成本同样高；KrakenD 只适合 BFF 聚合位。各家 benchmark 均为厂商自报（如 [APISIX 单核 18k QPS](https://api7.ai/learning-center/api-101/apache-apisix-open-source-api-gateway)、[Higress WASM AOT +50%](https://www.alibabacloud.com/blog/601025)），无统一横评，不作排名依据。
- **东西向：不上网格**。用已有 Cilium 组合：[WireGuard 节点间透明加密](https://docs.cilium.io/en/stable/security/network/encryption-wireguard/) + NetworkPolicy + [Hubble](https://docs.cilium.io/en/stable/observability/hubble/) 网络观测，零新增组件。
  - **诚实边界**：这是节点间传输加密，**不是 workload 级 mTLS**（同节点流量不加密），也没有 L7 重试/超时/金丝雀治理。当前服务间调用本来就未接线（matrix 里全是 planned），此边界可接受。
  - 未来触发（多团队/高危服务需要工作负载身份 + L7 治理）→ PoC **Istio ambient**（38,359★，graduated，v1.30.3）。
  - **Kmesh ❌**：仅 750★、latest release 2025-12、华为单厂商——「广泛使用」硬不达标。**Linkerd ❌**：数据面 Rust 非 Go，稳定版发布政策绑定 Buoyant 商业渠道（GitHub 只有 edge 版本），其 [2026 对比文](https://www.buoyant.io/articles/linkerd-vs-istio-ambient-mode-an-operators-architecture-comparison-for-2026)属厂商偏差材料。
- **南北向 LB：零新增**，维持 Cilium LB-IPAM + L2 Announcements（现有 192.168.3.110/114 两个 VIP 即此形态）。注意官方标注 [L2 Announcement 为 Beta](https://docs.cilium.io/en/stable/network/lb-ipam/)，安排一次 VIP 故障切换演练；机房有路由器后切 BGP。MetalLB（8,327★）与 Cilium 能力重复；kube-vip 定位控制面 VIP；LoxiLB（1,870★）无对应需求。

### §6 服务发现：Consul 退役采纳

- **三重收益**：少一个有状态组件；消掉 gossip 明文/8501 未启 HTTPS 的安全债；躲开 HashiCorp [BSL 许可证](https://www.hashicorp.com/en/blog/hashicorp-adopts-business-source-license)（实测 `hashicorp/consul` 仓库 license 已显示 NOASSERTION）。
- **目标形态**：网关直连 K8s ClusterIP（`service.namespace.svc.cluster.local`），靠 Cilium KPR 的 eBPF socket LB 选后端；服务侧删除 Registrar，CoreDNS（14,256★，graduated）为解析面。
- **关键技术风险要点名**：gRPC/h2c 长连接建立时即钉死单 endpoint，KPR 不做逐 RPC 重均衡，低连接数网关会打偏。对策按序：网关侧每 endpoint 多连接 + 优雅连接轮换 → headless Service + DNS A 记录轮询（注意 Go resolver TTL）→ 网关 watch EndpointSlice 自建端点连接池并做 drain。
- kratos 官方 kubernetes registry contrib 自标[「未生产验证，仅供参考」](https://pkg.go.dev/github.com/go-kratos/kratos/contrib/registry/kubernetes/v2)，不作首选。
- **迁移四步**：① 每服务建 ClusterIP + readiness/terminationGrace → ② 网关双写影子解析（Consul vs Service）比对 → ③ 灰度切 ClusterIP、观察连接分布与错误率 → ④ 删 Registrar、退役 Consul、收紧 NetworkPolicy 并开 WireGuard/Hubble。

### §7 弹性/调度：KEDA 引进，Kruise 试点

- **KEDA ✅**（10,446★，CNCF graduated，v2.20.2）：[`nats-jetstream` scaler](https://keda.sh/docs/2.20/scalers/nats-jetstream/)按消费积压扩缩（该 scaler 为社区维护，试点时验收 lag 语义）+ [`cron` scaler](https://keda.sh/docs/2.20/scalers/cron/) 大促预热保底副本。固定节点无法造容量：`maxReplicaCount` 按节点余量圈死；与已有 VPA 分工明确（KEDA 管副本数、VPA 管 request），避免同调同一指标。
- **OpenKruise 🟡 单服务试点**（5,320★，v1.8.5）：原地升级/镜像预热对发布体验的价值真实，但 Deployment→CloneSet 是工作负载语义迁移，先挑 1 个无状态服务验证与 ArgoCD 的协作，不全量吃。
- **Karpenter ❌**（固定节点自建集群无意义）；Goldilocks 可选（已有 VPA 时仅是可视化）；OpenCost/kube-green 需求出现再说。

### §8 可观测性：同族收敛

- **日志拍板：VictoriaLogs ✅ 替 Loki**。
  - 与已有 VictoriaMetrics 同族同运维模型；独立仓 [VictoriaLogs](https://github.com/VictoriaMetrics/VictoriaLogs) 2,171★/Apache-2.0，v1.52.0（2026-07-16），cluster 版随 [v1.46.0（2026-02-23）](https://docs.victoriametrics.com/victorialogs/changelog)线 GA；[Grafana datasource 插件](https://github.com/VictoriaMetrics/victorialogs-datasource)（v0.31.0）持续维护。
  - 性能证据：第三方个案（[TrueFoundry 对比](https://www.truefoundry.com/blog/victorialogs-vs-loki)：摄入 66 vs 20 MB/s、CPU 2 vs 4 vCPU、内存 1.3 vs ~4 GiB）方向一致，但属厂商个案不作通用基准。
  - Loki（28,764★/AGPL-3.0，v3.7.6）「广泛使用」占优，但性能/资源与同族运维两条输。**落地节奏：先单机版，量级到了再切 cluster**。Quickwit/OpenObserve 备选记录在案，不进主路径。
- **采集器：Vector ✅ 替 fluent-bit**（22,408★/MPL-2.0，v0.57 线，Datadog 治下发版正常）：DaemonSet 收容器日志，**VRL 重写失效的 PII 脱敏**（P0 整改项顺手落地；VRL 自带单元测试机制，比 Lua 模式可验证）。不推荐 OTel Collector filelog「一把抓」：应用日志已走 OTLP-HTTP 直发，节点级容器日志归 Vector，链路各自清晰。
- **链路：保持 Jaeger**（23,120★，graduated，[v2 已基于 OTel Collector 重构](https://www.cncf.io/blog/2024/11/12/jaeger-v2-released-opentelemetry-in-the-core)，v2.20）；Tempo（5,442★/AGPL）仅在需要 TraceQL/对象存储规模化时再议。
- **Profiling：短期 PoC 用 Parca**（Apache-2.0，v0.28）而非雷达初判的 Pyroscope（11,630★/**AGPL-3.0**，v2.2.1，更活跃）：自用两者义务都可控，但 Parca 许可干净、eBPF + Go pprof 双模同样契合；用法定为「大促前/回归排查时短期开」，不上常驻。若最终更看重 Grafana 集成成熟度，Pyroscope 是可辩护的反向选择。
- **eBPF APM/自动插桩：不上**。已有 OTel 全手动插桩 + Hubble 白拿网络层观测，再引 Coroot/Pixie/DeepFlow/Odigos 属重复采集。Coroot 🟡 留观察位（7,878★/Apache-2.0，v1.24.5，历史上有过许可反复，用则锁版本）；Pixie 最新 release 停在 2025-01，否决。

### §9 交付/构建/测试

- **金丝雀：Argo Rollouts ✅**（3,559★，v1.9.1；AnalysisTemplate 的 [Prometheus provider](https://argo-rollouts.readthedocs.io/en/stable/analysis/prometheus/) 直连 VictoriaMetrics）。**关键耦合点**：网关现经 Consul 直连 pod IP，任何基于 K8s Service/Gateway API 的流量切分都不生效——**Rollouts 必须排在 §6 Consul 退役之后**，此前只能做「副本分批」。Flagger（5,390★，v1.44.0）同样健康（「已停滞」不成立），选 Rollouts 纯因 ArgoCD 同生态一个操作面。
- **构建：ko ✅ 试点**（8,497★，v0.19.1）：10 个服务全命中 `CGO_ENABLED=0`，免 Dockerfile 秒出多架构镜像 + 默认 SBOM；保留 buildx 主线做兼容过渡。**分发：Spegel ✅ 试点**（3,742★/MIT，v0.7.4，无中心组件 P2P 镜像缓存，需 containerd）解大促扩容拉镜像；Dragonfly（graduated 但 Manager/Scheduler/SeedPeer 控制面过重）与 zot（已有三镜像仓，重复建设）否决。
- **压测：k6 ✅**（31,282★/AGPL/Go，v2.2.0，压测事实标准，需要时即采纳）。**混沌：缓**——Chaos Mesh（7,847★，v2.8.4）与 Litmus（5,599★，3.31.0）都仍活跃（雷达可改笔：不是项目衰减问题），但混沌体系对单人团队现阶段收益不足，先用 staging 故障演练 Runbook 顶。Keploy/Testkube 记录在案不引。
- **内环开发：mirrord ✅ 替 Okteto**（雷达 9.11 升级为采纳）：MIT/5,271★/v3.249.0 周更；本地进程注入 + 集群临时 agent，[官方明确不创建/不缩容 Deployment](https://mirrord.dev/docs/overview/introduction/)——**根治 okteto up 与 ArgoCD selfHeal 冲突、必须手工开关 devwindow 的坑**（该坑记录在 `context/team/okteto-inner-loop.md`）。Okteto 自托管现为 license-key 免费层模式，不再是无条件开源自托管。mirrord 默认用 mirror 模式、限定 dev/staging，防误 steal 生产流量。

### §10 存储/备份：一个立即、一个止血

- **Velero ✅ 立即引进**（10,243★，v1.18.2；CSI 插件自 1.14 并入主仓）——集群灾备是唯一「空白格」，优先级全场最高。顺序：① 独立 S3 备份桶放集群外 → ② 备集群资源 + 关键 PVC（先实测验收 OpenEBS LVM localPV 的 CSI snapshot：装 CRD/controller、创建/恢复/异机恢复语义）→ ③ **每周恢复演练到隔离 namespace** → ④ 配合 Pigsty pgBackRest 异地化补数据库侧 → ⑤ 写节点丢失 Runbook。K8up/Kanister 仅在需要应用一致性 hook 时补充。
- **对象存储：MinIO → SeaweedFS 列入正式迁移**。MinIO 上游已归档（见事实 1；最后 release 2025-10-15，AGPL，无安全补丁），扛商品图不可长期接受。SeaweedFS：**Go 本体**/Apache-2.0/34,149★/4.42（2026-08），三指标全达标；Garage（AGPL，4,377★）轻量备选；RustFS（31k★ 但无正式 release）只看不碰。节奏：Velero/pgBackRest 等**新增备份流量即刻不写 MinIO**；商品图完成 S3 兼容 PoC（签名/multipart/presigned URL/生命周期）后迁移。加速触发：出现未修复 CVE 或 SDK 兼容故障。
- **块存储：不动**。Longhorn v2 引擎仍按技术预览对待（hugepages/NVMe-oF 前提、实例管理器 ~1 CPU，[配置要求](https://oneuptime.com/blog/post/2026-03-20-configure-longhorn-v2-data-engine/view)）；Piraeus operator 社区信号弱（552★）。OpenEBS LVM localPV 继续，节点级风险由 Velero 补偿；触发迁移条件 = 出现跨节点块存储/近零 RPO 硬需求且能配三节点专用 NVMe。

### §11 安全/供应链：同栈闭环

- **运行时安全：Tetragon ✅**（4,936★/Apache-2.0，v1.7.0）：与已有 Cilium 同栈复用 eBPF 与运维面，不新增独立 daemon 体系。诚实说明两点：它是 Cilium 生态项目而非独立 CNCF 身份；**没有**可信的 Tetragon vs Falco 同条件开销横评——「开销远低」不写进验收，各开一周实测 CPU/内存/p99/事件丢失率再定稿。Falco（9,284★，graduated，0.44.1）规则生态最大，作合规向备选。
- **准入 policy：Kyverno ✅**（8,053★，**已 CNCF graduated**——比雷达登记时更进一步；v1.18.2）：YAML 策略门槛低，路线 = 先 Audit 后 Enforce（禁 latest、强制资源限制、runAsNonRoot、只允准指定 registry、镜像验签）。Gatekeeper（4,265★，v3.23.0）同样健康，但 Rego/ConstraintTemplate 成本对单人不值。
- **供应链闭环**：CI 内 gitleaks → **Syft** 出 SBOM → **Trivy**（37,509★，v0.74.0）扫镜像/IaC/密钥高危阻断 → 只推 digest → **cosign**（6,222★，v3.1.3）签名附 SBOM/provenance → **Kyverno verifyImages 准入验签**。Grype（12,765★）作二次抽检。**Ratify ❌**：迁入 notaryproject 后仅 308★，不给单人团队加独立验证平面。keyless 身份/issuer、私有仓、离线验签要提前设计；紧急放行走时限 + 审计例外。

### §12 应用架构

- **Dapr ❌ 不引进**：graduated/26,025★/v1.18.3，「广泛使用」满分，但对本项目是负收益——官方生产配置每 sidecar [100m CPU/250Mi 起步](https://docs.dapr.io/operations/hosting/kubernetes/kubernetes-production/)，10 服务 ≈ 白吃 1 vCPU + 2.5GiB request 还不含控制面；其 [outbox](https://docs.dapr.io/developing-applications/building-blocks/state-management/howto-outbox/) 要求业务改走 Dapr 事务 state API，与已定稿的 pgx/sqlc outbox 设计（`docs/design/order/consistency.md`）直接冲突。自研 relay + NATS 直连是更优解；未来跨语言/服务数显著增长再重估。
- **特性开关：OpenFeature ✅ + Flipt v2**：
  - OpenFeature 是 CNCF incubating 的开关标准，[Go SDK](https://openfeature.dev/docs/reference/technologies/server/go/) 支持 targeting/hooks/tracking，先采纳标准锁 API。
  - 引擎主选 **Flipt v2**（4,873★，v2.11.0，[Git-native 单二进制无外部依赖](https://docs.flipt.io/v2/introduction)）：服务侧流式拉快照后**进程内评估**，大促请求路径零网络跳。注意许可证：v2 为 [FCL fair-source](https://docs.flipt.io/v2/licensing)（自托管免费、非竞争限制、每版本 2 年后转 MIT），接受度需拍板。
  - 备选：零新增路线 = 给自研 Config Center 写 OpenFeature provider（复用 pg_notify 推送与权限审计）；GO Feature Flag（2,085★/MIT）个人项目 bus factor；flagd（974★）daemon 形态多一跳。Unleash 服务端 Node+AGPL，不引。
- **其余一句话**：Knative/KubeElasti ❌（常驻电商服务与 scale-to-zero 不合）；OpenFaaS ❌（社区版/商业边界）；WASM 仅留 **Spin** 观察位（6,502★，v4.0.2）；youki ❌（收益不可兑现、引入运行时排障风险）；Envoy AI Gateway ❌（无 LLM 场景）。
