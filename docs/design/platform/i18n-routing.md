# i18n URL 与语言路由策略

> **设计草案（2026-08-08 新增），不是现状描述。**
> 现状（真相源在 `frontend/packages/i18n`，以代码为准）：前端为 react-i18next 纯运行时方案，
> 支持 `zh-CN`（默认）+ `en`；语言状态存 localStorage（桌面端落 `settings.json`），
> 探测优先级 `?lang=` > 存储 > `navigator.language` > `zh-CN`；**URL 不含语言段、切换语言不改 URL**，
> 各 app 为纯 Vite SPA、无 SSR/预渲染。本文只回答一个问题：**要不要把语言放进 URL、怎么放**，
> 不改动已经成立的运行时方案。落地前本文任何一节都不代表"已实现"。

## 一、这是一个 URL 决策，不是文案问题

文案怎么翻是 `packages/i18n` + Crowdin 的事，已经有解。本文要定的是**语言要不要进 URL**——
它决定三件当前做不到的事：

1. **搜索引擎能否分别收录中英文**。现在同一个 URL 靠客户端切换承载两种语言，爬虫只会看到一种，
   另一种语言的页面在搜索里不存在。
2. **能否分享/收藏"某个语言的某一页"**。现在把链接发给别人，对方看到的语言取决于他自己的
   localStorage 和浏览器语言，不取决于链接。`?lang=` 能凑合做深链，但它不是可收录的规范 URL。
3. **能否按语言做规范化（canonical）与 hreflang 标注**，让搜索引擎理解"这两页是互为翻译"。

结论先行：**面向搜索引擎的公开页走子目录 `/:lang/`，登录后的应用内维持现状的客户端切换。**
下面先解释为什么排除其他方案，再给落地设计。

## 二、URL 方案对比

| 方案 | 形态 | 地理/语言信号 | 域权重 | 可分地域托管 | 运维成本 | 判断 |
|---|---|---|---|---|---|---|
| **子目录** | `example.com/zh-CN/` | 中 | **集中** | 难 | **最低** | ✅ 采用（公开页） |
| 子域名 | `zh.example.com` | 中高 | 分散 | 易 | 中 | ❌ 我们无分地域部署需求 |
| ccTLD 国别域 | `example.cn` | 最强 | 各自独立 | 易 | 最高 | ❌ 做的是语言不是国家市场 |
| URL 参数 / 纯 cookie | `?lang=zh` | 弱/无 | — | — | 最低 | ⚠️ 仅用于登录后免收录页 |

取舍要点：

- **子目录 vs 子域名**：两者 Google 处理相近，但子目录把外链权威集中在同一个域、且运维最省
  （一个域一张证书、cookie/session 天然共享）。子域名的价值在"独立部署与隔离"——我们是**单域名 +
  统一网关**的架构，没有把 `en` 站单独部署到另一套设施的需求，子域名只会平白增加证书与跨子域登录态的成本。
- **ccTLD** 给的是国家级信号，代价是每个域从零积累 SEO + 各国注册合规，只有做"国家市场"（而不只是
  翻译语言）才值得，与当前目标不符。
- **`?lang=`** 对需要收录的页面是硬伤（重复内容、非规范 URL），但对**登录后、本就不该被收录**的
  应用内页面完全够用——现状正是如此，不必为它引入路径段。

## 三、决策

1. **公开可收录页** → 子目录 `/:lang/`：落地页、商品详情、分类、营销页等对 SEO 有意义的路由。
2. **登录后应用内** → 维持现状：`consumer/merchant/admin` 的操作界面靠 `setLocale` 客户端切换 +
   localStorage，**不引入路径段**。这些页面不需要被收录，加路径段只会增加复杂度。
3. **明确不做**：子域名、ccTLD；不把 `?lang=` 用于任何希望被搜索引擎收录的页面。

## 四、落地设计

### 4.1 默认语言的 URL 形态

采用**默认语言裸路径、其余语言带段**：

- `/product/123` → `zh-CN`（默认语言，不带段）
- `/en/product/123` → 英文
- `/` 与 `/en` 互相用 `hreflang` + `canonical` 指认，`x-default` 指向 `/`（默认语言）。

理由：默认语言（`zh-CN`）是主要受众，裸路径最短且是既有链接，不引入 301。代价是路由要区分
"带 `/en` 前缀"和"不带前缀"两种形态——由 TanStack Router 的可选语言段统一处理，见下。

> 备选：所有语言都带段（`/zh-CN/…` 与 `/en/…`，`/` 302 到探测语言）。一致性更强，但默认语言
> 多一跳、且作废全部既有裸链接。除非将来语言数量增多到"没有主语言"，否则不采用。

### 4.2 TanStack Router 的语言段

在文件路由根部引入可选前缀段（示意，非最终代码）：

- 新增 `routes/{-$lang}/` 这一层可选路径参数（`zh-CN` 视为无前缀，`en` 视为 `/en`）。
- 根 loader 里解析 `params.lang`，收敛到受支持 locale；非法语言 → 404 或重定向到默认语言。
- 解析出的 locale 作为**权威来源**注入 i18next：在渲染前 `i18next.changeLanguage(urlLocale)`，
  并**写回 localStorage**，保证用户下次访问裸路径时不会被旧存储值拉走。

### 4.3 与现有探测优先级链的衔接

`detect.ts` 现在的链是 `?lang=` > 存储 > navigator > 默认。引入路径段后，**URL 路径段成为新的最高优先级**：

```
URL 路径段(/en)  >  ?lang=  >  localStorage  >  navigator.language  >  zh-CN
```

- 路径段命中：直接采用并写回存储（与现有 `?lang=` 的写回行为一致）。
- 应用内（无路径段的登录页）：链条从 `?lang=` 起，与现状完全一致，不受影响。
- `?lang=` 保留为深链/QA 快捷入口，但**不作为规范 URL**；命中后可 301 到对应 `/:lang/` 规范路径
  （仅对公开页）。

### 4.4 hreflang 与 canonical

每个公开页在 `<head>` 注入：

- `<link rel="canonical">` 指向自身规范 URL（默认语言裸路径 / 其余语言带段）。
- 每个语言一条 `<link rel="alternate" hreflang="…">`，外加 `hreflang="x-default"` 指向默认语言。
- `<html lang>` 已由 `applyLocale()` 同步（现状已实现），SSR 时需在服务端也写对首屏值。

### 4.5 SEO 前置条件：SSR 或预渲染（现状缺口）

**这是子目录方案能否生效的硬前提，也是当前最大的缺口。** 各 app 现在是纯 SPA：爬虫拿到的首屏
HTML 是空壳，多语言正文由客户端渲染，搜索引擎抓不全，`hreflang` 也失去意义。要让 `/:lang/` 真正
可收录，公开页必须：

- **SSR**：用 TanStack Start（Router 的 SSR 形态）在服务端按 `params.lang` 渲染对应语言首屏；或
- **预渲染**：构建期为每个 `(公开路由 × 语言)` 组合生成静态 HTML（商品这类动态页需要按数据源枚举，
  成本高，通常只预渲染落地/分类/营销页，商品页走 SSR）。

登录后的应用内不涉及此项——它本就不需要 SEO，维持 SPA 客户端渲染即可。

### 4.6 API 本地化：与页面 URL 解耦

页面 URL 的语言段**不等于** API 的语言，两条线要分开：

- 现状：后端返回的 message 以中文为主，前端 `errors.json` + `createErrorMessageResolver()` 做映射
  （中文优先用服务端更具体的 message，非中文优先用翻译）。这套已成立，短期不动。
- 目标（可选、按需）：若要让 API 直接返回多语言内容（而非前端映射），约定请求携带 `Accept-Language`
  （或自定义 header），网关**透传**给后端，后端按语言本地化。这属于后端改造，独立于本文的页面路由，
  不阻塞子目录落地。

## 五、迁移路径

1. 先补 **hreflang/canonical 注入 + `<html lang>` 的 SSR 正确性**的骨架（即使暂无 SSR 也先把 head 生成逻辑就位）。
2. 选定公开页范围（落地/分类/营销先行，商品页次之），为其引入 SSR 或预渲染。
3. 在 Router 根引入可选 `{-$lang}` 段，接通 4.2/4.3 的优先级链，默认语言保持裸路径。
4. 灰度：先对少量落地页开 `/en/`，用 Search Console 验证收录与 hreflang 无误，再铺开。
5. 应用内**全程不动**。

## 六、未决问题

- **公开页的确切边界**：哪些路由算"面向搜索引擎"需逐一圈定（涉及是否值得为其做 SSR）。
- **是否值得为电商引入 SSR**：SSR 带来运维与部署复杂度（多一层 Node 渲染或边缘函数），需权衡 SEO 收益；
  若初期只做少量静态落地页，预渲染可能比全站 SSR 更划算。
- **桌面端（Tauri）**：本地应用无 SEO 诉求，URL 路径段对它无意义，维持 `settings.json` 存储即可——
  需确保引入路径段后桌面端构建不误用公开页路由。
