# 00 从一个能响应的 RPC，到一个可靠的电商系统

[学习入口](README.md) · 下一课：[前端、网关与配置中心](01-platform.md)

## 1. MVP 的价值与边界

**MVP（Minimum Viable Product，最小可用产品）**不是「允许越权和丢钱的简化版」，而是用最小功能验证业务流程。商品 MVP 可以只有详情查询；购物车 MVP 可以没有优惠券；订单 MVP 可以只支持一种渠道。但只要接受真实写入，就必须诚实报告成功或失败。

因此要区分：

- **原型**：用假数据验证界面和流程，明确不能承诺真实交易。
- **服务骨架**：进程能启动，路由、数据库连接、配置、日志已接好。
- **单服务闭环**：一个业务操作完成校验、持久化、响应和重新查询。
- **跨服务闭环**：订单、库存、支付在重复和失败场景下仍保持正确。
- **生产就绪**：还证明了权限、容量、恢复、观测和发布回滚。

这些是递进的证明，不是靠安装组件自动升级的等级。本仓各服务处于不同位置；不能因为 search 有错误回归测试，就推导 payment 已经能够扣款。

最早 README `ac0e420f`（2025-11-06）是 Connect example：当时 GreetService 有 Register/GetAuthChallenge/SubmitAuth，前端是单 React 路由入口，尚不能从中读出十服务电商交付。

真正明确「核心业务 MVP」的是 `f3fe86d3:README.md`（2026-02-25），要求六个核心服务和完整「商品浏览→下单→支付→订单状态同步」。同文已有库存原子操作、支付幂等与数据权限要求，不能把它们统称后期增强。原文和判定见 [历史证据](13-history-and-readiness.md)。

后来 `49283008` 把架构从 README 移入历史 Design.md，再拆入当前设计目录。因此最初设计、目录新增、可执行实现、线上交付必须分别看，不能按文件现在的位置推断诞生时间。

在这个真实目标下，再用三个问题分析每个服务：**谁拥有数据、谁有权改变它、对外承诺什么**。例如购物车的单服务最小切片是读取 → 加入 → 改数量 → 删除 → 再读；它只是原始电商 MVP 的一个环节，不是整个 MVP。

服务矩阵中的十个目录覆盖了这些职责：

| 服务 | 自己应该掌握的事实 | 不应越权成为的真相源 |
|---|---|---|
| user | 应用需要的用户档案映射；现实现还承担遗留登录桥接 | 所有资源的统一归属数据库 |
| address | 收件地址及归属 | 已生成订单的历史地址 |
| merchant | 商家主体、入驻与审批状态 | Casdoor 会话真相或商品库存 |
| product | 商品目录、SKU 属性、可售与报价所需信息 | 付款是否成功、库存是否已经预占 |
| cart | 用户选购意向和条目 | 最终成交价格与库存保证 |
| search | 面向搜索的派生读模型 | 商品写入或交易计价 |
| behavior | 行为事件与推荐反馈 | 已付款、已发货等资金/履约事实 |
| inventory | 库存余额、预占、流水 | 商家订单状态 |
| order | 订单、请求事实、跨域编排 | 支付渠道实际入账事实 |
| payment | 支付尝试、渠道结果、退款与对账 | 订单是否最终接受某次付款 |

这里描述职责，不声称每一项已经实现。实际接线查 [服务矩阵](../../.service-matrix.yaml)：核查时十服务 `depends_on` 均为空，order/payment 另有 planned 依赖；领域设计里的箭头不能直接画成运行时调用图。

## 3. 高内聚、低耦合到底是什么意思

**高内聚（High Cohesion）**：一个模块里的逻辑围绕同一件事变化。库存预占、释放、余额约束应该由 inventory 统一维护；不能把扣减 SQL 散在 cart、order、payment 三处。

**低耦合（Low Coupling）**：调用方只了解必要契约，不依赖对方内部表结构和 SDK。order 可以要求「预占这一组 SKU」，不应连接 inventory 的表直接扣库存。

二者不是「类越小越好」「接口越多越好」。把一次购物车删除拆成十个透传层，并没有增加正确性。

**Module（模块）**是有接口与实现的单元，函数、包都可以是模块。**Interface（接口）**不仅是方法签名，还包括调用顺序、错误、配置和不变量。**Depth（深度）**指调用方学会少量接口后，能获得多少可靠行为。

本仓的 SearchCatalog 就是有价值的深度模块：业务只拿项目自有商品结构，Elasticsearch SDK 被藏在实现内。但当前只有一个生产 provider，不能据此夸称「已经可随意切换多个搜索引擎」。判据见 [能力接缝](../../context/team/capability-seams.md)。

## 4. 分层：不要把运行顺序当成依赖方向

以 cart 的 [server](../../backend/services/cart/internal/server/server.go)、[service](../../backend/services/cart/internal/service/cart.go)、[biz](../../backend/services/cart/internal/biz/cart.go)、[data](../../backend/services/cart/internal/data/cart.go) 为阅读样本：

```text
运行时请求：
Connect handler → service 消息/身份转换 → biz 用例 → data SQL/外部适配

编译期依赖：
service → biz 定义
            ↑
       data 实现接口

装配：server / Fx 把具体 data 实现交给 biz
```

- **service**处理协议：proto、身份输入、错误码映射。
- **biz**处理规则：允许谁做、当前状态能否做、需要哪些业务能力。
- **data**处理存储与外部系统：参数化 SQL、缓存、SDK、领域错误转换。
- **server/Fx**处理装配和生命周期：校验拦截器、HTTP、启动停止。

**依赖注入（DI）**是把依赖交给模块，而不是让业务函数自己创建数据库连接。收益是替换测试实现和统一生命周期；不是为了让构造函数看起来更高级。

## 6. 核心功能之外，系统已经做了什么

### 6.1 输入与错误

proto 的 Protovalidate 约束检查 UUID 格式、金额范围、批次数量。**格式正确不等于授权正确**：UUID 合法也可能属于用户 B。

业务错误由 data/biz 保留，service 映射到 Connect 错误码。`not_found`、`unauthenticated`、`unavailable`、`unimplemented`不是可互换的报错文案。空列表与依赖故障也不是一件事。

### 6.2 配置与连接

本仓 [configsource](../../backend/pkg/configsource/source.go) 固定来源策略；各服务 [config adapter](../../backend/services/cart/internal/pkg/config/config.go) 只实例化自己的 Bootstrap；共享实现归 go-connect-kit。

**Last-known-good（最后一份可用配置）**让坏热更新不覆盖仍可用的连接。代价是「收到新配置」和「正在使用新配置」可能不同，所以还需要 stale 指标与告警。

### 6.3 生命周期与可观测性

Fx OnStart/OnStop 管启动停止，连接复用避免每请求建连接，优雅关闭给进行中的操作完成机会。OTel 把日志、指标和 trace 关联起来。它们是业务正确性的支撑，而不是业务正确性本身。

### 6.4 工程约束

proto 生成、sqlc、goose、结构测试、部署 parity、文档门禁减少协作漂移。它们分别证明不同事实：编译能过不证明 SQL 的归属条件正确，Helm 两份相同不证明 live 集群相同。

## 7. 健壮性是管理不完美条件

| 条件 | MVP 常见假设 | 健壮实现必须回答 |
|---|---|---|
| 请求重复 | 用户只点一次 | 同一业务操作怎样去重？冲突重放返回什么？ |
| 网络超时 | 超时等于没执行 | 如何查询原结果？重试是否可能重复扣款？ |
| 并发 | 同时只有一个人改 | 谁能抢到最后一件库存？更新 0 行算不算成功？ |
| 身份 | 知道一个 ID 就能改 | 主体是谁？资源归谁？是否访客？ |
| 部分失败 | 调了下一服务就能接着跑 | 本地提交后远端失败，补偿任务存在哪？ |
| 配置更新 | YAML 改了就生效 | 客户端重建成功了吗？失败保留旧配置如何告警？ |
| 数据量增大 | 查出全部再筛选 | 最大请求量、分页、索引、超时和内存预算是什么？ |

## 8. 本课练习

**练习 S1：跟踪一次加购。** 从 proto 到 SQL，再回到 UI。写出成功响应前必须完成的动作；把缓存和数据库分开标注。

**练习 S2：删除一个看似多余的抽象。** 只做纸面实验：若删掉 SearchCatalog，业务层是否重新解析 vendor 类型？若是，它在保护 locality（修改集中在一处）；若删某个透传 wrapper 毫无影响，就需要问它是否值得存在。

**练习 S3：审查一个成功返回。** 读 order 的保存方法，回答「返回 nil 前有没有写库」。用行为断言而不是行数评价完成度。

完成理解后进入平台课。先形成这些判据，后面的性能、扩展、安全方案才不会变成组件堆砌。
