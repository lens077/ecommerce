# 13 历史证据与达标判定：原作者的 MVP 到底是什么

[学习入口](README.md) · 先读本章，再读各服务的「Git 证据」段。

## 1. 先纠正上一版教材的起点

上一版把「每服务最小 CRUD/查询闭环」作为教学 MVP，这是讲解方法，**不是原作者第一阶段的验收范围**。本次从可达 Git 历史读取原文，找到明确的阶段定义。

### 起点一：Connect 工程示例，而非完整电商

[ac0e420f，2025-11-06 的 README](https://github.com/lens077/ecommerce/blob/ac0e420f/README.md#L1-L19) 标题是「Connect example」，强调：

> 「参照了 go-kratos 的架构设计」；「使用 uber-fx 带来更好的生命周期管理」；「api 统一通过 protobuf 来编写」。

当时后端是根 backend 下的一套应用，前端是单应用入口；README 的测试示例调用 greet.v1.GreetService/SubmitAuth。它证明项目起于协议、认证与基础设施练习，不能证明已完成电商交易。

### 起点二：作者明确命名的电商 MVP

使用 Git 内容搜索定位后，最早可达命中是 **`f3fe86d3`（2026-02-25）**。已读取该提交 README，不仅看提交标题。

[原文「实施路线图」](https://github.com/lens077/ecommerce/blob/f3fe86d3/README.md#L854-L898)：

> 「第一阶段：核心业务 MVP（2-3 个月）」
>
> 「核心目标：完成电商核心交易闭环，实现可上线的最小可用版本」
>
> 「完成核心交易流程：商品浏览→下单→支付→订单状态同步全流程打通」
>
> 「交付成果：可上线的 MVP 版本，支持用户完成完整的购物流程」

作者还列出六个核心服务：认证、商品、订单、支付、库存、搜索；前端要有商品详情、购物车、下单、支付、订单列表。

**所以原始 MVP 不是十个服务各返回一次 200。** 即使今天搜索、登录、配置非常完善，只要订单不落库、支付未实现、库存不能正确预占，原始 MVP 就还没有达标。

「2-3个月」是历史计划，不是本教材给出的当前工期承诺。

### 后续阶段不能倒填进原始 MVP

原文把商家/履约/结算及后台放在第二阶段，压测/高可用深化放在第三阶段，营销/数据分析/个性化推荐放在第四阶段。cart 虽未单列为六服务之一，但购物车页面和交易链明确在首期；address 没被单列为首期服务，后来独立设计承担收货地址能力。

不能将 behavior 的晚期加入解释成首期交易的必需依赖；也不能把「第三阶段性能优化」理解为首期可以没有金额、权限或库存正确性。

## 2. 最初设计原本就要求哪些安全与一致性

同一份 [f3fe86d3 README](https://github.com/lens077/ecommerce/blob/f3fe86d3/README.md) 已要求：

- 库存操作用 PostgreSQL 事务与行锁，扣减带数量条件，保留流水与对账。
- 支付/退款幂等，回调验签，主动查询和对账补足通知失败。
- 按用户/merchant_id 过滤数据，消费者只能操作自己的资料和订单。
- 商品写入 PostgreSQL、搜索读取 ES，读写分离。

这些不是今天才添加的「奢侈功能」。现在代码违反它们，应归为**原设计未兑现**，而非可延后的性能加固。

原文也提出 Redis 分布式锁、多级缓存、全局限流和较高吞吐目标。后续设计已经收敛：当前正确性锚点是 PostgreSQL，不恢复 Redis 领域锁；容量数字要由实测验收，不把历史目标当现有能力。历史证据解释来路，不覆盖现行设计裁决。

## 3. 如何读证据，不被提交标题误导

| 证据层级 | 能证明 | 不能证明 |
|---|---|---|
| Git 文档 blob | 当时作者写下的目标和范围 | 目标已经实现 |
| 可执行源码与SQL | 当时存在的行为和可见断点 | 编译、外部服务和部署当时都正常 |
| 注释、TODO、示例 | 想做什么、建议怎么做 | 那段逻辑在运行 |
| mode 160000 gitlink | 当时引用某个外仓提交 | 外仓实现已包含在本仓历史里 |
| 具名测试结果 | 特定环境下特定行为通过 | 未测试的跨服务/线上故障路径也通过 |
| 现场端到端与恢复验收 | 该版本在该环境的行为 | 未来所有配置与版本都继续达标 |

本次仓库不是浅克隆，但早期嵌套仓的独立历史不一定在本仓对象库。因此本文用「最早可达」「最早展开源码」，不宣称找到了作者电脑上从未提交的第一份构思。

## 5. 今天是否满足原始 MVP？

**结论：尚不满足原作者定义的可上线购物 MVP。** 这不是因为缺营销、推荐或大促能力，而是原始主链仍有明确断点。

| 原始验收点 | 当前源码证据 | 判定 |
|---|---|---|
| 浏览、搜索商品 | 详情/搜索路径已存在；商品SKU映射仍有缺口，列表能力有限 | 有可用切片，不等于完整目录能力 |
| 购物车 | 有PG CRUD；数量漏参、0删除契约、shop_name等断点仍在，前端删除/数量仍本地 | 不满足完整可持久CRUD闭环 |
| 下单 | 请求未传入用例、用例空成功、Save方法只日志、响应无订单标识 | 不满足 |
| 库存预占/释放 | 数量/版本错参、忽略更新行数、非完整事务、释放未接 | 不满足 |
| 支付 | repo统一Unimplemented | 不满足；不能真实收款 |
| 订单状态同步与查询 | 可靠事件/状态落库/前端真实订单链未闭合 | 不满足 |
| 核心页面 | 页面已存在，地址交互有新修复；结算仍缺真实订单/支付结果契约 | 界面进展不等于交易交付 |

**工程原型已经远超最早 Connect example；正式交易 MVP 仍未交付。** 两句话同时成立，不矛盾。

## 6. 逐服务的 MVP / 生产判定

这些是本次源码评估结论，不是第二套进度看板；状态推进仍归 TODO。具体证据见对应章节。

| 服务/平面 | 相对历史范围 | 原始范围完成度 | 生产运行判定 |
|---|---|---|---|
| user | 首期认证+资料 | 认证切片存在，BFF已迁职责；旧令牌路径/资料主体边界待收口 | 有明确安全阻断，不宣告可用 |
| product | 首期商品目录 | 详情切片存在；SKU映射、公开字段、管理/列表尚不足 | 有正确性/信息暴露阻断 |
| search | 首期搜索 | 关键词查询切片具备；完整筛选/分页/推荐未齐 | 可隔离验证只读切片；大ID/金额/恢复/容量未完成评估，不等于生产批准 |
| cart | 首期页面和交易支撑 | 原始CRUD要求仍有写入/数量断点 | 不足 |
| address | 后续独立地址设计 | 公开区划和地址CRUD部分实现；后端归属/默认唯一仍缺 | 私有地址簿不应按现状生产开放 |
| inventory | 首期库存 | 原子预占与释放仍不成立 | 不足，阻止真实交易 |
| order | 首期订单 | 关键用例仍为空成功 | 不足，阻止真实交易 |
| payment | 首期支付 | 历史注释不能算实现，当前显式未实现 | 不足，阻止真实资金 |
| merchant | 第二阶段平台；后期有企业店MVP | 部分申请/查询；全表审批和协议桩仍阻断 | 不足；不应因管理员角色存在而放行 |
| behavior | 扩展推荐能力 | Track/Recommend切片具备，端到端身份/投影仍未齐 | 可作受限实验；重复累加与多副本补投等阻断可靠画像 |
| 前端 | 原始五类交易页面 | UI/Query/BFF与新增交互修复存在，后端主链不成立 | 只能按真实能力开放功能，不能显示支付假成功 |
| 网关 | 统一入口与鉴权 | 反代/BFF/路由等已有源码 | 需认证类别、绕过防护、CSRF/撤销及网络验收；不凭源码批准线上 |
| 配置中心 | 首轮键管理与版本竖切 | 现架构与SDK已超过原来只拉取范围 | 未重跑控制台CRUD/回滚/凭据/恢复验收，不能宣告全平台达标 |

生产的否定判定分两种：**看到明确阻断**和**关键证据未取得**。前者现在就不能交付，后者需要测试/演练后裁决，不能被等同于「一定存在bug」。

## 7. 现在受限于哪些设计选择

先把三种问题分开：**设计取舍**是明确选择承担某种限制；**实现缺陷**是代码没兑现契约；**验收缺失**是还拿不出运行证据。比如「behavior允许丢曝光」是取舍，「库存忽略0行更新」是缺陷，「没有近期压测」是证据缺口。不能全部用「架构不够高级」解释。

### 7.1 现行方案主动接受了什么限制

| 已接受的设计 | 换来的好处 | 必须接受的受限能力 | 何时、如何优化 |
|---|---|---|---|
| checkout v2全组原子、全成全败 | 不会出现一个用户意图只成交部分商家而前端不知情 | 任一SKU失败，整组不能成交；不支持无提示部分购买 | 有明确产品需求才设计用户授权的部分成交，不能后台自动剔除失败商品 |
| PG是库存/订单幂等真相，Redis是可丢加速层 | 缓存故障不抹掉已发生的业务事实 | 热点SKU与数据库事务吞吐存在上限 | 用索引、短事务、固定锁顺序、批量化和实测容量优化，不把不变量迁进无持久保证缓存 |
| 搜索/推荐使用派生投影 | 读写解耦、可重建，不让目录库承担全部检索 | 有传播延迟，不能保证所展示价格/库存可成交 | 明确新鲜度目标、断链告警与恢复，再做权威下单复验，而非同步写两套库 |
| behavior先入内存、队列满可丢 | 埋点不拖垮交易页面 | accepted不代表持久化，不能承担支付/销量事实 | 只有业务要求可靠收集时才调整ACK边界；先度量损失，不盲目增队列 |
| BFF统一会话、桌面session只存内存 | 业务前端不持长期OAuth令牌 | 网关/会话存储成为依赖；桌面重启要重登录 | 先验故障/撤销路径；明确免登录需求后再评估OS安全存储，不恢复localStorage长期token |
| gateway/config独立control-tower，共享kit基础能力 | 消除本仓重复平台实现 | 跨仓routes/Schema/依赖版本必须协调发布 | 建明确兼容窗口和同批验收，不把平台代码复制回来规避版本管理 |

### 7.2 为什么有些限制不应靠继续加组件解决

| 选择 | 当前收益 | 现在的限制 | 下一步 |
|---|---|---|---|
| 先铺多服务与基础设施 | 分层、配置、部署、观测已有统一形式 | 依赖图中的计划接口没有真正接线，操作链断开 | 先做一条可验交易切片，停止用新增平台组件代替业务实现 |
| 早期复制模板 | 新服务起步快 | 空桩/类型错位也被复制，基础设施改动要同步多处 | 共享实现已下沉kit；业务按契约和真实SQL测试修，不继续复制桩 |
| 商品/地址快照由早期参数拼装 | 快速连UI | 价格/归属可能不可信，跨服务ID不一致 | 明确权威来源、稳定标识、服务端快照与字段兼容 |
| 内存队列/事件总线 | 简单、响应快 | 崩溃丢失，不适用于资金/库存责任 | 浏览埋点明确尽力而为；交易副作用用持久事实/Outbox/Inbox |
| 宽泛目标图 | 提前想到扩展方向 | 容易误把完整蓝图当已实现或一次性施工单 | 区分原始要求、现行裁决、已实现行为、下一条实验 |

## 8. 优化顺序：先满足自己的原始承诺

1. **止住假成功与越权**：订单未实现明确失败；商家审批限定目标；地址归属；日志不含凭据。
2. **把单服务写入修真**：cart数量/插入/计数、product SKU映射、inventory事务/行数/预占状态。
3. **形成跨服务MVP**：权威报价、地址快照、组预占、订单落库、支付尝试、订单接受与可靠同步。
4. **再证明生产条件**：并发/重放/故障恢复、权限与网络、发布回滚、备份恢复、固定数据集容量和观测。
5. **最后深化优化**：有证据地做缓存、分页、批量化、弹性扩容；不为追旧文档中的大QPS数字无条件堆组件。

本次只读取历史与当前源码，并运行文档检查；未重建历史环境、未跑真实支付/交易、未检查线上集群。历史代码导出位于被忽略的本地审计缓存，正式证据以提交与路径定位，教材不依赖该缓存存在。
