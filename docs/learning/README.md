# 从 MVP 到可靠电商：架构与源码学习路线

这套教材回答的不是「用了多少组件」，而是：**一次用户操作，究竟由谁负责、何时算成功、失败后怎样恢复、如何证明不会伤到另一位用户。**

先读 [历史证据与达标判定](13-history-and-readiness.md)：原作者在 `f3fe86d3` 的 README 明确把首期 MVP 定为「商品浏览→下单→支付→订单状态同步」的完整购物流程。再按「Git 原始设计 → 当时实际实现 → 后续演进 → 当前局限 → MVP/生产判定 → 修复练习」逐服务学习。先理解为什么，再修改代码；不要照着清单一次性重写十个服务。

## 阅读边界

- **历史与源码复核日期：2026-09-25（UTC）**。基于本地 `4ce0b2a0` 和读取时的工作树，其中包含并发会话未提交的地址/结算整改；已按实际内容更新，不将未提交代码当已发布。
- **原始 MVP**引用作者 `f3fe86d3:README.md` 的明确首期范围；**服务最小切片**是从当时接口/实现提炼的教学范围，不冒充作者曾逐服务命名的 MVP。各章分别给出证据、实现缺口和适用边界。
- 历史 blob 证明当时的文字/代码存在，不证明它通过测试或线上验收。早期 gitlink 所指外仓的完整历史本次不可据本仓展开，还原边界见历史章。
- **当前实现**指已读到的源码；**当前缺陷**指源码可证明的问题；**目标设计**来自既有设计文档；**建议练习**是尚未执行的修复办法。
- 进度只维护在 [TODO.md](../../TODO.md)。本目录不维护完成勾选、线上部署状态或第二套优先级看板。学习后发现结论过期，应复核源码并修正文案。
- 规范以 [context/](../../context/INDEX.md) 为准，拓扑以 [服务矩阵](../../.service-matrix.yaml) 为准，设计以 [docs/design/](../design/README.md) 和 [TECH.md](../TECH.md) 为准。本目录解释它们，不取代它们。
- payment 的实际实现由你亲自完成；本教材提供理解和验收方法，不代替实现决定。

## 先用架构师的眼光重读 README

根 [README](../../README.md) 适合作为技术栈、目录和启动入口，但不能据此推导整个交易已经可用。

| README 中容易产生的印象 | 应当追问什么 | 本项目的学习切入点 |
|---|---|---|
| 十个微服务都有目录、镜像与部署清单 | 服务之间是否真的调用？ | matrix 的 `depends_on` 与 `depends_on_planned` 不同；目前不能把 order 的设计依赖画成已运行链路 |
| 已有 proto 和生成客户端 | 字段是否承载正确业务语义？ | 空 `CreateOrderResponse` 无法告诉前端该支付哪一组订单 |
| 已有登录和网关 | 是否检查了这条数据属于谁？ | 用户身份认证不等于地址、订单、商家资源授权 |
| 已有数据库、缓存和队列 | 成功响应对应持久化还是仅入内存？ | cart 写库、behavior 入队、payment 未实现的成功语义不能混用 |
| 有健康检查和可观测性 | 是否看得见业务没做成？ | 进程活着，不代表订单落库；配置下载成功，不代表客户端已经换到新连接 |
| 有架构分层 | 调用方向与依赖方向是否清楚？ | 请求通常 server → service → biz → data；编译依赖应让 data 实现 biz 定义的接口，而不是 biz 绑定数据库 |

README 内仍有不同时间的运行态叙述。阅读时以 TODO 的状态和必要的现场验证裁决，不能用 README 的一段旧文字证明当前集群是什么。

## 每章如何使用

1. **先复述业务目标。** 不说技术名词，用一句话解释用户想完成什么。
2. **读指定入口。** 先 proto，再 service，再 biz/data 和 SQL；只跟踪一个方法，不全仓漫游。
3. **画成功路径。** 哪一步开始写状态，哪一步才允许响应成功？
4. **插入一个失败。** 数据库超时、重复请求、用户 B 使用用户 A 的 ID，结果应该是什么？
5. **做一个薄改动。** 一次只修一个可观察行为，沿用现有工具，不重建第二套架构。
6. **留下证据。** 请求/响应、数据库结果、失败时无副作用、回归测试；不能只写「代码已完成」。

每章练习编号只用于定位学习题。是否开工、是否完成，仍回到 TODO 对应业务项，不在本目录新增平行进度。

## 什么叫「完美对接」

没有协议能保证永不出错。本教材把它改写为可验收的目标：

- 双方对身份、ID、金额单位、状态、错误码的理解一致。
- 调用超时后知道能否重试、用什么幂等键、怎样查询原结果。
- 一方升级时，旧客户端仍有明确的兼容或迁移路径。
- 失败不会造成越权、重复扣款、超卖或假成功。
- 能用契约测试与故障场景证明，而不是只靠接口文档对齐。

## 这不是评分整改计划

Repowise 的复杂度、死代码、调用图是阅读线索。`@/` 路径别名、Fx 注入、脚本入口都会让静态图漏边；低分不能证明有漏洞，高分也不能证明订单正确。先修业务不变量和契约，再考虑文件拆分、缓存和并发优化。
