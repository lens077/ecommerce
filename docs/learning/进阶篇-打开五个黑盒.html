进阶篇 · 打开五个黑盒

基础篇里我们把这五个当黑盒跳过了。现在打开它们——但目的不是让你现在就学会， 而是让你知道：里面长什么样、为什么这个项目要用它、什么信号出现时你必须真的学它、以及不碰集群也能做的实验。 每个模块结构固定：它是什么 → 原理图 → 在这个仓库里长什么样 → 什么时候必须学 → 进阶实验。

先看学习顺序建议（很重要）。 这五个黑盒不该平均用力。按「你现在多快会撞上它」排： M1 身份（你做结算页就会撞上，最先懂）→ M4 可观测性（上线后第一天就要用，第二学）→ M3 部署（从 Compose 迁到集群时才需要）→ M5 分布式一致性（出现第一个真实跨服务副作用时才触发） → M2 数据流 CDC（商品规模上来才需要，可以拖最久）。

如果你时间有限：M1 + M4 读完就够了，其余三个知道「有这个东西、什么时候找它」即可。
M1身份：Casdoor / Session / OpenFGA最先学 · 安全根 M2数据流：Kafka / Debezium / Elasticsearch可拖最久 · 规模触发 M3部署：K8s / Cilium / ArgoCD / Helm迁集群时学 M4可观测性：OTel / Grafana / vmalert上线第一天就要用 M5一致性：OrderGroup / Saga / Outbox触发式 · 别提前学
M1

身份：Casdoor / Session / OpenFGA

建议最先学 · 约 2.5 小时
MVP 现状：「身份是网关注入的，请求体里的身份一律不可信」——这句话你现在已经会用了。这一模块是把它背后的机制补全。
先想通：三题

Q1 为什么浏览器不能直接持有 Casdoor 的 access token？

因为 token 是 bearer 凭证，任何拿到它的代码都能用它调接口——XSS 偷走一个 token 就等于偷走身份。httpOnly cookie 里的 session id 偷不走（JS 读不到），而且服务端可以随时作废。

Q2 Session 存在 Dragonfly（Redis 协议）里，Redis 挂了会怎样？

fail-closed：所有人变成未登录。这是刻意选择——fail-open（Redis 挂了就放行）等于把鉴权变成可选。/readyz 必须把 session store 可达性纳入条件。

Q3 有了网关 RBAC，为什么还要 OpenFGA？对象级授权是什么？

RBAC 回答「这个角色能不能调这个 RPC」，是粗粒度的。但「商家 A 的运营能不能看商家 B 的订单」这种问题，RBAC 表达不了——它取决于对象之间的关系（用户是不是这个 store 的成员）。OpenFGA 就是干这个的。

图 1 · BFF Session 登录全流程（注意第 5 步：token 交换在服务端完成，浏览器从未见过 token）
遗留轨：legacy bearer JWT 仍是迁移残留，按 docs/TECH.md 红线属须移除项——别在新代码里用它
图 2 · 三层授权是互补关系，不是替代关系
什么时候必须真的学它：① 你要做商家子账号 / 多角色协作；② 你要开放「A 用户能看 B 用户分享的订单」这类关系型权限；③ 现有 Casbin 策略开始变得难维护（角色爆炸）。MVP 阶段第 2 层就够了。
进阶实验（不碰集群）：
  1. 读 ../control-tower/routes/dev.yaml，找 anonymous_paths 里列出的 RPC，想清楚「为什么 /user.v1.UserService/SignIn 必须匿名、而 /order.v1.OrderService/CreateOrder 必须登录」。
  2. 在 .service-matrix.yaml 的 gateway 段，看 A/B/O/C 四级路径分类，说出 optional_auth_paths 为什么对 behavior 服务是必需的。
  3. 读 STACK.md 第七章「信任边界」6 条，逐条判断你的 MVP 代码有没有违反。
  4. 写一个「漏洞演示」：临时让某个 RPC 读请求体里的 user_id，用 curl 传别人的 ID 复现越权，再改回可信身份头。亲手复现一次比读十遍记得牢。
踩坑预警：这个仓库已经因为 Casdoor 凭据踩过坑——NewCasdoorAuthClient(conf *conf.Bootstrap) 拿启动快照一次性构造 client，不随配置热更新走。所以改 Casdoor 凭据必须重启服务。你如果照抄这个模式，会继承同一个坑。
M4

可观测性：OTel / Grafana / vmalert

建议第二学 · 上线第一天就要用
MVP 现状：「出问题看日志就够，别现在搭监控」。这一模块告诉你日志怎么看、什么时候日志不够用、以及一套最小可用观测长什么样。
先想通：三题

Q1 有日志了，为什么还要 trace？

日志告诉你「发生了什么」，trace 告诉你「卡在哪一步、卡了多久」。一个请求穿过 5 个服务，日志是 5 段互不相干的文本；trace 是一条带时间轴的链，能直接看出 480ms 里有 460ms 花在哪个服务。

Q2 为什么指标标签禁止放 user_id / order_id / sku_id？

因为那是高基数字段。每个用户一个时间序列，一百万个用户就是一百万条 series，存储和查询都会崩。这些信息应该进结构化日志，用 trace_id 关联——指标用于聚合，日志用于定位。

Q3 告警搭完就完事了吗？

远没有。这个仓库的 TODO.md 里最实在的一条是「告警送达」——Alertmanager 收到告警但没送到人手里，等于没有告警。告警的价值 = 能被收到 × 有人处理，中间任何一环断了都是零。

图 3 · 三大支柱的分工（同一次故障，三种视角）
本节课重点：MVP 阶段的最小可用观测 = 结构化日志（带 trace_id）+ 一个错误率面板 + 一条能送到你手机的告警。就这三样，别的都可以等。没有告警触达的监控等于没有监控。
进阶实验（不碰集群）：
  1. 在任意服务的 biz 层加一条带 trace_id 的日志，本地 make dev 跑一次请求，从日志里找到它。
  2. 读 docs/observability/OBSERVABILITY.md，找出「指标标签禁止高基数」那条规定的原文。
  3. 给自己定一条 MVP 告警规则：下单接口 5 分钟错误率 > 5%。想清楚它要发到哪里、你多久能看到、看到后第一步查什么。
  4. （可选）用 docker compose 起一个 VictoriaLogs + Grafana，把自己的服务日志打进去——这是最小可观测栈，两个容器。
踩坑预警：这个仓库在日志上踩过的坑值得记住——code.file.path 恒为 server/logging.go，导致所有错误都指向同一个文件、无法定位真正抛错点。后来用 errinfo.Here 记录最内层调用点才修好。你如果自己写日志拦截器，务必记录真实抛错位置。
M3

部署：K8s / Cilium / ArgoCD / Helm

迁集群时学 · 约 3 小时
MVP 现状：「MVP 用 Docker Compose 跑，别碰集群」。这一模块解释集群到底帮你做了什么、以及这个仓库为什么同时维护两套清单。
先想通：三题

Q1 Docker Compose 能跑，为什么要 K8s？它到底多给了什么？

三样东西：自愈（进程挂了自动重启、节点挂了重新调度）、声明式对账（你说要 3 个副本它就维持 3 个）、服务发现与流量治理（Service/DNS/负载均衡/滚动发布）。Compose 是「启动一组容器」，K8s 是「持续维持一个状态」。

Q2 Helm 和 kustomize 都在做「生成 YAML」，为什么要两套？

Helm 是模板 + 参数（适合打包分发、给别人用），kustomize 是基线 + 补丁（适合多环境差异、改动可追溯）。这个仓库两套并存是因为使用场景不同——所以它用 verify-deploy-parity.sh 强制两份渲染结果逐字段等价。

Q3 ArgoCD 和「手动 kubectl apply」的本质区别是什么？

手动 apply 是一次性推送，推完就不知道谁改了。ArgoCD 是持续对账：Git 是期望态，集群是实际态，它不断比较并把实际态拉回期望态（selfHeal），删除 Git 里没有的对象（prune）。这就是 GitOps。

图 4 · GitOps 控制循环：Git 是唯一真相源
什么时候必须真的学它：① 你的 Compose 单机成为单点（机器一挂全站没）；② 你需要「改一行配置就滚动发布、失败自动回滚」；③ 你要跑多副本。在那之前，Compose + 一份备份脚本比一套没人维护的 K8s 清单更可靠。
进阶实验（不碰集群）：
  1. 本地跑 scripts/verify-deploy-parity.sh —— 它不需要集群，只做 helm template 与 kubectl kustomize 的渲染对比。看它输出「pre 58 对象 / prod 56 对象」时，你就理解了「两套清单等价」是怎么被强制保证的。
  2. 读 helm/values.yaml 与 helm/values-prod.yaml 的 diff，找出那 2 个被有意关掉的开关。
  3. 用 docker compose config 看你自己的 Compose 最终渲染结果——这是 Compose 版的「期望态可视化」。
  4. （可选）本地 kind 起一个单节点 K8s，把 backend/compose.yaml 里的一个服务手写成 Deployment + Service。手写一个，比读二十份清单有用。
踩坑预警：这个仓库的部署债很典型——ecommerce-config-source-{pre,prod} 这个 Secret 全仓只有引用、没有本体定义，prod 起来就缺它；prod 的 default-deny NetworkPolicy 被 values-prod.yaml 关掉了，所以线上其实是全放行。「清单里写了」不等于「线上生效」——这是集群学习和 Compose 最大的认知差异。
M5

分布式一致性：OrderGroup / Saga / Outbox

触发式 · 别提前学
MVP 现状：「那是 v2 设计，MVP 用同步调用 + 事务」。这一模块解释：为什么同步调用在 MVP 够用、它什么时候会不够用、以及不够用时的标准解法长什么样。
先想通：三题

Q1 本地事务能保证正确，为什么还需要 Saga？

因为跨服务没有本地事务。订单在 order 库、库存在 inventory 库，一个事务包不住两个数据库。你要么用 2PC（强一致但可用性差、且要两边都支持），要么接受最终一致——先各自提交，出错再补偿。Saga 就是后者。

Q2 Outbox 解决什么问题？

「业务写库」和「发消息」两步不可能同时成功——先发消息后写库，可能消息发了但库回滚；先写库后发消息，可能库提交了但服务崩在发消息中途。Outbox 把消息当成业务数据写在同一个事务里，再由外部进程搬去 Kafka。原子性回到了数据库。

Q3 为什么这个项目说「领域事件待首个真实业务生产者触发」？

因为没有真实副作用需求时，提前建一套 Outbox + Inbox + DLQ + 重放审计，是在为想象中的问题付真实成本。等第一个「下单成功后要通知库存确认」出现，再接。这个克制是对的。

图 5 · 两种跨服务写法：同步链（MVP）vs 事件链（v2）
不含业务语义，不需要 Outbox。搜索走这条，已经在跑。 · 领域事件：表达「订单已支付」这种业务事实，必须 Outbox 保证原子发布，消费者必须幂等。业务侧尚未接线。 同一套 Kafka 两种语义，混用会导致「搜索消费了业务事件」或「业务消费者被投影变更刷爆」。
本节课重点：MVP 阶段你要做的不是「用 Saga」，而是把同步链写正确——库存单条原子 SQL、订单唯一约束、失败显式返回。这三件事做对了，将来迁到事件链时，你要补的只是「发布」和「消费」两层，核心正确性不用重写。
什么时候必须真的学它：你的代码里出现第一个「下单成功后还要做别的」的真实需求——比如要发短信、要通知库存确认、要生成结算单。那一刻，先写 Outbox，再写消费者。顺序反了（先接 Kafka 再补 Outbox）会留下一段「消息可能丢」的窗口。
进阶实验（不碰集群）：
  1. 读 docs/design/order/checkout.md 的 Outbox 与超时自愈部分，只看设计，不看实现。
  2. 在本地用两个 PG schema 模拟：建一张 outbox 表（aggregate_type + payload + 已创建未发送），在同一个事务里插业务数据和 outbox 行。然后手写一个 20 行的「relay」把它读出来打印。亲手写一次 relay，你就永远理解 Outbox 了。
  3. 想清楚：relay 把消息发出去了但自己崩了，重启后会不会重发？消费者怎么保证不重复处理？（答案：至少一次投递 + 消费者幂等，靠 Inbox 唯一键）
踩坑预警：这个仓库的 order 服务现在用进程内 GoEventBus(1<<16, DropOldest)——高负载下事件静默丢弃，进程重启即失。如果你照抄「进程内事件总线」图省事，会继承一个最隐蔽的数据丢失路径。MVP 阶段宁可同步调用，也不要用会丢事件的内存总线。
M2

数据流：Kafka / Debezium / Elasticsearch

可拖最久 · 规模触发
MVP 现状：「MVP 用不到，先当它们不存在」。这一模块解释这条链路解决什么问题、以及它已经在这个仓库里跑起来了（只是不在你的 MVP 路径上）。
先想通：三题

Q1 搜索为什么不能直接查 PostgreSQL？

能，但只在小数据量下。LIKE '%关键词%' 无法用索引、要全表扫描；没有分词（「精华液」搜不到「精华」）；没有相关性排序；聚合筛选（按品牌/价格区间统计）很慢。商品上万后就必须专用搜索引擎。

Q2 什么是 CDC？它和「业务代码里发消息」有什么不同？

CDC（Change Data Capture）是从数据库的 WAL 日志里读变更，不碰业务代码。好处：业务代码零改动、不丢不错（WAL 是数据库自己的真相）、不增加写延迟。代价：它搬的是「行变化」而不是「业务意图」。

Q3 为什么搜索走 CDC、而业务事件走 Outbox？

因为语义不同。搜索要的是「商品表变成什么样了」——行的最终状态，CDC 正合适。业务事件要的是「订单已支付」这个事实，必须和业务写在同一个事务里保证原子性——所以用 Outbox。用错工具的结果：要么丢事件，要么搜索索引被无意义的事务内变更刷爆。

图 6 · 搜索行投影链路（这个仓库已经跑通，2026-09-03 切流）
什么时候必须真的学它：① 商品/内容过万，PG 查询 P99 超过几百毫秒；② 你要做「按品牌+价格区间+规格聚合筛选」；③ 你要中文分词搜索。在那之前，search_catalog 那张表和它的 trigger 就是你需要的全部。
进阶实验（不碰集群）：
  1. 读 backend/services/product/internal/data/migrations/00005_*.sql，看 products.search_catalog 的 trigger 是怎么维护投影表的——这是全仓库最值得读的一个 trigger。
  2. 读 docs/design/search/search.md，重点看「SearchCatalog 深度模块边界」——为什么 search 服务只能读固定 alias，不能让调用方指定索引名。
  3. 本地起一个 PostgreSQL，建一张商品表 + 一个 tsvector 全文索引，体验一下「PG 自带的全文检索能走多远」。这能帮你判断自己离需要 ES 还有多远。
踩坑预警：这个仓库为搜索换过三次方案（Meilisearch → 自写 indexer → ES CDC），每次迁移都留下过「mapping 不是契约」的回归——索引由 sink 自动创建，mapping 和预期不符，搜索静默返回错结果。你自己做时：mapping 必须进版本控制，alias 切换必须可回退。

收一页总结：五个黑盒的「触发条件」速查

把这张表贴在显眼的地方。看到左栏信号出现，再去学右栏——不要提前学，也不要永远不学。

模块触发信号（出现任何一个）要学什么学到什么程度算够
M1 身份 要做子账号 / 多角色协作 / 关系型权限（A 能看 B 分享的订单）；Casbin 策略开始角色爆炸 Casdoor OIDC 流程、Session 存储、OpenFGA 关系模型 能说清三层授权各自管什么；知道改 Casdoor 凭据必须重启

M3 部署 Compose 单机成单点；要滚动发布/失败回滚；要跑多副本 K8s 核心对象、Helm/kustomize、GitOps 控制循环 能手写一个 Deployment + Service；理解「清单写了 ≠ 线上生效」
M4 可观测 上线第一天（用户报「打不开」，你无法判断是前端、网关还是数据库） 三大支柱、四黄金信号、告警触达闭环 能从 metric → trace → log 三步定位一次慢请求
M5 一致性 出现第一个「下单成功后还要做别的」真实需求；同步链开始变蜘蛛网 Saga 补偿、Outbox 原子发布、Inbox 幂等、DLQ 能解释「为什么业务写和 outbox insert 必须同事务」
最后一句：基础篇教你把交易链写正确，进阶篇教你在正确之后把系统撑住。 顺序不能反——一个没有正确性的高可用系统，只是更快地制造错误。
