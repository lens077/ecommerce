第 1 课

让东西在你自己手里跑起来

约 1.5 小时 · 只改配置不改代码
教学目标：能从「敲命令」到「看到响应」，并且知道启动过程中每一步在干什么。
先想通：两题

Q1 为什么不能直接 go run main.go？

因为这个服务的启动配置不在仓库里，而在配置中心（Config Center）。selector 缺失、token 无效、key 不存在，都会直接启动失败——它不会静默降级。这是设计，不是 bug。

Q2 启动日志那行「实际生效的配置数据源」不打印会怎样？

「改了配置没生效」这类问题只能靠猜。打印了，一眼就能看出你连的是 dev 还是 pre、是文件还是配置中心。

第 2 课

一个请求的完整旅程

约 2 小时 · 纯阅读课，不动业务代码
教学目标：能不看文档画出「一次 SignIn 从网络到数据库再回来」的完整链路。这是后面所有课的地基。
先想通：三题

Q1 为什么 service 是唯一允许 import proto 生成代码的层？

因为 proto 是对外契约，会随业务演进频繁变化。如果 biz 也 import 它，契约一变，领域模型跟着抖，测试跟着崩。把「翻译」关在一层，契约演进就被隔离了。

Q2 biz 为什么不许 import data？

第一周看不出问题，第三个月出事：biz 的单元测试会悄悄变成集成测试，然后慢慢没人再跑单测——因为跑一次要连数据库。依赖方向是测试能不能跑的地基，不只是洁癖。

Q3 错误码在哪一层决定？

在 service 层。biz 只定义领域错误（带 [模块] 前缀），data 用 %w 包装保证 errors.Is 能穿透，最后由 service 映射成 Connect 错误码。更早决定会让领域层被迫知道 HTTP 语义。

图 2 · 四层依赖方向：绿箭头允许，红虚线禁止
允许 import 禁止（会被门禁拦住）
图 3 · 一次 SignIn 的完整旅程（编号对应下方说明）
1 浏览器发 /user.v1.UserService/SignIn 2 网关鉴权后剥离伪造身份头，注入可信 x-md-global-* 3 server 拦截器链：otel → log → validate 4 service 做 proto ⇄ biz 转换 5 biz 调 Repo 接口（接口在 biz，实现在 data） 6 data 发 SQL（pgx） 7 返回行 8 出错则 %w 包装，保证 errors.Is 穿透 9 service 映射成 CodeUnauthenticated 等
读代码（按这个顺序，别乱）
cmd/server/main.go            ← fx 装配顺序（谁先起谁后起）
internal/server/server.go     ← Connect handler 注册 + 拦截器链 + CORS/h2c
internal/service/*.go         ← proto ⇄ biz 转换 + 错误码映射（唯一接触 proto 的层）
internal/biz/*.go             ← 领域模型 + Repo 接口 + UseCase（纯结构，不碰框架）
internal/data/*.go            ← Repo 的真实实现（pgx / cache / 三方 SDK）
本节课重点：biz 定义 Repo 接口，data 实现它。这样 biz 的单元测试可以用假实现跑、不连数据库。这就是 biz 不许 import data 的真正原因——一旦允许，测试就悄悄变成集成测试，然后慢慢没人再跑单测。
踩坑预警：你会很想在 biz 里直接写 SQL，那是 data 的活；也会很想在 service 里写业务规则，那是 biz 的活。service 只做「翻译」。

第 3 课

契约先行：给商品加「列表」能力

约 3 小时 · 第一次完整改三层
教学目标：完整走一次「改 proto → 生成 → 三层实现」的全流程，理解为什么这个项目把 proto 当边界。
先想通：三题

Q1 商城只能看详情不能逛列表，荒谬在哪？

用户进商城的第一个动作是「逛」，不是「知道编号后精确查一个」。product.proto 现在只有 GetProductDetail，等于只有货架格子没有商场。

Q2 为什么列表必须用游标分页，不能用 OFFSET + LIMIT？

两个原因：① OFFSET 10000 要扫描并丢弃前 10000 行，越翻越慢；② 翻页期间若有新商品插入，OFFSET 会重复或漏项。游标（keyset）从「上次最后一行」继续，两者都不会发生。

Q3 为什么校验加在 proto 上而不是 biz 里？

因为 proto 是前后端共用的契约。写在 proto 上，Go 和 TypeScript 两侧同时获得约束；写在 biz 里，前端还得再写一遍，两边必然漂移。

图 4 · 契约先行：一份 proto，两边生成，四层实现
动手
  1. 在 backend/api/product/v1/product.proto 加 ListProducts：请求带 page_size、page_token（游标）、可选 category_id；响应带 next_page_token。每个字段都加 buf.validate 约束。
  2. buf generate —— 生成 Go 与 TypeScript 两份。
  3. 按第 2 课的地图从 server 开始往下写：注册 → service 转换 → biz 定义 ListProducts + Repo 方法 → data 写 sqlc 查询。
踩坑预警：前端类型是从 proto 生成的，不是你手写的。改了 proto 不重新生成，前端会拿到旧字段——这是「前端显示不出来」最常见的原因。

第 4 课

数据层：迁移、schema 与那张让你踩坑的 NOT NULL

约 2.5 小时
教学目标：理解「一个服务一个 schema」的物理隔离意味着什么，以及为什么迁移里一行小疏漏能让线上功能 100% 失败。
先想通：三题

Q1 10 个服务共用一个 PostgreSQL，为什么还要每服务一个 schema？表名前加前缀不行吗？

前缀只是命名约定，任何人任何服务都能 SELECT 别人的表。schema 是权限边界：可以做到「cart 服务的数据库账号只能看见 cart schema」。约定靠自律，边界靠权限。

Q2 为什么迁移里禁止 SET search_path？

goose 的版本表按非限定名解析。search_path 一改，版本表可能被写到别的 schema，迁移状态就乱了。所以表名必须显式限定（cart.cart_items）。

Q3 为什么 seed 数据能插入、真实加购却 500？

seed 行是手工写全字段插进去的，shop_name 有值；而 INSERT 语句里没写这一列，它是 NOT NULL 且无默认值，于是每次都违反约束。测试数据掩盖了代码路径的缺陷——这是最危险的一类 bug。

第 5 课

安全第一课：身份与归属

约 2 小时 · 修一个真实越权漏洞
教学目标：亲手修掉一个真实的越权漏洞，建立「可信身份」这个后续所有安全决策的根。
先想通：三题

Q1 网关已经做了 RBAC，为什么服务还要校验归属？

RBAC 只回答「你能不能调这个 RPC」，不回答「你能动哪一行数据」。任何已登录用户都能调 DeleteAddress，RBAC 当然放行。

Q2 用户 A 拿着用户 B 的地址 ID 调删除，谁负责拦住？在哪一层？

服务层。而且必须在 SQL 或领域层带 owner 条件（WHERE id = ? AND user_id = ?），不是「先查出来再在代码里比一下」。

Q3 为什么拦下来要返回 403/404 而不是 500？

500 表示「服务器错了」，会触发告警、掩盖真实问题，也让攻击者能区分「服务故障」和「被拒绝」。403/404 是可预期的拒绝。

图 6 · IDOR：两种写法，两种结局
本节课重点（请抄进笔记）：RBAC 决定「你能不能调这个 RPC」，归属校验决定「你能动哪一行数据」。前者是粗粒度门禁，后者是每一行查询都必须带的条件。少了任何一个，另一个都不能救你。同理：buf.validate 只校验结构，不校验权限。
动手
  1. 修 address/internal/service/address.go：创建地址不再信任请求体的 UserId，改从网关注入的 x-md-global-user-id 取。
  2. 读 / 改 / 删 / 设默认，全部在 SQL 或领域层带 owner 条件。

第 6 课

并发第一课：库存为什么不能「先查后改」

约 3.5 小时 · 全项目最重要的一课
教学目标：搞懂为什么数据库约束是正确性的最后一道防线。这一课想通了，后面所有「一致性」问题你都有直觉。
先想通：三题

Q1 库存剩 10 件，两人同时各买 8 件，「先查再改」哪里会错？

两个请求都查到 10，都判断 10 ≥ 8 成立，然后都执行扣减。库存变成 2，但实际卖出 16 件 —— 超卖 6 件。关键在于「判断」和「扣减」是两个独立操作，中间有时间窗。

Q2 用 Redis 分布式锁行不行？

能降低概率，但引入了新问题：锁超时了怎么办、加锁的服务挂了怎么办、锁本身和数据库的一致性怎么保证。你在用一个更难正确的机制去保护一个可以很简单的机制。

Q3 为什么说「约束是最后一道防线」？

应用层校验跑在进程里，进程会重启、会有多副本、会有 bug。数据库约束跑在数据库里，进程死了它还在。所有判重的最终依据都应该是唯一约束，所有扣减的最终依据都应该是单条原子 SQL。

图 7 · 库存扣减：错误做法 vs 正确做法
动手
  1. 重写 inventory 的 Reserve 与 ReleaseReserve：判更新行数（0 行 = 库存不足），不要「先 SELECT 再决定」。
  2. 配 stock_ledger 流水表：每次预占 / 确认 / 释放都记一行，可对账。
  3. reservation_id 加唯一键做幂等：同一订单重复提交只扣一次。
  4. 多 SKU 预占放进同一个事务（data.go 已提供 ExecTx，现在没用上）。
  5. 顺手把 inventory.proto 的请求体补全——现在它是空结构体，根本无法表达「释放哪个订单的哪些 SKU」。
踩坑预警：多行扣减要按同一顺序（比如 sku_id 升序）执行，否则两个事务互相等待会死锁。现在的代码把防死锁排序整段注释掉了，别学。另外，别在事务里做外部调用（HTTP、支付）——事务要短。
验收（这节课的验收最硬）
第 7 课

事务、幂等与「假成功为什么最危险」

约 3 小时
教学目标：修掉 order 的假成功，并建立对幂等的正确直觉——幂等的层次是数据库，不是应用。
先想通：三题

Q1 CreateOrder 返回 {} 和 200 但什么都没存，为什么比 500 危险十倍？

500 会触发告警、留下日志、用户知道失败了。空 200 是静默的数据丢失：用户以为下单成功，你的库里什么都没有，没有任何地方记录这次失败。等你在对账时发现，已经过去几周，损失无法追溯。

Q2 用户连点两次「提交订单」会发生什么？

没有唯一约束的话，生成两组订单、扣两次库存。你必须在某处判重——而那个地方不能是应用层的 map 或 Redis（进程重启、多副本都会漏）。

Q3 为什么幂等键要放数据库唯一约束？

因为它是唯一在「进程死了也一样有效」的判重手段。map 重启就没了，SETNX 依赖 Redis 可用性且和数据库不在一个事务里。唯一约束和业务数据在同一个事务里提交，要么都成，要么都不成。

图 8 · 幂等：把判重交给数据库唯一约束
本节课重点：幂等的正确层次是数据库，不是应用。订单号、reservation_id、支付回调 trade_no，全部走唯一约束。
动手（顺序不能反）
  1. 先止血：把 CreateOrder 的空实现改成显式 CodeUnimplemented。让失败显式发生。
  2. 再实现：真实落库 + 订单号唯一约束 + 金额字段从 float64 改为整数分。
踩坑预警：注意 CompleteOrder 看起来是完整的，但它调用的 SaveOrder 是空实现——这种「上层完整、底层空转」的假象是最难发现的缺陷形态。读代码时看到「看起来写完了」的方法，一定要点进去看它调用的下一层。

第 8 课

第一次跨服务调用

约 2.5 小时 · 全仓第一个 client
教学目标：让 10 个「互不相通的独立单体」第一次真正对话。这也是你学会服务间通信的唯一一课。
先想通：三题

Q1 服务间为什么要直连，从公网绕一圈有什么问题？

绕公网要多走一次 TLS、一次鉴权、一次网关限流，还把内网调用暴露在外部攻击面上。服务间应走集群内 Service + CoreDNS 直连。

Q2 调 Reserve 超时了但对方其实成功了，订单该算什么状态？

未知，不是失败。所以不能简单置为 CANCELLED——那会一边占着库存一边订单取消。MVP 的处理：保持 PENDING，靠定时任务回查补偿（第 10 课实现）。

Q3 depends_on 和 depends_on_planned 为什么必须分开？

混在一起，AI 和 CI 会以为依赖已接线，然后基于错误假设改代码。「设计上需要」和「代码里已连」是两件事，这个项目用两个字段把它们分开，structcheck 会核对。

踩坑预警：别吞错误——服务间失败必须显式映射成用户可理解的错误，不能一律返「系统错误」。超时必须显式设置：没有超时的调用是可用性事故的第一来源。

第 9 课

支付安全（最重要的一课，值得花两倍时间）

约 5 小时 · 建议分两次做
教学目标：理解「回调不可信」四个字到底意味着什么，并把 payment 从 5 个 Unimplemented 变成真的。
先想通：四题（支付安全的核心）

Q1 支付平台通知「用户已付款 100 元」，你凭什么相信它？

只能靠验签。回调是一个公网可达的 HTTP 端点，任何人都能往它发请求。没有验签，等于把「标记订单已支付」的按钮挂在公网上。

Q2 验签通过了，回调里的 total_amount 就是你数据库里那个金额吗？

不是。验签只证明「消息真的来自支付平台」，不证明「这笔消息对应你这一单」。有人可以拿一笔 1 分钱订单的成功回调来标记一笔 100 元订单已支付——所以必须回查订单 + 校验金额。

Q3 同一条回调被送达三次，账会记几笔？

没有幂等就三笔。网络重试、平台重发、你自己重试，都会造成重复投递。用回调里的 trade_no 做唯一键。

Q4 CreatePayment 用请求体的 customer_id 当付款人，会发生什么？

和第 5 课 address 的 bug 一模一样：任何人都能以他人身份发起支付。同一个错误模式在不同服务重复出现——这正是为什么要记住「身份只信网关注入」这一条根规则。

图 10 · 支付安全的四道闸门（顺序不能换）
本节课重点（请原样抄进笔记）：① 验签防伪造 → ② 回查订单防张冠李戴 → ③ 校验金额防 1 分钱冒充分百元 → ④ 幂等落账防重复入账。顺序不能换，缺一不可。
动手
  1. CreatePayment：付款人取网关注入的 x-md-global-user-id，不用请求体字段；按 proto 兼容规则废弃 customer_id。
  2. 下单：调支付宝 / 微信创建支付意图，返回收银台参数。
  3. 回调：验签 → 回查订单 → 校验金额 → 幂等落账。
  4. 主动查询：用户付完款但回调丢了，要能主动查（alipay.trade.query）。

backend/go.mod 已有 smartwalle/alipay/v3，直接用；微信支付 APIv3 需自己引 SDK 并按平台文档验签。

第 10 课

状态机、超时补偿与上线前的功课

约 4 小时 · 最后一课
教学目标：让链路自己学会处理「用户付了钱但回调丢了」和「用户下单了但不付钱」，并完成上线前的硬门槛。
先想通：三题

Q1 订单状态有哪些？哪些迁移合法？PAID → PENDING 为什么必须非法？

钱都收了，不可能退回「待支付」。非法迁移是状态机要防的核心——它意味着代码里有条路径能把已完成的交易拉回去。每个迁移都要走守卫检查。

Q2 用户下单 30 分钟不支付，库存一直被他占着，会怎样？

库存被无效占用，真实买家买不到。所以必须有定时任务扫超时 PENDING，释放预占并取消订单。

Q3 定时任务跑到一半挂了，下次重跑会发生什么？

如果任务不幂等，会重复释放、重复发通知。定时任务必须幂等：同一订单被扫到两次不出副作用（用状态判断 + 唯一约束）。

图 11 · 订单状态机（绿色 = 合法迁移，红色虚线 = 必须禁止）
动手
  1. 订单状态机：PENDING → PAID → SHIPPED → DONE，分支 CANCELLED。所有迁移走守卫检查。
  2. 定时任务：扫超时 PENDING → Release 释放预占 → CANCELLED。任务本身要幂等。
  3. 手动发货：后台填快递单号（先用 http-client 脚本或 admin app，够用即可）。
  4. 上线前收尾：删掉 user/internal/data/user.go 里的 Debug(token.AccessToken)；首页换真实商品；加亮照 / 隐私 / 退货政策页。
踩坑预警：错误码约定——找不到 → not_found，未实现 → unimplemented，不用 unknown / 零值兜底。返回零值让调用方以为「查到了，就是这个值」。
