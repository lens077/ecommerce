# 12 跨服务契约实验室：把「接口能调通」变成「业务对得上」

[学习入口](README.md) · 前置：[平台](01-platform.md)、[订单](10-order.md)、[库存](09-inventory.md)、[支付](11-payment.md)

本章不是新 proto 草案，不复制整份字段定义。现行字段以源文件为准；尚未实现的接口按既有设计推进，不把表里的目标方法当成已经可调用。

## 1. 编译通过只证明一小部分契约

**契约（Contract）**是调用方与提供方共同遵守的规则。protobuf 能约束一部分类型，但它不能自动回答：

- 这个 UUID 是用户、商家还是地址？
- quantity=0 是删除，还是非法请求？
- price 是元、分，还是仅供展示的近似值？
- 成功是「已经入队」「已经写库」还是「渠道已扣款」？
- 超时后能不能重新发，重复请求会不会做两次？

至少逐项写出下面八种契约：

| 契约 | 当前项目中的例子 | 典型故障 |
|---|---|---|
| 身份与归属 | gateway 主体、访客标记、address 用户归属 | 拿到合法 UUID 就能改别人的数据 |
| 标识 | cartItemId、SKU ID、spu_code、group_no、pay_no | 前端传错 ID，服务静默过滤或匹配错商品 |
| 数值与单位 | 整数分、dwell 秒、事件毫秒、库存件数 | 金额漂移，停留时长放大千倍 |
| 状态 | pending_payment、captured、cancelled | 订单已取消却被晚到支付回调复活 |
| 错误 | not_found、failed_precondition、unavailable | 依赖故障显示成空购物车；业务拒绝被反复重试 |
| 重复与顺序 | 同 token 重放、同事件去重、版本更新 | 重复订单、重复扣库存、旧数量覆盖新数量 |
| 时间与预算 | 总 deadline、每步超时、报价有效期 | 多层各重试三次导致请求风暴 |
| 版本与上线 | proto 生成、控制面 Schema、routes 包 | 新服务字段被旧控制面拒绝，前端发了服务不认识的字段 |

## 2. 当前协议的重点对齐表

| 边界 | 当前事实 | 目标/下一步，不是现有能力 |
|---|---|---|
| 前端 ↔ cart | GetCart 返回条目 ID；Remove 仍是平行数组，Update 是商品组合键；数量为目标值，0 表示删除 | 先接 mutation，再按设计统一条目 ID；请求范围绑定当前用户 |
| cart/product ↔ order | order 输入仍是 CartItemIds/addressId/remark，响应为空；matrix 依赖未接线 | checkout v2 的报价 token、权威价格、地址快照、group_no 与支付期限 |
| order ↔ inventory | 现行 Reserve/ReleaseReserve 与目标跨商家组接口不同 | ReserveGroup/ConfirmReservationGroup/ReleaseGroup：全组原子、稳定 reservation_id、重复结果一致 |
| order ↔ payment | 当前 payment 契约仍有单订单形态，repo 显式 Unimplemented | 按 group_no 发起支付尝试，capture/refund 分轴；渠道结果与订单接受分别保存 |
| product ↔ search | 商品投影经 CDC，不是服务间同步 RPC；search ID 是 uint32、price 是 double | ID 位宽与金额读模型统一，分页与变更/删除传播验收 |
| product ↔ behavior/gorse | ItemId=spu_code，读取推荐只返回 ID/Score | 商品卡片补全与上下架过滤、同一分类语义、幂等投影 |
| gateway ↔ 业务服务 | 可信身份头、四类路由、仍有 legacy 兼容 | C 类必须拒访客；对象归属落 service/biz/SQL；网络层阻止绕过网关 |
| Config Center ↔ 消费者 | selector + Bootstrap Schema + Watch | 更新先验证后换入，未生效可观测；控制面 Schema 先于消费者新字段上线 |

不要为实现表中所有目标一次性修改十个服务。按下面实验顺序形成一个个薄闭环。

## 3. 实验一：购物车写入闭环

**前置**：使用隔离测试用户和数据库；先确认现行 cart proto，不凭 UI 字段推断请求。

1. 加购并重新 GetCart，记录服务端返回的真实条目 ID。
2. 用完整条目构造现行删除/改数量请求，等待服务端成功后失效共享 Query。
3. 刷新页面、第二个标签页重新查询，验证服务端状态一致。
4. 注入 RPC 拒绝和超时，观察 UI 不伪报保存成功；超时写结果未知时重新查询。
5. 用户 B 使用用户 A 的商品组合或条目 ID，断言无越权修改。

**高内聚检查**：请求拼装和缓存更新收在同一个 cart hook，用例规则收在 cart 服务；页面不直接写 SQL，也不新建第二个 transport。

**退出标准**：删除/数量可以从数据库重读验证，错误路径有证据；不是只检查按钮动画。

## 4. 实验二：订单最小可信闭环

**前置**：先阅读 [checkout v2](../design/order/checkout.md)；不要把原型空响应接到正式支付。未完成路径先显式 Unimplemented。

1. 由权威商品数据生成报价；购物车只提供购买意向。
2. 报价 token 与提交参数绑定。用户身份由服务端取，地址必须属于该主体。
3. 用 PostgreSQL 唯一约束认领请求事实；重复请求要能拿到原状态或明确 pending，不再创建另一个订单组。
4. 预占一组库存，写订单与必要的事件/补偿事实。
5. 本地事务提交后才返回真实 group_no、金额与期限；前端进入收银台，不是成功支付页。

**事务边界**是一个服务的数据库提交范围，不是把三个 RPC 套进一个 Go 函数就变成分布式事务。

**失败场景**：库存成功、订单事务失败。必须有可恢复的释放责任；只在 defer 里调用一次释放，进程崩溃时会消失。

## 5. 实验三：最后一件库存

用具名并发测试启动两个请求，同时购买最后一件商品：

- 必须只允许一方得到已持久化预占。
- 余额不能负数，失败方无成功流水。
- UPDATE 影响 0 行不能返回成功。
- 同 reservation 重放不重复扣；同 ID 不同内容要报冲突。
- Release 重复到达不额外增加库存；Release 先到而 Reserve 晚到时按设计墓碑拒绝复活。

**不变量（Invariant）**是每次状态变更后都必须成立的等式或约束。它比「用了乐观锁」更重要；锁只是实现不变量的一种工具。

把业务状态与数据库唯一键/条件更新一起检查。仅用 mock 返回 nil 不能证明真实 SQL 安全。

## 6. 实验四：支付结果未知与晚到回调

付款具有三个结果：成功、明确失败、**未知**。网络超时属于第三类，不能自动当失败后新建另一笔扣款。

学习用例：

| 场景 | 必须保证 |
|---|---|
| 同一 payment_request_id 重试 | 返回/查询同一支付尝试，不生成新的渠道交易 |
| 同 key 换金额或订单组 | 明确冲突，不重放错误结果 |
| 渠道扣款成功、服务没收到响应 | 记录请求事实，能主动查询/对账恢复 |
| 相同回调两次 | 验签后幂等推进一次；签名有效也仍要核对金额、商户、订单映射 |
| 订单取消后才收到 captured | 保存真实资金事实，再走退款责任，不把取消订单复活 |
| 用户打开/伪造前端 result URL | 不能据此改变 payment 或 order 状态 |

这些实验只在渠道沙箱或测试 adapter 中做；不对生产资金执行故障注入。payment 实现仍由你亲自完成。

## 7. 实验五：重放不是再次加一

选 behavior 的 read 事件。模拟「gorse 收到 POST，返回包丢了」，再触发 PendingSync。当前累加语义会暴露重复副作用。

正确性测试应比较最终反馈值，不只比较记录条数。同主键的一行被加了两次，仍然不幂等。

如果采用数据库绝对汇总值 + PUT，还要模拟旧快照晚到：是否能覆盖更新值？按 key 串行或受控版本同步解决顺序，而不是仅把 HTTP 方法换个名字。

## 8. 错误和重试的对照课

| Connect 语义 | 人能理解的意思 | 调用方默认动作 |
|---|---|---|
| unauthenticated | 身份不成立 | 登录/恢复会话，不反复业务重试 |
| permission_denied | 已识别但无权 | 停止，不能换个 ID 试探 |
| invalid_argument | 输入不符合契约 | 修输入；保留表单帮助用户修改 |
| not_found | 目标不存在或按策略对该主体不可见 | 提示/刷新，不泄漏他人资源是否存在 |
| failed_precondition | 当前状态不允许，如库存不足 | 修改业务选择，不盲目自动重试 |
| unavailable / deadline_exceeded | 依赖暂不可用或没及时得到结果 | 读请求可有界重试；写请求先看幂等与结果查询 |
| unimplemented | 功能未落地 | 禁用/提示，不渲染成功结果 |

最终映射以 [错误处理规范](../design/platform/error-handling.md) 为准；业务 reason 用于机器区分，不靠匹配中文错误字符串。

## 9. 兼容与发布不是最后再想

**Expand-contract（先扩展、后收缩）**：先让提供方支持新字段/新方法，再更新生成客户端和调用方，最后按明确边界退役旧形态。proto 的已删除字段号/name 用 reserved，不能回收给另一个含义；字段类型兼容性由 Buf breaking 检查，不凭直觉改 uint32 为 uint64。

本仓变更链：设计 → proto 与约束 → Go/TS 生成物 → server 校验 → biz/data → 前端调用 → 契约测试。跨仓路由还要同步 control-tower routes 发布并升级本仓依赖；配置字段还有 Schema 先行发布链。

**定义完成**不是「两边代码都编译了」，而是旧/新调用方各自的行为明确、错误和失败可验、部署版本能定位。

## 10. 如何逐项推进而不制造新耦合

- 一次只选一个实验、一个可观察结果，先写能失败的断言，再实现最小修复。
- 不为了目标图先装新消息组件；首个真实跨服务副作用出现时再落 Outbox/Inbox。
- 不把缓存升级成锁/幂等真相，正确性保持在数据库。
- 不用高 Repowise 分数替代业务断言；工具提示是否保留，以源码与实验裁决。
