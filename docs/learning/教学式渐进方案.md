# 从零手写一个能上线的商城：教学式渐进方案

> **这份方案和上一份路线图的区别**：上一份告诉你「做什么」，这一份教你「怎么想」。
> 每节课都有固定的五段结构：**先想通 → 读代码 → 动手 → 踩坑 → 验收**。
> 建议每节课一个整块时间，**不要跳课**——后面每一课都依赖前面建立起来的心智模型。
>
> 你的起点假设：写过一点代码，但这个项目的分层/契约/事务/支付安全已经生疏。
> 所以第 1 课到第 3 课几乎不动业务代码，先把「一个请求到底怎么走」重新建立起来。

---

## 怎么用这份方案（先读这一节）

**三条学习法则**

1. **先猜，再验证。** 每节课的「先想通」环节，先合上文档自己答一遍，答不上来再往下看。猜错的部分才是你真正的知识缺口。
2. **每课写 10 行笔记**，放在 `.scratch/learn-notes/Lxx.md`。写不出来 = 这节课没懂，重做，不要进下一课。
3. **卡住 30 分钟就停**，去读同目录下另一个服务的同样代码。这个仓库里 `user` 和 `cart` 已经能跑，它们是免费答案。

**一份「现在不要学」清单**（这比学什么更重要）

你被这个项目吓到，是因为它在同一层堆了太多东西。下面是**现在必须当黑盒**的部分，学会了反而干扰你：

| 黑盒 | 你现在只需要知道的一句话 |
|---|---|
| Casdoor / Session / OpenFGA | 身份是网关注入的，请求体里的身份一律不可信 |
| Kafka / Debezium / Elasticsearch | MVP 用不到，先当它们不存在 |
| K8s / Cilium / ArgoCD / Helm | MVP 用 Docker Compose 跑，别碰集群 |
| OTel / Grafana / vmalert | 出问题看日志就够，别现在搭监控 |
| OrderGroup / Saga / Outbox | 那是 v2 设计，MVP 用同步调用 + 事务 |

**你真正要学透的只有四件事**：分层与依赖方向、ConnectRPC 契约、PostgreSQL 事务与并发、支付安全。这份方案 10 节课，全部围着它们转。

## 第 2 课 · 一个请求的完整旅程（纯阅读课）

**教学目标**：能不看文档画出「一次 SignIn 从网络到数据库再回来」的完整链路。这是后面所有课的地基。

### 先想通

1. 为什么 `service` 层是**唯一**被允许 import `api/*/v1`（proto 生成代码）的层？
2. `biz` 层为什么不允许 import `data`？如果允许了，第一周看不出问题，第三个月会出什么事？
3. 错误码是在哪一层被决定成 `CodeNotFound` / `CodeUnauthenticated` 的？为什么不能更早决定？

### 读代码（按这个顺序读，别乱）

```
cmd/server/main.go            ← fx 装配顺序（谁先起谁后起）
internal/server/server.go     ← Connect handler 注册 + 拦截器链 + CORS/h2c
internal/service/*.go         ← proto ⇄ biz 转换 + 错误码映射（唯一接触 proto 的层）
internal/biz/*.go             ← 领域模型 + Repo 接口 + UseCase（纯结构，不碰框架）
internal/data/*.go            ← Repo 的真实实现（pgx / cache / 三方 SDK）
```

对照 `STACK.md` 第三章的「依赖方向铁律」：

```
server → service → biz ← data
```

箭头意思是「允许 import」。注意 `biz` 和 `data` 之间是**反向**的：`biz` 定义接口，`data` 来实现它。

### 一个关键理解（这节课的真正重点）

`biz` 定义 `Repo` **接口**，`data` 实现它。这样 `biz` 的单元测试可以用假实现跑，不连数据库。这就是为什么 `biz` 不许 import `data`——一旦允许，测试就悄悄变成集成测试，然后慢慢没人再跑单测。

### 踩坑预警

- 你会很想在 `biz` 里直接写 SQL。忍住，那是 `data` 的活。
- 你会很想在 `service` 里写业务规则。忍住，那是 `biz` 的活。`service` 只做「翻译」。

### 验收

- [ ] 画一张图：一个请求经过的文件顺序，以及每一层「不允许做什么」
- [ ] 说出三层错误处理的传递方式：`biz` 定义领域错误 → `data` 用 `%w` 包装保证 `errors.Is` 能穿透 → `service` 做映射
- [ ] 跑一次门禁，看它是否已经是绿的：`scripts/verify-quick.sh`

## 第 3 课 · 契约先行：给商品加「列表」能力

**教学目标**：完整走一次「改 proto → 生成 → 三层实现」的全流程，并理解为什么这个项目把 proto 当边界。

### 先想通

1. 现在 `product.proto` 只有 1 个 RPC（`GetProductDetail`）。一个商城只能看详情不能逛列表，荒谬在哪？
2. 为什么列表接口**必须**用游标分页，不能用 `OFFSET + LIMIT`？翻到第 50 页时会发生什么？
3. 为什么 `buf.validate` 的约束加在 proto 上，而不是在 `biz` 里手写 if？

### 动手

1. 在 `backend/api/product/v1/product.proto` 加 `ListProducts`：请求带 `page_size`、`page_token`（游标）、可选 `category_id`；响应带 `next_page_token`。**每个字段都加 `buf.validate` 约束**。
2. `buf generate`（生成 Go 与 TypeScript 两份）。
3. 按第 2 课的地图，从 `server` 开始往下写：`server` 注册 → `service` 转换 → `biz` 定义 `ListProducts` + Repo 方法 → `data` 写 sqlc 查询。

### 读代码

- `docs/design/product/listing.md` —— 游标分页的设计定稿，先读它再动手。
- `backend/services/product/internal/data/queries/*.sql` —— sqlc 的查询长什么样，命名参数怎么用 `@xxx`。

### 踩坑预警（这节课的坑最值钱）

- **兼容性四条红线**：不删字段（要删就 `reserved` 占号）、不复用字段号、不改类型、不改语义。改 proto 前先想清楚这是不是破坏性变更——CI 的 `buf breaking` 会拦你，但拦的是构建，不是你的设计错误。
- **金额字段禁止 `double`/`float`**。这个项目已经在 `search.proto` 里犯过这个错（`double price`），别再犯。用 `int64`（单位：分）或 decimal 字符串。
- 前端类型是**从 proto 生成的**，不是你手写的。改了 proto 不重新生成，前端会拿到旧字段。

### 验收

- [ ] `cd backend && go build ./... && go vet ./...` 通过
- [ ] 前端 `src/gen` 里能看到新的 `ListProducts` 类型
- [ ] 写一个测试：并发翻页不重复、不漏项
- [ ] 你能解释「为什么 `query_parameter_limit: 1` 会强制你用命名参数结构体」

## 第 4 课 · 数据层：迁移、schema 与那张让你踩坑的 NOT NULL

**教学目标**：理解「一个服务一个 schema」的物理隔离意味着什么，以及为什么迁移里的一行小疏漏能让线上功能 100% 失败。

### 先想通

1. 10 个服务共用一个 PostgreSQL 实例，为什么还要每服务一个 schema？直接共用一个 schema、表名前加前缀不行吗？
2. 为什么迁移文件里**禁止** `SET search_path`？
3. 现在购物车加购会 500，原因是 INSERT 没写 `shop_name`，而这一列是 `NOT NULL` 且无默认值。**为什么 seed 数据能插入、真实加购却不行？**（想通这个，你就懂了「测试数据掩盖真实缺陷」）

### 动手

修购物车那个 bug。二选一，**先定契约再动手**：
- 方案 A：proto 加 `shop_name`，客户端传商品快照（和 `spu_name`/`sku_name` 同风格）
- 方案 B：服务端查 merchant 填

按 `docs/design/cart/api-decisions.md` 的裁决倾向走，改完写一条迁移 + 一条能复现原问题的测试。

### 读代码

- `backend/services/cart/internal/data/migrations/00001_*.sql` —— 看规范的迁移长什么样。
- `backend/sqlc.yaml` —— 三个非显然选项的为什么。

### 踩坑预警

- 每服务一个 schema，**SQL 里的表名必须显式限定**（`cart.cart_items` 而不是 `cart_items`）。不限定的话，goose 的版本表会被 `search_path` 带偏。
- 表和关键列**必须**有 `COMMENT`。这不是洁癖，是半年后你唯一能看懂这一列干嘛用的东西。
- 迁移必须写 `+goose Down`。这个仓库 16 个迁移 16 个都写了，别当第一个破例的。

### 验收

- [ ] 新增加购、重复加购都成功，刷新后与服务端一致
- [ ] 你写的测试在修复前是红的、修复后是绿的
- [ ] 你能说出「seed 数据为什么掩盖了这个 bug」

## 第 5 课 · 安全第一课：身份与归属

**教学目标**：亲手修掉一个真实的越权漏洞，并建立「可信身份」这个后续所有安全决策的根。

### 先想通

1. 网关已经做了 Casbin RBAC，为什么 `address` 服务还要再校验一次归属？RBAC 不是已经挡住没登录的人了吗？
2. 用户 A 拿着用户 B 的地址 ID 调 `DeleteAddress`，RBAC 会放行。谁负责拦住？在哪一层拦？
3. 为什么拦下来要返回 403/404，而不是 500？

### 动手

修 `address/internal/service/address.go`：创建地址不再信任请求体的 `UserId`，改从网关注入的 `x-md-global-user-id` 取；读/改/删/设默认全部在 SQL 或领域层带 owner 条件。

### 读代码

- `STACK.md` 第七章「认证、会话与授权边界」——**第 3、4、5 条是安全设计的地基**，逐条读。
- `backend/services/user/internal/server/` 看身份头是怎么被读进来的。

### 这节课的真正重点（请抄进笔记）

> **RBAC 决定「你能不能调这个 RPC」，归属校验决定「你能动哪一行数据」。**
> 前者是粗粒度门禁，后者是每一行查询都必须带的条件。少了任何一个，另一个都不能救你。

同理：**`buf.validate` 只校验结构，不校验权限**。别因为「我加了 validate」就省掉 owner 校验。

### 验收

- [ ] 用户 A 无法读/改/删用户 B 的地址，且收到的是可预期的错误码（不是 500、不是空 200）
- [ ] 覆盖游客、已登录 A、已登录 B 三种身份的测试
- [ ] 你能解释「为什么不能信任请求体里的任何身份字段」

## 第 6 课 · 并发第一课：库存为什么不能「先查后改」

**教学目标**：这是整个项目最重要的一节课。搞懂它，你就搞懂了为什么数据库约束是正确性的最后一道防线。

### 先想通（这题想不通，后面白学）

1. 库存剩 10 件，两个人同时下单各买 8 件。「先查库存（10 ≥ 8 ✓）→ 再 UPDATE 减 8」这个流程哪里会错？错的结果是什么？
2. 如果不用数据库，用 Redis 分布式锁行不行？锁超时了怎么办？加锁的服务挂了怎么办？
3. 为什么说「约束是正确性的最后一道防线」——前面的应用层校验有什么用？

### 动手

重写 `inventory` 的 `Reserve` 与 `ReleaseReserve`：

```sql
-- 关键就这一行：把「判断」和「扣减」合成一个原子操作
UPDATE inventory.stock
   SET available = available - $1, updated_at = now()
 WHERE sku_id = $2 AND available >= $1
RETURNING available;
```

- 判**更新行数**：0 行 = 库存不足（不要用「先 SELECT 再决定」）。
- 配一张 `stock_ledger` 流水表：每次预占/确认/释放都记一行，可对账。
- `reservation_id` 加唯一键，做幂等：同一个订单重复提交只扣一次。
- 多 SKU 预占要在**同一个事务**里（`data.go` 已经提供了 `ExecTx`，现在没用上）。
- 顺手把 `inventory.proto` 的请求体补全——现在它是**空结构体**，根本无法表达「释放哪个订单的哪些 SKU」。

### 读代码

- `docs/design/inventory/inventory.md` —— 库存分层模型与状态机。
- `inventory/internal/data/inventory.go` —— 看现在错在哪：传未来版本号、忽略更新行数、未组事务。

### 踩坑预警

- **多行扣减的顺序**：为了防止死锁，所有事务按同一顺序（比如 `sku_id` 升序）扣减。现在的代码把防死锁排序整段注释掉了，别学。
- 别在事务里做外部调用（HTTP、支付）。事务要短。

### 验收（这节课的验收最硬）

- [ ] 写一个并发测试：库存 10 件，100 个 goroutine 同时预占 1 件，**恰好成功 10 次，其余明确失败**
- [ ] 同一 `reservation_id` 重复预占只扣一次
- [ ] 你能向别人解释：为什么这个正确性不依赖「锁」而依赖「单条 SQL 的原子性」

## 第 7 课 · 事务、幂等与「假成功为什么最危险」

**教学目标**：修掉 order 的假成功，并建立对幂等的正确直觉。

### 先想通

1. `CreateOrder` 返回 `{}` 和 HTTP 200，但什么都没存。用户看到什么？你事后发现时损失是什么？**为什么这比直接返回 500 危险十倍？**
2. 用户连点两次「提交订单」，会发生什么？如果没有唯一约束，你打算在哪里判重？
3. 为什么幂等键要放**数据库唯一约束**，而不是应用层的 `map` 或 Redis `SETNX`？

### 动手

分两步，**顺序不能反**：

1. **先止血**：把 `CreateOrder` 的空实现改成显式 `CodeUnimplemented`。让失败显式发生。
2. **再实现**：真实落库 + 订单号唯一约束 + 金额字段从 `float64` 改为整数分。

### 读代码

- `backend/services/order/internal/biz/application/order.go` —— 看 `CompleteOrder` 看起来完整，但它调用的 `SaveOrder` 是空实现。这种「上层完整、底层空转」的假象是最难发现的缺陷形态。
- `docs/design/order/checkout.md` —— **只读 MVP 需要的部分**（报价、预占、支付意图），OrderGroup/Saga/Outbox 全部跳过。

### 这节课的真正重点

> **幂等的正确层次是数据库，不是应用。**
> 应用层判重（`map`、Redis）在进程重启、多副本、并发竞争下都会漏。
> 唯一约束是唯一能在「进程死了也一样有效」的判重手段。订单号、`reservation_id`、支付回调 `trade_no`，全部走唯一约束。

### 验收

- [ ] 并发重复提交只生成**一组**订单（写测试证明，不是嘴上说）
- [ ] 下单失败时返回明确的错误码，绝不返回空 200
- [ ] 金额全链路是整数分，`go.mod` 里 `shopspring/decimal` 只在你需要展示换算时用

## 第 9 课 · 支付安全（最重要的一节课，值得花两倍时间）

**教学目标**：理解「回调不可信」这四个字到底意味着什么，并把 payment 从 5 个 `Unimplemented` 变成真的。

### 先想通（这四题是支付安全的核心）

1. 支付平台通知你「用户已付款 100 元」。这个通知可能被伪造、被重放、被篡改金额。**你凭什么相信它？**
2. 即使验签通过，回调里的 `total_amount` 是你数据库里那个金额吗？如果有人拿「1 分钱订单的成功回调」来冒充「100 元订单」呢？
3. 同一条回调被送达三次，你的账会记几笔？
4. `CreatePayment` 用请求体的 `customer_id` 当付款人，会发生什么？（提示：第 5 课你刚修过一模一样的 bug）

### 动手

实现 `payment` 的完整闭环：

1. `CreatePayment`：付款人取网关注入的 `x-md-global-user-id`，**不用请求体字段**；按 proto 兼容规则废弃 `customer_id`。
2. 下单：调支付宝/微信创建支付意图，返回收银台参数。
3. 回调：**验签 → 回查订单 → 校验金额 == 订单金额 → 幂等落账**。四步缺一不可。
4. 主动查询：用户付完款但回调丢了，要能主动查（`alipay.trade.query`）。

代码上 `backend/go.mod` 已经有 `smartwalle/alipay/v3`，直接用；微信支付 APIv3 需要自己引 SDK 并按平台文档验签。

### 读代码

- `docs/design/order/checkout.md` 的支付意图与 capture/refund 部分（**只读 MVP 需要的创建/查询/回调**）。
- `payment/internal/data/payment.go` —— 看它现在怎么「诚实地失败」。

### 这节课的真正重点（请原样抄进笔记）

> **支付安全的四道闸门，顺序不能换：**
> ① **验签**——确认消息真的来自支付平台（防伪造）
> ② **回查订单**——确认这笔回调对应你系统里真实存在的订单（防张冠李戴）
> ③ **校验金额**——确认回调金额 == 你订单金额，单位统一到分（防 1 分钱冒充分百元）
> ④ **幂等落账**——确认同一条回调记一次账（防重复入账）
>
> 少任何一道，前两道都白做。少第 ③ 道，是最经典的支付事故形态。

### 验收

- [ ] 沙箱跑通一次完整支付
- [ ] 伪造签名的回调被拒
- [ ] 篡改金额的回调被拒
- [ ] 同一回调重复投递只入账一次
- [ ] 付款人取自可信身份，冒用他人 ID 被拒（写测试）

## 第 10 课 · 状态机、超时补偿与「上线前的功课」

**教学目标**：让链路自己学会处理「用户付了钱但回调丢了」和「用户下单了但不付钱」。

### 先想通

1. 订单状态有哪些？哪些迁移是合法的？`PAID → PENDING` 为什么必须是非法的？
2. 用户下单后 30 分钟不支付，库存一直被他占着，会怎样？谁来释放？
3. 定时任务释放预占时，任务自己跑了一半挂了，下次重跑会发生什么？

### 动手

1. 订单状态机：`PENDING → PAID → SHIPPED → DONE`，分支 `CANCELLED`。所有迁移走守卫检查。
2. 定时任务：扫超时 `PENDING` → `Release` 释放预占 → `CANCELLED`。**任务本身要幂等**（同一个订单被扫到两次不出错）。
3. 手动发货：后台填快递单号（先用 `backend/services/*/internal/tests/` 里的 http-client 脚本或 admin app，够用即可）。
4. 上线前收尾：删掉 `user/internal/data/user.go` 里的 `Debug(token.AccessToken)`；首页换真实商品；加亮照/隐私/退货政策页。

### 读代码

- `docs/design/platform/error-handling.md` —— 错误码约定：找不到 → `not_found`，未实现 → `unimplemented`，**不用 `unknown`/零值兜底**。

### 验收

- [ ] 下单不支付，超时后库存被自动释放
- [ ] 支付成功，库存确认扣减，且不重复扣
- [ ] 定时任务重复执行同一订单不产生副作用
- [ ] 全链路跑通一次真实小额订单（沙箱）

## 全部 10 课之后：你学会了什么

如果你能独立回答下面五题，你就真的「学会」了，而不是「跟着做过」：

1. 一个请求从 `transport` 到数据库事务，经过哪几层、每层不许做什么？
2. 为什么库存扣减必须是单条 SQL，而不是「先查再更新」？
3. 支付回调的四个字段/动作里，哪三个必须回查校验，为什么？
4. 幂等为什么必须靠数据库唯一约束，而不是应用层判重？
5. 为什么 `biz` 不许 import `data`？这个规定保护的是什么？

**五题都能答 → 你可以自己接手这个项目的任何交易链路改动。**
**答不上第 2、3 题 → 重做第 6、9 课，那两课是安全底线。**
