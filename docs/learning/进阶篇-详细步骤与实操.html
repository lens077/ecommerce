任务 1.1

读懂 identity 包：三种身份的判定

M1 身份 · 约 40 分钟 · 前置：基础篇第 5 课
目标：能不看文档说出「登录用户 / 访客 / 无身份」三种请求在该分别返回什么，并且永远不再写出 userID != "" 这种判断。
前置阅读：backend/pkg/identity/identity.go（全文 119 行，包注释比代码更重要）。
为什么这个任务是 M1 的核心：这个仓库支持匿名购物——网关会给未登录用户也注入一个合法 UUID 到 x-md-global-user-id。它和真实用户 ID 形状完全一样，唯一区别是访客请求额外带 x-md-global-anonymous: true。所以「判空」会把你认为要登录的接口开放给访客。
  1. 打开文件，先只读包注释（前 13 行）。它用 ❌/✅ 直接写出了这个坑： 
    // ❌ 错：userID != ""            —— 访客也满足，等于把访客放进下单/支付链路
// ✅ 对：RequireUser(header)     —— 显式拒绝带匿名标记的请求
  2. 做一张判定表（这是本任务的唯一交付物）。把下面这张表抄到你的笔记里，空白处自己填：
    请求类型带的头UserID()IsAnonymous()RequireUser()RequireAny()
    已登录用户user-id + role真实 UUIDfalse返回 ID，err=nil返回 ID
    访客（匿名购物）user-id + anonymous=true访客 UUIDtrueErrAnonymousNotAllowed返回 ID（平权）
    无身份（anonymous 路径）（网关不注入）""falseErrNoIdentityErrNoIdentity
  3. 想清楚三种错误分别该映射成什么 HTTP 语义：
    提示：看 merchant_service.go 里的 requireAdmin 是怎么 switch 的。
  4. 动手改一处：打开 backend/services/address/internal/service/address.go，把创建地址取身份的方式改成 identity.RequireUser(req.Header())。这就是基础篇第 5 课的修复——现在你用的是仓库提供的正规军，而不是自己解析 header。
  5. 写三条测试（登录 / 访客 / 无身份头各一条），断言返回的错误码分别是 nil / CodeUnauthenticated / CodeUnauthenticated。
怎么知道做对了：三条测试全绿；并且你能在 30 秒内说出「为什么 if userID != "" 在支持匿名购物的系统里是漏洞」。
常见失败： ① 直接 req.Header().Get("x-md-global-user-id") 手写字符串——头名会和网关契约漂移，必须用 identity.HeaderUserID 常量或 identity.UserID()。
② 只判空不判 anonymous，测试里只造了「已登录」一种用例，所以没暴露问题。三种身份都要测。
③ 把访客错误映射成 CodePermissionDenied——语义错了，前端会提示「无权限」而不是「请登录」，用户卡住。
任务 1.2

handler 内角色授权（抄 merchant 的范式）

M1 身份 · 约 40 分钟 · 前置：任务 1.1
目标：理解「网关不是唯一防线」，并能把一个需要角色的 RPC 加上第二道判定。
前置阅读：backend/services/merchant/internal/service/merchant_service.go 第 22–40 行（requireAdmin 函数）。
为什么需要第二道判定：网关 Casbin 按 (procedure, method) 粗粒度放行——它回答「谁能碰这条路」。但策略可能被改宽、请求可能绕过网关（东西向调用、误配置）、攻击者可能换传输层方法。handler 自己再判一次「这个主体能不能做这个动作」，这些逃逸全部失效。这就是 TECH.md §8.5 原则六。
  1. 读范式。 merchant 的写法值得逐字读，尤其是注释里那句「到了这一层，请求是什么 HTTP 方法已经无关」： 
    func requireAdmin(h http.Header) error {
    _, err := identity.RequireRole(h, identity.RoleAdmin)
    switch {
    case err == nil:
        return nil
    case errors.Is(err, identity.ErrRoleNotAllowed):
        return connect.NewError(connect.CodePermissionDenied, err)
    default:
        return connect.NewError(connect.CodeUnauthenticated, err)
    }
}
  2. 注意三个细节（这是抄范式的真正价值）：
  3. 动手：给自己服务里一个「只有主人能操作」的 RPC 加同样的判定。例如 order 的 ShipOrder（发货）——MVP 阶段只有你能发货，所以它应该要求 admin 角色。
  4. 写两条测试：带 admin 角色头通过；带 customer 角色头返回 CodePermissionDenied。
怎么知道做对了：你能回答「如果我把网关的 Casbin 策略删掉一条，我的服务还会拦住未授权请求吗？」——答案是会，因为你加了第二道。
常见失败： ① 在 biz 层做角色判定——角色是传输层概念，属于 handler。biz 应该收「谁」这个参数，不关心他从哪来。
② 以为加了 handler 判定就可以不用网关 RBAC——两层管的事不同，都要有。
③ identity.Roles() 返回的是逗号拼接的多角色字符串（如 "admin,merchant"），别用 == 比较整个字符串。

任务 4.1

按本仓基线给自己服务配指标

M4 可观测 · 约 50 分钟 · 上线前必做
目标：让你的服务具备「上线后最低限度可观测」——不是搭监控系统，而是确认指标在产出、且你看得懂。
前置阅读：docs/observability/OBSERVABILITY.md 第 3 节「本仓指标基线」（第 44–83 行）。这是全仓库最实用的一节，它不只列指标，还写了「这个指标异常了我该做什么」。
先建立判断标准：那份文档第一句就是——「判断一个指标要不要采，只问一句：这个指标异常了，我应该做什么？答不上来的不采。」照这个标准，MVP 你只需要 6 个指标。
  1. 确认运行时指标已开。每个服务的 internal/pkg/otel/otel.go 里已经设了 RuntimeMetrics: true（以 behavior 为例在第 58 行），并且有测试断言它： 
    // backend/services/behavior/internal/pkg/otel/otel_test.go
assert.True(t, options.RuntimeMetrics)
    跑一下这个测试确认：cd backend && go test ./services/behavior/internal/pkg/otel/...
  2. 按 RED 方法论确认服务层指标在产出。你的服务已经有 otelconnect 中间件（10 服务同构），自动产出 RPC QPS / 延迟 / 错误率。你要做的只是确认它开着：看 internal/server/ 里拦截器链是否包含 otelconnect（仅当 observability.enable == true）。
  3. 抄一张「指标 → 行动」表到笔记里（从 OBSERVABILITY.md §3 摘最重要的四行）：
    指标异常时的行动
    RPC QPS突降查上游/网关；突增查刷量/重试风暴
    p99 延迟单独恶化 → 查慢查询/GC/锁；整体抬升 → 查依赖服务，用 trace 下钻
    错误率 by rpc.code突升即告警；先分 4xx（客户端错）还是 5xx（服务端错）
    Goroutine 数持续增长 = 泄漏/阻塞/资源未释放——Go 服务最重要的单一健康指标
    pgx 连接池 wait count出现即预警：很多故障不是数据库挂了，是连接池耗尽
  4. （可选，强烈建议）本地把指标看一遍。两个容器的最小栈：docker compose 起 VictoriaMetrics + Grafana，服务 OTLP 指过去，Grafana 里随便建一个面板看 go_goroutines。亲眼看到一条曲线，比读十页文档管用。
怎么知道做对了：你能在 Grafana（或任何面板）里指出「我的服务现在有多少 goroutine、QPS 多少、错误码分布如何」；并且看到 wait count > 0 时知道要去查慢查询。
常见失败： ① 一上手就搭全家桶（OTel Collector + VM + VL + VT + Grafana + vmalert + Alertmanager）——单人维护七個组件的成本远超收益。先两个容器。
② 指标标签放 user_id / order_id——高基数，一百万个用户就是一百万条 series，存储和查询都会崩。这些进日志，用 trace_id 关联。
③ 采一堆「异常了也不知道做什么」的指标。答不上来行动就不采。
任务 4.2

加一条带 trace_id 的日志 + 一个自定义 counter

M4 可观测 · 约 60 分钟 · 前置：任务 4.1
目标：亲手产出「一条能和其他请求关联的日志」和「一个业务指标」——这是你把可观测性从「知道」变成「会做」的分界任务。
  1. 先理解为什么日志必须带 trace_id。一次下单会打出十几行日志，没有 trace_id 你无法把属于同一请求的行捞出来，也无法从一条 trace 反查到日志。trace_id 是三大支柱之间唯一的关联键。
  2. 加业务 counter。在 order 服务的 biz 或 service 层加一个计数器（用 OTel 标准 API，不要自己造）： 
    import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/attribute"
    "go.opentelemetry.io/otel/metric"
)

var meter = otel.Meter("github.com/lens077/ecommerce/backend/services/order")

var orderCreated = otel.Must(meter.Int64Counter(
    "ecommerce.order.created",
    metric.WithDescription("成功创建的订单数"),
))

// 在 CreateOrder 成功返回前：
orderCreated.Add(ctx, 1, metric.WithAttributes(
    attribute.String("rpc.method", "CreateOrder"),
))
    注意 Add(ctx, ...) 传的是 ctx——OTel 会从 ctx 里取出当前 span，指标自动带上 trace 上下文。这是「指标与追踪关联」的关键，别传 context.Background()。
  3. 加一条结构化日志（用服务现有的 log kit，关键是字段化而不是字符串拼接）： 
    // 好的写法：字段化，可被日志系统检索
l.Infow("order created", "order_no", orderNo, "amount", amountFen, "user_id", userID)

// 坏的写法：拼字符串，查不了
l.Infof("order %s created for %s", orderNo, userID)
  4. 本地验证。make dev 起服务，打一次请求，然后：
怎么知道做对了：随便打一次请求，你能只用日志把这次请求的所有行捞出来，并且能说出「如果我要统计今天的下单量，该用哪个指标、该看哪个标签」。
常见失败： ① Add(context.Background(), ...) —— 丢失 trace 上下文，指标和追踪关联不上。
② 在 biz 层直接 import OTel 包 —— 会破坏分层（biz 不许碰框架）。正确做法：biz 通过接口或 ctx 传递，指标在 service 层或 data 层记。先用 structcheck 门禁验证你没越界。
③ 把金额、订单号这种高基数值做成指标标签——那是日志的活。
任务 4.3

设计一条能送到你手机的告警

M4 可观测 · 约 40 分钟 · 上线前夜做
目标：不搭任何监控系统，只用纸笔（或一个 md 文件）设计出一条完整可用的告警——并且想清楚它触达你的路径。
为什么这个任务最重要：这个仓库 TODO.md 里最实在的一条是「告警送达」——Alertmanager 收到告警但没送到人手里，等于没有告警。告警的价值 = 能被收到 × 有人处理，中间任何一环断了都是零。设计比搭建重要。
  1. 选一条规则。MVP 只需要一条：下单接口 5 分钟错误率 > 5%。为什么是它——因为它直接对应「用户下不了单」，是你唯一不能容忍的故障。
  2. 写全五个要素（缺一个就不是一条可用的告警）：
    要素你的填写
    触发条件下单接口 5 分钟错误率 > 5%（写清是哪个指标、哪个标签、窗口多长）
    持续时间连续满足 5 分钟才发（避免一次抖动就叫醒你）
    严重级别critical（交易链断了）
    通知渠道手机（ntfy / Bark / 企业微信 / 邮件——选一个你真会看的）
    处理动作收到后第一步查什么——这是最常被漏掉的一格
  3. 填「处理动作」这一格。照 OBSERVABILITY.md 的排查路径写： 
    1. 看错误码分布：是 5xx（我的锅）还是 4xx（调用方的锅）？
2. 如果是 5xx，看是哪个 rpc.method，用 trace 下钻最慢/最错的 span
3. 按该 span 的 trace_id 去日志里捞 error.origin（真实抛错行）
4. 常见三选一：数据库连接池耗尽 / 下游 inventory 挂了 / 部署了新版本
  4. 做一次「告警演练」。不需要真故障——手动发一条测试告警到你的手机，确认：手机响了、你点开能看到内容、知道该干什么。这个仓库就是因为没做这一步，才有「告警送不到人」的 TODO。
怎么知道做对了：你手机收到过一条测试告警，且你能在 5 分钟内走完上面四步排查路径。只设计不演练 = 没做。
常见失败： ① 告警条件写「CPU > 80%」——CPU 高不一定是问题，CPU 高但服务正常你为什么要被叫醒？告警要对齐用户可感知的故障。
② 没有持续时间，一次请求抖动就发通知——三天后你就把通知静音了。
③ 只搭了 Alertmanager 没配 receiver，或者 receiver 指向一个没人看的渠道。
④ 收到告警不知道干什么——那这条告警只是焦虑生成器。
任务 5.1

本地模拟 Outbox（两个 schema + 20 行 relay）

M5 一致性 · 约 90 分钟 · 不接真 Kafka
目标：亲手写出「业务写 + outbox 插入在同一个事务里」和「一个会重发的 relay」，从而真正理解为什么需要 Inbox 幂等。
为什么先做本地模拟：接真 Kafka 之前，你必须先理解 Outbox 解决的原子性问题。用两个 schema 加 20 行 Go 就能复现全部核心矛盾，且不需要任何中间件。这个任务做完，你将来看 Kafka 只是把 log.Printf 换成 producer。
前置阅读：docs/design/order/checkout.md 里 Outbox 相关章节（只看设计）。另外看一眼 backend/services/product/internal/data/migrations/00004_outbox.sql —— 这个仓库曾经建过又主动删除了 outbox 表，看看它当初的字段设计。

        if _, err := tx.Exec(ctx,
            `INSERT INTO ordersim.orders (order_no, amount_fen, status)
             VALUES ($1, $2, 'PENDING')`, orderNo, amountFen); err != nil {
            return err
        }

        if _, err := tx.Exec(ctx,
            `INSERT INTO ordersim.outbox (aggregate_type, aggregate_id, event_type, payload)
             VALUES ('order', $1, 'OrderCreated', $2)`, orderNo, payload); err != nil {
            return err
        }
        return nil
    })
}

    var lastID int64

func relay(ctx context.Context, db DBTX) {
    for {
        rows, err := db.Query(ctx,
            `SELECT id, aggregate_type, aggregate_id, event_type, payload
             FROM ordersim.outbox WHERE id > $1 ORDER BY id LIMIT 100`, lastID)
        if err != nil { time.Sleep(time.Second); continue }
        n := 0
        for rows.Next() {
            // 将来这里换成 producer.Send(...)
            log.Printf("event: %s %s", r.EventType, r.Payload)
            lastID = r.ID; n++
        }
        if n == 0 { time.Sleep(time.Second) }
    }
}

给同步链加显式补偿

M5 一致性 · 约 60 分钟 · 前置：基础篇第 10 课
目标：把「下单成功但后续步骤失败」这条路径补完，让系统在部分失败时能自己回到一致状态。
为什么这是 MVP 必需：同步链最大的风险不是「失败」，而是「失败后没人收拾」——库存预占了但订单取消了，那份库存就永远被占着。补偿逻辑不是可选的增强，是同步链能上线的前提。

    订单落库成功，调 inventory 超时可能已预占保持 PENDING，定时任务回查（不能直接取消）
    预占成功，创建支付意图失败库存已预占立即 Release，订单置 CANCELLED
    支付成功，订单状态更新失败钱已收支付回调重试 + 主动查询补偿（绝不让钱收了单没成）
    用户下单后不支付库存被占定时任务扫超时 PENDING → Release → CANCELLED

  4. 写测试验证每条补偿路径（每条一行，共四条）。特别是第一条「超时但实际成功」——它验证的是你没有把订单错杀。

常见失败： ① 用「进程内事件」做补偿通知——就是 order 现在那个 GoEventBus(DropOldest)，高负载静默丢事件、重启即失。补偿必须走数据库状态 + 定时任务，不能走内存。
② 补偿动作本身不幂等——补偿重试时把库存释放了两次。
③ 忘了「超时但实际成功」这种未知态，一律当失败取消 → 库存被占着、订单却取消了，用户钱货两空。

    CREATE TABLE demo.spu (id BIGSERIAL PRIMARY KEY, name TEXT NOT NULL, status TEXT NOT NULL);
CREATE TABLE demo.spu_projection (spu_id BIGINT PRIMARY KEY, name TEXT NOT NULL);

CREATE FUNCTION demo.sync_projection() RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'DELETE') THEN
        DELETE FROM demo.spu_projection WHERE spu_id = OLD.id;
    ELSE
        INSERT INTO demo.spu_projection (spu_id, name) VALUES (NEW.id, NEW.name)
        ON CONFLICT (spu_id) DO UPDATE SET name = EXCLUDED.name;
    END IF;
    RETURN NULL;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync AFTER INSERT OR UPDATE OR DELETE ON demo.spu
    FOR EACH ROW EXECUTE FUNCTION demo.sync_projection();
