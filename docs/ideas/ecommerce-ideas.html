01

Agent-Ready 商品层：把搜索投影直接导出成 AI 能读的商品资产

不做一个 AI 导购，而是让 ChatGPT / Perplexity / 豆包的购物助手能选中你的商品——补全 Schema.org、发 llms.txt、开一个只读 MCP server。

96资产契合
资本 低≤1 月1 人 流量入口SEO / AEO

研究依据

  • 完整的 Schema.org 商品标记让商品被 AI 代理选中推荐的概率约 6.4 倍，标记缺失等于在这个渠道被整体排除。（2026 代理式电商实战手册 / Kilowott）
  • AI 带来的零售流量 2026 Q1 同比 +393%，转化比传统搜索高约 42%；Shopify 平台口径 AI 引流转单量同比近 13 倍。（Adobe / Shopify 遥测，2026）
  • 供给极度稀缺：仅 61% 品牌完成 Schema.org 商品标记，34% 发布 llms.txt，9% 跑 MCP server；83% 品牌不支持任何 agent 支付协议。（Web Tonic 2026 报告）
  • 关键节奏判断：agent 活动 76% 落在商品页与搜索路由，结账只占 2.6%——先解决「被发现」，不必先做 agent 支付。（HUMAN Security，2026-07）

为什么是你（资产契合）

  • products.search_catalog 是策展投影的唯一真相源，PG trigger 维护 + CDC 搬运——一份数据同时喂 SSR、ES、agent feed，不需要新建数据管道。
  • consumer-next 已 SSR，AI 爬虫不执行 JavaScript，SSR 是硬前提，你已具备；product-jsonld.ts 已存在，只差字段正确。
  • TODO 里「商品详情 SKU 字段映射与结构化数据」正是这条的前置——顺手把技术债变成增长项。

最小第一步

修 GetProductDetail 的 SKU 映射 → JSON-LD 补全 Product / Offer / AggregateRating / BreadcrumbList（无可靠可售依据时省略 availability，别造假）→ 由 search_catalog 生成 /llms.txt 与商品静态页 → 挂一个只读 MCP endpoint（仅 SearchCatalog + 库存查询，不含写操作）。

怎么死

协议层仍在混战（ACP / UCP / MCP 五套并存），押注单一厂商 UI 会白做；且 AI 流量绝对值仍小（约 0.14% 访问量），把它当主渠道会失望。正确姿势是「数据结构做对，界面不押注」。

02

价格诚实度披露：用 CDC 价格流做「先涨后降」照妖镜

你的 CDC 管道天然拥有每一次改价记录。把它变成商品页上的价格史与可引用事实，让 AI 助手回答「这个价划算吗」时引用你。

90资产契合
资本 低1–3 月1 人 流量入口信任

研究依据

  • 消费者信任是 agentic commerce 的近期天花板：65% 愿意让 AI 比价，只有 14% 愿意让 AI 无人监督下单——「比价」是有真实需求的高意愿场景。（Visa 2026 全球数字购物指数，n=5241）
  • AI 助手回答「值不值得买」时缺乏价格史数据源，谁提供可引用的价格事实，谁就进入答案。

为什么是你

  • 2026-09-23 已用真实 SKU 可逆改价验证 PG → Debezium → Kafka → ES 全链路——价格变更事件流已经在跑，只需落一张 price_history 表（消费者侧只读，不改业务语义）。
  • 与创意 01 叠加：价格史作为结构化数据一并进 JSON-LD，形成「别家没有的字段」。

最小第一步

在商品服务加一张只读价格史表（由改价事务写入，不动现有 CDC）→ 商品页展示近 180 天价格带与最低价 → 促销价必须带「30 天内最低」标注 → 同步进 JSON-LD。

怎么死

商家会恨它——尤其靠「先涨后降」玩满减的商家。这是平台与商家的利益冲突点，需要产品层拍板：做，就得接受部分商家流失；不做，这只是个技术 demo。

03

库存诚实度：把库存变更流水变成消费者的补货预期

「这件什么时候补货」是电商最常被问、最少被回答的问题。你有库存事件流，可以给出真实答案，而不只是「缺货」。

84资产契合
资本 低≤1 月1 人 交易与决策信任

研究依据

  • 本仓库现状（非市场数据）：inventory.stock 的 Reserve/ReleaseReserve 仍是桩，库存由业务流入；但正因为库存是事件驱动模型，补建流水表几乎零成本，而多数平台的库存是缓存值，补不出历史。
  • 缺货页是电商转化漏斗最大的静默流失点，而「到货通知」是唯一标配补救手段——它有需求但体验粗陋。

为什么是你

  • 库存变更天然可入 outbox（线 B 待触发的第一个真实跨服务副作用，正好拿它当首个事件契约的试点）。
  • 前端已有 SSR 商品页、到货提醒可复用既有 notification 设计的空位。

最小第一步

先修完 Reserve 原子条件更新（P0，本来就要做）→ 同事务写 stock_ledger → 商品页展示「近 30 天补货 N 次 / 平均补货周期 X 天」→ 缺货页给出基于真实节奏的到货预估区间，并标注为预估。

怎么死

冷启动期商品少、库存数据稀疏，统计口径没意义。必须设最低样本门槛（如少于 3 次补货就不展示），否则就是拿噪声当承诺。

04

出口合规护照：为商家生成欧盟 DPP 就绪的商品档案

纺织、家具、轮胎——中国出口主力品类全在欧盟数字产品护照首批名单。淘宝京东不会为中小出口商做这件事，你做就成了供给侧的独家入口。

88资产契合
资本 中1–3 月2–3 人 B 端 / 合规出海窗口期

研究依据

  • 欧盟 DPP 注册系统 2026-07-20 已正式运行；2027-02-18 电池护照率先强制（EV / 轻型交通 / >2kWh 工业电池）；纺织、铝、轮胎 2027 Q3–Q4 出授权法案，2029 强制；家具 2028；玩具 2030。（欧盟委员会官方时间表；中国海关总署国门时报 2026-09）
  • 规则性质是准入而非费用：CBAM 管「价」，DPP 管「格」，无照连上场资格都没有；进口产品唯一注册标识在欧盟海关环节核验，一码不通货难入关。
  • 关键机制：注册系统只存标识与索引，数据由企业自持自管——「数据不必出厂」，平台有做数据托管与生成层的空间。（国门时报，2026-09-17）
  • 先行者可把合规成本转化为品牌信用：透明化催生维修、翻新、再制造与绿色溢价。

为什么是你

  • OpenFGA 关系授权天然实现 DPP 的分层访问（公开层 / 买家层 / 监管层 / 维修者层），这是法规明确要求的按角色取数。
  • merchant 域已有申请/审批骨架（信用代码、法人信息）+ product 域 SKU/规格模型 + 商品投影，护照可作为商品的附加属性集扩展，不必新建服务。
  • i18n 路由（/en/product/{spuCode}）已设计，护照页天然是英文面向海外买家的页面。

最小第一步

选一个品类（纺织最贴中国出口、强制在 2029 但有 18 个月过渡）→ 定义护照字段集（材质成分、产地、再生含量、认证编号、碳足迹等级）→ 商家端录入 + OpenFGA 分级可见 → 生成一个可扫码的只读护照页（SSR，英文）→ 先做「就绪度评分」而非「合规认证」，规避法律风险。

怎么死

合规是雷区：法规明说注册不构成合规证明，语义目录未配齐、时间表屡有延后。绝不能声称「帮你通过认证」，只能做「数据就绪与档案托管」，措辞错一次就是法律风险。另外要真有出口型商家供给，否则空转。

「灯会」策展货架：让品牌名变成一个可编排的产品形态

灯市之所以叫灯市，是因为灯会是有主题、有期限、有人挑过的集市。把 search_catalog 投影升级成可编排的主题货架，运营、商家甚至 KOL 都能开一场「灯会」。

82资产契合
资本 低1–3 月2–3 人 品牌形态策展SEO

研究依据

  • AI 带来的会话超半数直接落到商品页（约 56%，自然搜索仅约 20%）——说明「单一商品页」是入口，但「集合页」仍有品牌与 SEO 价值。（Shopify Q1 2026 遥测）
  • 综合商城的最大弱项是「什么都卖、什么都不像」；策展（curation）是把货架变成立场的最小成本手段，也是对抗纯价格竞争的少数有效路径。

为什么是你

  • 你的投影表名就叫 search_catalog（策展投影）——概念已经写在数据模型里了，只差一层编排能力。
  • consumer-next SSR + i18n 路由 + JSON-LD 已就绪，主题集页天然可索引、可分享、可生成 ItemList 结构化数据。
  • admin 端管类目/规则的权限模型已有，OpenFGA 可直接表达「谁能开灯会、谁能往里放商品」。

最小第一步

定义 curation_set（主题 / 期限 / 选品规则 / 责任人）→ 先只做人工选品，不做自动规则 → SSR 主题页带 ItemList 结构化数据 + 独立 TDK → 到期自动下架，形成「灯会」节奏感（季节、节气、年货）。

怎么死

没有商品就没有策展。首页目前还是 DEMO-* 演示商品——策展是放大真实供给的杠杆，不是替代供给的魔法。必须先跨过「真实商品上架」这条线。

上架代理：商家丢图丢表，AI 出 SKU / 规格 / 标题 / 类目，人点确认

综合商城冷启动的真正瓶颈不是买家，是「谁把货搬上来」。把上架从填表变成审校，供给侧效率提高一个数量级。

85资产契合
资本 中3 月+2–3 人 供给侧效率AI

研究依据

  • 本仓库现状（非市场数据）：product.proto 目前只有 GetProductDetail，「商品列表与管理能力」仍是未完成项——也就是说，商家现在根本上不了货。与其照着老设计手写 CRUD，不如直接做成 AI 优先的上架流。
  • agentic commerce 的共识结论：商家必须集中化、结构化、丰富化商品数据（PIM），这比界面或营销更重要——AI 时代商品数据是基础设施。

为什么是你

  • 契约先行（protobuf + buf.validate）意味着 AI 生成的字段有强校验兜底，幻觉字段会被 validate 拦住——这比自由表单的 AI 应用安全得多。
  • Tauri 桌面壳是长时间操作的商家工作台，适合承载批量导入 + 审校的交互密度。
  • 已有 docs/design/copilot/copilot.md 设计与页内助手实现可复用。

最小第一步

先定 CreateProductDraft / SubmitProduct 的 proto 契约（含 buf.validate 约束）→ 商家上传图/表 → 服务端调模型生成草稿 → 草稿必须人工确认才落库 → 与「商品列表与管理能力」同批交付，避免做两遍 CRUD。

怎么死

AI 生成的规格/类目错了会污染整个搜索索引（你的索引由 PG 投影 CDC 而来，脏数据会一路污染到 ES）。必须有「未确认不进 search_catalog」的硬闸，且类目只能从既有类目树里选，不许模型自创类目。

离线优先的档口工作台：网断了也能改库存、打单

真实商家在档口、仓库、展会——Wi-Fi 差的现场，网页后台一卡就没法干活。Tauri 桌面壳 + 本地队列，恢复后幂等同步。

76资产契合
资本 低1–3 月1 人 供给侧效率桌面端

研究依据

  • 本仓库现状（非市场数据）：商家端设计是「桌面浏览器或 Tauri 桌面壳长时间操作工作台」，高频、任务型使用；PRODUCT.md 明确商家是任务型高频角色。
  • 幂等基建已在 TODO 中规划：Idempotency-Key + 去重表要推广到 CreatePayment/Reserve——离线回放必须幂等，两者是同一件事。

为什么是你

  • Tauri 壳已存在，本地持久化（SQLite/文件）是客户端侧工作，不改动服务端架构。
  • 服务端只需支持 Idempotency-Key（本来就要做），离线队列是纯客户端增量。

最小第一步

选定一个高频离线动作（改库存数量）→ 客户端写本地队列 + 乐观 UI → 服务端先落地 Idempotency-Key 去重表 → 恢复后按序回放，冲突显式提示不静默覆盖。

怎么死

企业采购：把 OpenFGA 变成预算、审批与对公结算

B2B2C 里的那个 B，是高客单、高留存、低退货率的部分。多级审批关系正是 OpenFGA 的本职工作。

资本 中3 月+2–3 人 B 端 / 合规高客单

研究依据

  • B2B 电商 AI 采用率高但系统化低：约 71% B2B 企业已在电商运营中用 AI，但只有约 20% 跨多个工作流系统化部署——流程类能力是明确的空白地带。（Algolia / Escalent 2026，n=300）
  • B2B 的定价、合同、审批流与 B2C 根本不同，通用电商 AI 建议在这里失效——因此竞争也小。

为什么是你

  • OpenFGA 关系授权已部署并 smoke 通过，正是「部门→预算→审批人→订单」这类关系建模的原生场景。

  • 三端账号体系共享，企业子账号不需要新建身份系统。

最小第一步

最小切片：一个企业主体 + 多个子账号 + 单级审批 + 月结额度上限（不做发票、不做合同价）→ 用 OpenFGA 表达「子账号可下单、主管可批准、财务可见全部」→ 验证越权不可达。

怎么死

发票、对公支付、合同价、账期是真正的重头，做完就是另一家公司。最小切片若不能在一个季度内产生真实企业客户，就该停。另外这会挤压 B2C 主线资源，优先级要产品层拍板。

10

不带货的决策助手：只给证据，不推商品

既然只有 14% 的人信 AI 下单、却有 65% 愿意让它比价——那就做一个只负责把证据摆齐、明确标注哪句是推断的助手。

78资产契合
资本 中1–3 月2–3 人 交易与决策信任

研究依据

  • 信任天花板数据：愿让 AI 比价 65% vs 愿让 AI 无人监督下单 14%，差 51 个百分点；仅 17% 用户信任 AI 完成购买。（Visa 2026；2026 代理式电商手册）
  • 但 48% 购物者在最近一次购买调研中用了 AI、76% 消费者想要 AI 购物助手——需求在「调研与比价」环节真实存在。
  • Shopify 数据：自运营购物 agent 的零售商销售增速快 59%（6.2% vs 3.9% YoY）。

为什么是你

  • 你有别人没有的三样事实：价格史（创意 02）、库存节奏（创意 03）、字段完整度（创意 08）——助手的价值取决于事实供给，不是模型。
  • 无真实评价与销量数据（PRODUCT.md 明令不得虚构）——这反而倒逼你走「只给可验证事实」的路线，与定位天然一致。

最小第一步

限定场景（同类目 3–5 个 SKU 的横向对比）→ 只输出：参数差异表、价格史、库存状态、字段缺失提示 → 每条结论标注来源（库内事实 / 商家填写 / 模型推断），推断必须显式打标 → 不出现「推荐你买 XX」。

怎么死
