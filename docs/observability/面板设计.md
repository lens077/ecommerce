## 1. 术语与口径（所有面板与告警共用，改动需过评审）

### 1.1 错误（Error）

connect-go 的 RPC 结果用 `rpc_connect_rpc_error_code` label 表达，**成功请求没有这个
label**（otelconnect v0.9 行为，2026-08-12 实测 VM 确认：成功序列无该 label，错误序列
值为小写 code 名，如 `unknown` / `invalid_argument`）。

> 注意：`OBSERVABILITY.md` §3.1 提到「成功已修为显式 ok」——metrics 实况不是这样，
> 该修复只落在日志侧。面板与告警一律按本节实测口径写。

错误分两类，**只有服务侧错误进错误率与告警**：

| 类别 | code 集合 | 用途 |
|---|---|---|
| **服务侧错误**（server-fault） | `unknown` `internal` `unavailable` `deadline_exceeded` `resource_exhausted` `data_loss` `unimplemented` | 分子进错误率，进 SLO，进告警 |
| **客户端异常**（client-fault） | `invalid_argument` `not_found` `already_exists` `permission_denied` `unauthenticated` `failed_precondition` `out_of_range` `canceled` `aborted` | 单独一图观察流量质量，不进错误率 |

PromQL 正则常量（生成器 `common.py` 里唯一定义，别在面板里手抄）：

```
SERVER_FAULT_CODES = "unknown|internal|unavailable|deadline_exceeded|resource_exhausted|data_loss|unimplemented"
CLIENT_FAULT_CODES = "invalid_argument|not_found|already_exists|permission_denied|unauthenticated|failed_precondition|out_of_range|canceled|aborted"
```

**已知且接受的后果**：payment 的 5 个 RPC 全是 `Unimplemented` 桩，按此口径 payment
错误率恒 100%、面板恒红——这是事实暴露而非误报（「未实现却被调用」正是要看见的）。
告警侧单独排除 payment（见 §6），直到它有真实现。

网关侧（HTTP）：错误 = `http_response_status_code >= 500`。4xx 单列观察，不进错误率。

### 1.2 慢（Latency）

**没有「慢调用次数」这个概念。** ARMS 的慢调用/慢 SQL 计数依赖厂商预设阈值（Java 探针
产物），不可行动（「慢调用=3 次」不知道该干什么）。本仓一律用 **P50/P95/P99 分位数曲线**：
histogram 天然支持、无需拍阈值、退化幅度一眼可见（「P99 从 80ms 涨到 1.2s」可直接行动）。
慢请求的**明细**不在 Grafana——去 Jaeger 按 duration 过滤（§4 每个区块带跳转）。

### 1.3 服务身份

- `service_name` 是 Consul 注册名不是目录名（`user-identity` / `search-product` /
  `behavior-service` …，完整对照见 `.service-matrix.yaml`）；
- **全部查询排除 `config-service`**（与独立仓 config-center 撞名，历史教训见
  `OBSERVABILITY.md` §6.1）。电商服务当前未设 `service_namespace`（实测），所以过滤
  写 `service_name!="config-service"` 而不是按 namespace；
- 指标不带 pod 维度（collector 侧 `k8s_attributes/metrics` 刻意只留 namespace+node，
  基数原因见 collector 配置注释）。「哪个实例在抖」去 trace / 日志。

### 1.4 零填充（zero-fill）

错误类指标只挂在**出过错的序列**上，健康服务整条序列不存在，直接相除得空集——
面板一片空白像坏了。**一律用「分母乘 0」补零**：

```promql
( sum by (service_name) (rate(错误[$i]))
  or sum by (service_name) (rate(总量[$i])) * 0 )
/ sum by (service_name) (rate(总量[$i]))
```

**刻意不用 `or on() vector(0)`**：VM 会把无标签单序列广播到任意分组，Prometheus 不会——
换后端就坏。判据是「该指标是否覆盖分母里的每一个分组」，不是「它有没有序列」。

### 1.5 db_client_* 撞名（PG 与 Redis 共用指标名）

otelpgx 与 redisotel-native 都按 semconv 导出 `db.client.operation.duration` →
VM 里同名 `db_client_operation_duration_seconds_*`，**靠 `db_system_name` 区分**
（`postgresql` / `redis`，前者已实测确认）。任何 `db_client_*` 查询**必须带
`db_system_name` 过滤，禁止裸聚合**——否则 Redis 埋点上线当天，DB 时延图会被
Redis 微秒级样本拉出一条假「优化」。

### 1.6 指标名以 VM 实测为准

OTLP → VM 的名字由 `usePrometheusNaming` 转换（`.`→`_`、按 unit 加后缀、counter 加
`_total`）。**写查询前先查 `/api/v1/label/__name__/values`，不要照 SDK 源码猜**——
旧盘曾因猜名画了从建盘起就是空的图（`pgxpool_total_conns`，实际是 `_connections`）。
本文所有 P0 指标名均为 2026-08-12 实测；P1 指标名按对应版本源码预写，
部署后必须回来核一遍（§7 有核对清单）。

## 2. 三层总览与排障动线

| 盘 | uid | 回答的问题 | 默认时间窗 |
|---|---|---|---|
| ① 业务总览 business-overview | `ecommerce-overview` | 生意有没有事、用户体验掉没掉 | 90d |
| ② 应用 APM apm-service | `ecommerce-apm` | 哪个服务有事、事在哪层 | 3h |
| ③ 基础设施 infrastructure | `ecommerce-infrastructure` | 是不是资源 / 采集管道 / 中间件的锅 | 6h |

三盘标题栏互跳、`keepTime=true`（在 ① 看到尖峰点进 ② 仍停在同一时间窗）。

**排障动线**（`OBSERVABILITY.md` §1 的 Metrics→Trace→Logs 在面板上的落法）：

```
告警响 / ① 红绿灯变色
   → ② 顶部全服务 RED 行锁定服务
   → ② 选 $service 看：错误码分布 / P99 / runtime / DB / Redis 哪层异常
   → 明细跳 Jaeger（每区块带链接）；资源怀疑跳 ③；日志在 ③ 底部或 Grafana Explore
```

布局权重 = 排障顺序：每张盘从上到下按「先看什么」排，第一屏必须能回答该盘的核心问题。

| Row | 面板 | 指标 | 口径要点 | 优先级 |

| R4 $service Go runtime | goroutine 数 / heap used vs GC goal / alloc 速率 / **调度延迟 P99** | `go_goroutine_count` `go_memory_used_bytes` `go_memory_gc_goal_bytes` `go_memory_allocated_bytes_total` `go_schedule_duration_seconds_bucket` | 对标 ARMS「JVM/FullGC」：GC 暂停由调度延迟直方图承载（runtime v0.70 无 pause 指标）；名字待部署实测 | **P1** |

| R7 网关入口（不分 $service） | 入口 QPS by status class / 5xx 比率 / 入口 P95/P99 / 4xx 观察 | `http_server_request_duration_seconds_*` | otelhttp v0.70；网关此前 meter 挂 noop，本次修复 | **P1** |

**上下游映射**（对标 ARMS「上游应用/依赖服务」）：本仓服务间不直调（经网关），所以
「上游」= R7 网关入口，「下游」= R5/R6/R8（DB/Redis/外部 HTTP）。真出现服务间直调时
再加 `rpc_client_*` 区块（otelconnect 客户端拦截器随 connect client 自动生效）。

**Jaeger 跳转**：R2-R8 每个 row 标题带 dashboard link →
`https://<jaeger>/search?service=$service&minDuration=…`（错误行带 `tags={"error":"true"}`）。

## 6. 告警规则（全面型，Grafana unified alerting）

落地形态：规则文件由 Grafana sidecar 捡（`grafana_alert` label 的 ConfigMap，
provisioning 通道已开）；**当前不配 contact point，只在 Grafana UI 看**。
后续接飞书 webhook 时只路由 `severity=critical`，`warning` 留 UI（已记入长期决策）。

规则文件：`grafana/alerts/`（生成器产出，见 README）。每条规则必须能回答
「响了我干什么」（`OBSERVABILITY.md` §5 判据）；全面型 ≠ 无脑多，是每个面板区块
配「这个区块变坏」的那一条。

| # | 规则 | 表达式概要 | for | severity | 响了干什么 |
|---|---|---|---|---|---|
| A1 | 服务侧错误率 > 5% | §1.1 口径，by service，**排除 payment** | 5m | critical | 盘② R3 看码分布 → Jaeger |
| A2 | P99 > 1s | `histogram_quantile(0.99, …)` by service | 10m | critical | 盘② R4/R5 看 runtime/DB |
| A3 | 服务无流量（曾有流量的服务 QPS=0） | `rate(count[10m])==0 and rate(count[1h] offset 1h)>0` | 10m | critical | 查部署/网关路由/Consul |
| A4 | goroutine 持续增长 | `deriv(go_goroutine_count[30m])>0` 且绝对值抬升 | 30m | warning | 泄漏排查，对照最近发版 |
| A5 | pgx 空池等待出现 | `rate(pgxpool_empty_acquire_total[5m])>0` | 5m | warning | 慢查询占坑或池配小 |
| A6 | DB 操作错误率 > 1% | `db_client_operation` 错误/总量，`db_system_name="postgresql"` | 5m | critical | 查 PG 与网络 |
| A7 | Redis 客户端错误出现 | `rate(redis_client_errors_total[5m])>0` | 5m | warning | 查 Dragonfly 连通性 |
| A8 | 网关 5xx 比率 > 1% | `http_server_request_duration_seconds_count{5xx}` / 总量 | 5m | critical | 盘② R1 定位下游服务 |
| A9 | 节点 CPU > 85% / 内存 > 90% | `system_cpu_utilization_ratio` 等 by node | 15m | warning | 盘③ R2，查 top pod |
| A10 | 磁盘 > 85% / inode > 80% | `system_filesystem_*` | 30m | critical | 清理或扩容（存储钉 node3） |
| A11 | 上报节点数 < 3 | `count(count by (k8s_node_name)(system_cpu_utilization_ratio)) < 3` | 10m | critical | collector DaemonSet 查 pod |
| A12 | collector 导出失败 | `rate(otelcol_exporter_send_failed_…[5m])>0` | 10m | critical | 遥测在丢，查 VM/Jaeger/Loki 后端 |
| A13 | Kafka Connect task failed | `kafka_connect_connector_task_metrics_…status="failed"` | 5m | warning | CDC 排障（当前预期会响，见 R4 说明） |
| A14 | Kafka UnderReplicatedPartitions > 0 | `kafka_server_replicamanager_underreplicatedpartitions` | 5m | warning | 单 broker 集群此项应恒 0 |
| A15 | 前端 LCP P75 > 4s | `web_vitals_lcp_milliseconds_bucket` | 30m | warning | 前端性能回归排查 |

> A4-A5、A13 这类「预警型」全部 warning；「用户已经受伤」的才 critical——将来飞书
> 只收后者。阈值是首版拍的，上线后按真实曲线校准（验收含注入故障实测，§7）。

## 8. ARMS 功能裁剪对照表

| ARMS 功能（原摘抄章节） | 去向 | 理由 |
|---|---|---|
| 概览分析（总请求量/错误数/实例数…） | 盘② R1 | 同比环比砍掉（offset 查询贵且丑，stat 趋势迷你图够用） |
| 应用详情（拓扑/请求数/响应时间/HTTP 状态码） | 盘② R2/R7 | 拓扑图不做——10 个服务经网关星型，`.service-matrix.yaml` 已是真相源 |
| 慢调用次数 / 慢 SQL 次数 | **删除概念** | §1.2：分位数替代计数；明细在 Jaeger |
| 线程池监控（ThreadPoolExecutor/Tomcat/Jetty…） | 盘② R4 | 全是 Java 物；Go 对应 = goroutine + 调度延迟 + pgx/redis 池（R5/R6） |
| 连接池监控（Druid/HikariCP/Jedis…） | 盘② R5/R6 | pgxpool_* 与 db_client_connection_* 等价物 |
| Full GC 次数 | 盘② R4 | Go 无 FullGC；GC 压力 = heap vs goal + alloc 速率 + 调度延迟 P99 |
| 主机监控 | 盘③ R2 | 由 collector hostmetrics 承担（无 node-exporter，等价） |
| 容器监控（Pod CPU/MEM/网络） | **P2 留位** | 无 cAdvisor/kube-state-metrics，单独轮 |
| SQL 调用分析（语句列表/调用统计） | 盘② R5 + Jaeger | 聚合归面板，语句明细 = otelpgx span（span 名即 sqlc 查询名） |
| NoSQL 调用分析 | 盘② R6 | redisotel-native，本次埋点 |
| 异常分析（Java 埋点方法抛异常语义） | 盘② R3 | Go 无异常；= 服务侧错误码 + panic（recover 后是 `internal`） |
| 错误分析（HTTP >400 + 错误明细列表） | 盘② R3/R7 + Jaeger | 明细列表 = Jaeger error tag 检索 |
| 上游应用 / 应用依赖服务 | 盘② R7 / R5-R6-R8 | 服务间不直调，上游=网关、下游=DB/Redis/外部 HTTP |
| 调用链查询页签 | **不做面板** | Jaeger UI 检索远好于 Grafana 内嵌；面板只做跳转链接 |
| MQ 监控（RocketMQ 发布/订阅统计） | 盘③ R4（基础设施视角） | 应用无 MQ 客户端；Strimzi broker/Connect 健康归基础设施；应用级统计 P2 |
| 深度分析 / 对比查看 / 事件中心 / 0-1 报警 | **删除** | SaaS 产品交互能力，Grafana 复刻性价比为负；K8s 事件维度归 P2 那轮 |
