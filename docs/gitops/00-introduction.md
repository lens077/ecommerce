# 00 · 开篇：一条镜像的生产之旅

> 本篇是 [GitOps 供应链系列](./)的第一篇。它不教你装任何工具，只回答三个问题：
> 为什么这个电商项目需要七道关卡；这七道关卡拼起来是一张什么样的地图；
> 每一篇会讲到什么、不讲到什么。

姊妹系列：[从 MVP 到可靠电商：架构与源码学习路线](../learning/README.md)讲的是**业务链路**——一次下单由谁负责、何时算成功、失败怎么恢复。本系列讲的是另一条看不见的链路：**一行代码如何变成一个可证明的、在生产里运行的镜像**。两条链路在同一个订单服务身上交汇：`10-order` 章关心它的状态机，本系列关心它的镜像凭什么被允许进集群。

## 1. 一次不设防的发布会漏掉什么

设想最朴素的发布：写代码 → push → CI 里 build → push 镜像 → kubectl apply。这条链上每一环都默认「上游给的东西是对的」。逐环追问，每个默认都是一个事故入口：

| 事故 | 缺的那道关卡 |
|---|---|
| 开发者把测试用的高危密钥连着 `.env` 提交进仓库，历史里永久可挖 | 密钥扫描（Gitleaks） |
| 依赖里躺着一个已知 CVE 的库，或者 Helm values 里 `privileged: true` 谁也没发现 | 依赖与 IaC 扫描（Trivy fs/config） |
| CI 工作流本身用了会被注入的第三方 Action，攻击者借它偷走发布凭据 | 工作流审计（zizmor） |
| 出事后没人说得清「线上这个镜像里到底有哪些包」 | SBOM（Syft） |
| 基础镜像带了漏洞，构建通过就直接推上去了 | 镜像扫描（Trivy image） |
| 镜像仓里的 tag 被人覆盖成恶意内容，名字没变，集群照拉 | 镜像签名（Cosign） |
| 某人为了救火手动 `kubectl set image` 到一个未签名镜像，绕过了整条流水线 | 准入验签（Kyverno） |
| 集群里的清单被人改了，Git 仓库和现实悄悄分叉，几周后才发现 | GitOps 持续校验（ArgoCD） |

最后一行是本系列标题的由来：**前七道关卡都发生在「部署之前」，而 GitOps 的核心主张是让 Git 仓库成为唯一事实源，集群持续向它收敛**——手动改动要么被拉回，要么显式失效。这七关不是七个独立的开源项目凑数，而是同一条流水线上**按位置排列的七个检查点**：丢掉任何一个，前后关卡都无法弥补它的缺口。例如签名（第 06 篇）再可靠，如果准入（第 07 篇）不强制验签，签名就只是装饰；反过来准入验签再严，若上游镜像没扫过漏洞（第 05 篇），它只会忠实地把漏洞放进集群。

## 2. 全景：这条流水线在什么时候检查什么

```
 写代码 ──push──▶ GitHub Pull Request ──merge──▶ tag X.Y.Z 推送 ──▶ 生产集群
                    │                                   │
                    ▼ PR 阶段（改代码就跑，发布不跑）        ▼ 构建发布阶段（tag 才跑）
              ┌─────────────┐                    ┌──────────────────┐
              │ 01 Gitleaks │                    │ 构建多平台镜像      │
              │ 02 Trivy    │                    │ 04 Syft → SBOM   │
              │   fs/config │                    │ 05 Trivy image   │
              │ 03 zizmor   │                    │ 06 Cosign 签名    │
              └─────────────┘                    └──────────────────┘
                                                              │
                                                    镜像 + SBOM + 签名
                                                              ▼
                                        ┌──────────────────────────────────────┐
                                        │ 07 Kyverno 准入验签：没签名不许落地      │
                                        │ 08 ArgoCD：集群向 Git 持续收敛          │
                                        └──────────────────────────────────────┘
```

两个阶段用**不同的触发器**，这是本仓的刻意设计（细节见 [context/team/git-commit.md](../../context/team/git-commit.md)「发布 tag 与 CI 触发」一节）：

- **PR 门禁**轻量：每次 push/MR 都跑 gitleaks、Trivy fs/config、zizmor——它们检查的是文本和配置，快，拦得住。
- **构建发布**昂贵：只有裸 semver tag `X.Y.Z` 推到 GitHub 才触发构建、SBOM、扫描、签名、推镜像。改代码不发布，发布必然带着完整的产物证据。

## 3. 工具总表

> 每一行的「拦什么」都是上一节的某个事故；「产出」是下游篇章消费的东西。01–08 均未写（见 §7）。

| 工具 | 检查对象 | 拦住的事故 | 产出（下游消费什么） | 篇章 |
|---|---|---|---|---|
| Gitleaks | 密钥、Token、私钥等敏感信息泄露 | 凭据永久留在 Git 历史 | 「无密钥」的代码快照 | 01 |
| Trivy fs/config | 文件系统依赖漏洞、IaC 错误配置 | 已知 CVE、特权容器等错误配置 | 干净的构建输入 | 02 |
| zizmor | GitHub Actions 工作流安全问题 | 借 CI 偷凭据、注入命令 | 可信的构建环境 | 03 |
| Syft | 生成镜像 SBOM | 「镜子里有什么」永远说不清 | 包清单 → Trivy image 与事故取证 | 04 |
| Trivy image | 镜像漏洞 | 漏洞镜像直接进仓 | 扫描通过的镜像 digest | 05 |
| Cosign | 签名镜像与证明 | tag 被覆盖、镜像被调包 | 可验证的 sigstore bundle 签名 | 06 |
| Kyverno | 在 Kubernetes 准入阶段验证镜像 | 未验签镜像被 kubectl 手动塞进集群 | 只有验签过的 Pod 能创建 | 07 |
| ArgoCD | 集群与 Git 仓库的持续校验 | 手动改动造成不可见漂移 | 漂移即告警、即回滚的闭环 | 08 |

## 4. 本系列怎么读：统一结构

每一篇都按同一套结构写，顺序就是流水线顺序，**不可跳读着装**：

1. **它拦什么**——先讲事故，再讲工具。不知道在拦什么，配置就是抄。
2. **名词**——只解释本篇新出现的名词，前篇讲过的回链不讲第二遍。
3. **通用做法 vs 电商配置**——本系列的立场（下一节展开）：`kubernetes/components/` 目录的安装器面向任何读者，本系列给出的是**电商项目的最终配置**，两者差异每篇都讲清原因。
4. **验收**——正反向都要证明：关卡在放行该放的东西，也在拦该拦的东西。只测「坏事被拦」会漏掉「好事也被拦」这类假阳性，本仓在签名验签上真付过这笔学费（见 [context/team/image-supply-chain.md](../../context/team/image-supply-chain.md)）。
5. **交接**——上游产出什么、下游消费什么。这是把七篇文章串成一条流水线的机制，而不是靠目录顺序硬排。

**最小阅读闭环：00 → 06 → 07 → 08。** 只想理解「镜像凭什么可信」的话，SBOM（04）和两个扫描（02、05）可以后补；但签名到验签再到 GitOps 收敛这条主线不能断。

## 5. 系列的立场：为什么不用通用配置

同级 kubernetes 仓（`~/lens077/kubernetes/components/`）里已经有 kyverno、harbor、argo 等组件的通用安装器，本系列**不重复它们**，而是站在上面回答「这个电商项目为什么配置得不一样」。已知的差异有真实案例支撑：

- **签名格式**：CI 用 cosign 3.x keyless，默认落 sigstore bundle 格式（OCI referrers）；TCR 个人版没有 Referrers API，退化为 `sha256-<digest>` 回退 tag。Kyverno 按 legacy 格式找签名会对已签名镜像报 `no signatures found`——策略类型必须显式 `SigstoreBundle`。这是通用安装器不会替你做的决定。
- **跨架构**：Mac（arm64）搬运镜像到 amd64 节点，三条命令都要显式 `--platform linux/amd64`，否则集群上 `exec format error`。
- **双真相源**：`helm/` 与 `deploy/`（kustomize）逐字段等价，由 parity 脚本强制——Kyverno 策略、ArgoCD Application 如果写进部署清单，两边都得改。
- **发布即 tag**：不是 push main 就发布。所有「何时构建、何时签」的答案都从 tag 触发器推导。

**篇章配置一律以本系列为准**；components 目录在每篇里以引用形式出现，作为通用安装的背景。

## 6. GitLab 怎么办

当前所有供应链工具的接线都做在 GitHub Actions 上（`.github/workflows/supply-chain-pr.yml`、`service-ci.yml`）。GitLab 侧是**计划项而非已有实现**，本系列不假装它已存在：GitLab CI 的等价接线（PR 门禁对应的 MR pipeline、发布对应的 tag pipeline、runner 上的 cosign/keyless 差异）单独立一篇 TODO 占位，写成后放在终章之后。
