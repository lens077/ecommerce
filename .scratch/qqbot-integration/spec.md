## 摘要

新增一个后端服务 `qqbot`，承接 QQ 机器人开放平台的事件回调与消息下发，
把电商系统的通知与只读查询能力接到 QQ 群聊和单聊。

方案分三段推进：**P0 内部运维通知**（不碰用户数据，用于验证接入本身）、
**P1 账号绑定与被动查询**（`openid` 绑定 Casdoor 身份，只读指令）、
**P2 主动通知与互动召回**（支付、发货提醒与复购提醒）。

分段顺序不是按开发难度排的，是按**外部阻塞项**排的：P0 不依赖 ICP 备案、不依赖账号绑定、
不依赖本仓交易缺陷的修复，因此可以先行验证接入是否走得通；P1、P2 各自压着一组前提，
见「与本仓现状的三处硬碰撞」。

## 目标

1. 让订单状态变化能够主动到达用户，而不是等用户回站里查。
2. 让查订单、查物流这类高频只读操作可以在 QQ 内完成。
3. 让团队的部署结果与告警推送到常驻的即时通信工具。
4. 把 QQ 侧身份（`openid`）与平台身份（Casdoor）建立稳定映射，且不引入新的身份伪造面。

## 非目标

- **不在机器人内做写操作。** 下单、支付、修改地址全部留在 Web 端，机器人只提供跳转入口。
  理由：写操作需要完整的授权判定与幂等保证，而 QQ 侧的消息重投与按钮重复点击会放大这两项风险。
- **不做 QQ 频道（Guild）场景。** 频道的权限模型与审核口径和群聊不同，等群聊跑通后单独评估。
- **不修复本仓已有缺陷。** 本方案是调用方，`TODO.md` 登记的交易缺陷由对应待办承担。
- **不新增免鉴权的网关入口。** 原因见「安全与合规」。

## 前提假设

**本方案依赖的下游调用与事件流大多是待建，不是现成能力。** 排期必须按这个现实来，
不能按「复用已有接线」估算。以下四项全部引自 [`.service-matrix.yaml`](../../.service-matrix.yaml)，
是仓库事实，不是本文推断。

### 一、跨服务调用边当前不存在

`known_gaps` 记录：

> 服务间调用几乎全未接线：10 个服务的 `depends_on` 当前均为空；order/payment 只有 `depends_on_planned`。

`qqbot` 的 `/查订单`、`/物流`、`/搜商品` 需要调用 order、product、search 三个服务。
这些调用边**一条都还不存在**——不是「已有接口待接」，是连服务间调用这件事本身在本仓都尚无先例。

对排期的影响：P1 的工作量包含「在本仓建立第一条跨服务调用」，
其中的服务发现、超时与重试、错误分层、服务工作负载身份都要一并解决。
具体形态见 [wiring.md](./wiring.md)。

同时注意 order 自己的 `depends_on_planned` 是 `[inventory, product, address]`（预占、核价、地址快照），
payment 的是 `[order]`。这些也未接线，意味着订单数据的完整性本身还依赖尚未建立的调用。

### 二、事件流是待建

`known_gaps` 记录：

> 事件链的拓扑边：Product/Order 未导入 outbox producer；无 consumer Inbox 表；无 DLQ topic/stream。
> Kafka 与 Elasticsearch 在 node3 已运行但本仓零客户端（两者 `used_by` 均为空）。

NATS 的 `used_by` 同样为空。矩阵特别注明：导入方是 `backend/tools/{search-indexer,outbox-relay}`，
不在 `services` 段。也就是说 **outbox-relay 这个工具存在，但没有任何业务服务在事务内生产 outbox 记录**——
中继端有了，源头没有。

对排期的影响：P2 依赖的「支付成功」「订单发货」领域事件属于**需新建**，
包含事务内 producer、consumer 侧 Inbox 去重表、DLQ 三部分。
`TODO.md` 全局 P0 第 15、16 项（一致性底座、领域事件落地）正是这项工作，
本方案是它的**下游消费者**，不承担建设，但也不能早于它交付。

### 三、Dragonfly 不得承载领域真相

矩阵在 `externals.redis` 明确写：

> 业务服务只放可丢缓存，不得承载锁、幂等键或领域真相；control-tower gateway 的 BFF session
> 是已接受例外，依赖不可用时 fail-closed。

这条直接决定了 `qqbot` 的存储划分，不是可选建议：

| 数据 | 存储 | 理由 |
|---|---|---|
| `openid` 绑定关系 | PostgreSQL | 领域真相，丢失等于所有用户掉绑 |
| 出站消息 `msg_seq` 分配记录 | PostgreSQL | 幂等键，丢失会导致后续消息全部失败 |
| 入站事件去重记录 | PostgreSQL | 幂等键 |
| 绑定码 | PostgreSQL | 短生命周期但属安全凭据，丢失即用户无法完成绑定 |
| 各类配额计数与窗口记录 | **见「频率账本」** | 四个维度落点不同，判据是两条正交测试，本节不重复 |

领域真相与幂等键一律 PostgreSQL，这一段到此为止。

**配额计数是唯一有 Dragonfly 余地的一类，但四个维度落点不同**，
判据、落点表与「缓存不可用时安全降级」的适用边界统一放在「频率账本」一节。

> **落点表只在「频率账本」出现一次，本节不复制。**
> 这是刻意的：同一个决策写两遍就一定会漂移，而这份文档已经因此出过一次事故——
> 早前「只有最后一项允许放缓存」那句在表格重排后静默反转成了它的反面。
> 需要查某个维度放哪，去「频率账本」查那一张表，不要在这里找。

### 四、身份与授权机制部分未落地

[`docs/design/platform/rbac.md`](../../docs/design/platform/rbac.md) 记录：
「统一的数据级 owner 过滤、商家子账号、服务工作负载身份与 OpenFGA」仍是迁移缺口。

`qqbot` 作为服务工作负载调用下游时的身份取得方式，因此也属待建。
这一项在 P1 准入时必须与 wiring 方案一并确认，**不得假定已有机制可用**。

## 平台事实基线

以下均为平台侧既有约束，不是本方案的选择。工程上只能适配，不能协商。

### 场景与鉴权

- 场景：QQ 群聊、消息列表单聊（C2C）、QQ 频道（含频道私信）。企业与个人开发者均可开通这三个场景。
- 鉴权：AppID + AppSecret。旧的 Token 鉴权已废弃，改用 Access Token，
  获取凭证接口 <https://bots.qq.com/app/getAppAccessToken>，不区分正式与沙箱。
- API 地址：正式 `https://api.sgroup.qq.com/`，沙箱 `https://sandbox.api.sgroup.qq.com`。

### 事件接入方式（二选一）

| 方式 | 要点 | 对部署的影响 |
|---|---|---|
| Webhook | HTTPS 回调地址，需 ed25519 签名校验；回调端口只允许 80/443/8080/8443。平台先发 `op=13` 做回调地址验证：用 AppSecret 派生 seed 生成 ed25519 密钥，对 `event_ts` + `plain_token` 签名后返回 | 需要一个公网可达的入站 HTTPS 端点 |
| WebSocket | 纯出站长连接。先调 `/gateway/bot` 取 wss 地址与建议分片数；`op=10` Hello 下发心跳周期，`op=2` Identify 鉴权（token 格式 `QQBot {AccessToken}`，带 intents 位掩码与 shard），`op=1` 心跳，`op=6` Resume 断线补发 | 不需要入站端点，但需要固定公网出口 IP |

**方案选择：Webhook。** 接线论证见 [wiring.md](./wiring.md) §1.1、§4、§5。

证据链分三段，全部是仓库事实，可逐条核：

**一、WebSocket 的「只需出站」不构成优势。**
初稿的理由是「WebSocket 只要求出站，与现有出网路径一致，前置条件更少」。
前半句是事实，后半句不成立——**「现有出网路径」恰恰是不能承诺固定 IP 的那条**：

- 三个 Kubernetes 节点同在 `192.168.3.0/24`，这是一个带 DHCP 的家用或办公局域网，
  `DHCP 192.168.3.2-20` 由**路由器**动态分配
  〔[`context/team/local-env.md`](../../context/team/local-env.md):121-125〕。
- 集群出网还依赖开发机上的代理：节点 containerd 配了 `http-proxy = 192.168.3.220:7890`，
  而 `.220` 就是那台 Mac。文档原话是「这是个真实单点：笔记本合盖 = 集群失去发布能力」
  〔`local-env.md`:164-170〕。
- 本仓**没有任何真相源**记载这个出口 IP 是什么。

一个把出网代理挂在开发者笔记本上的网络，不适合承诺「固定出口 IP」。

**二、Webhook 的入站有本仓已走通多次的成熟通路。**
`qqbot.apikv.com` → node1 Pangolin（`node1`，固定公网 IP，对外 443）
→ cilium-gateway → HTTPRoute。这条路有逐字的两步操作手册
〔[`context/team/pangolin-tunnel.md`](../../context/team/pangolin-tunnel.md):160-171〕
与三条缺一不可的验收判据〔`pangolin-tunnel.md`:200-217〕。
端口也满足平台的 80/443/8080/8443 限制——Pangolin 对外就是 443。

**三、WebSocket 会引入三个新问题，Webhook 让其中两个消失。**

1. 群聊与单聊事件在多分片下如何分布**尚未核实**（wiring.md 待验证项 V3）。
   官方分片公式只对频道定义，而本方案不做频道。
2. `op=6` Resume 需要持久化 `session_id` 与 `seq`。这两个值丢失会漏事件，
   不是可丢缓存，按存储纪律要进 PostgreSQL——于是接收进程变成有状态的。
3. 由此产生单活协调需求。而 Webhook 无状态、可多副本，
   直接满足集群 suite-wide 打散的硬调度约束。

> **必须记住的一条纠正：选 Webhook 不等于绕过 IP 白名单。**
> 正式环境的白名单同时管「连 WebSocket」和「调 OpenAPI」，而**发消息必然要调 OpenAPI**。
> 所以 Webhook 只把需要解决的问题从两个减到一个，**没有减到零**：
> 入站可以走 Pangolin，出站不行。
> 「固定公网出口 IP」是两种模式**共同的**前置条件，不是 WebSocket 独有的代价。
> 本文任何地方都不应被读成「选了 Webhook 就不用管出口 IP」。

**这个选择不是在所有维度都更优，取舍如实记在这里。**
沙箱不受 IP 白名单约束，但 Webhook 即使在沙箱也需要一个公网可达的入站端点；
而沙箱环境下的 WebSocket 既不需要白名单、也不需要入站端点。
严格说：**「最快验证一次连通」是 WebSocket，「长期正确」是 Webhook。**
选 Webhook 的理由是 Pangolin 那两步本仓已经做过多次、成本已知，
不值得为省这两步先建一套有状态实现、再在上正式环境时推倒重来。
如果你只是想在半小时内确认 AppID 与 intents 配置无误，用 WebSocket 连一次沙箱是合理的**探测手段**，
但不要让它长成第一版实现。

**对本文的影响**：接入模式不改变任何产品形态、阶段划分或验收标准，
只改变两处工程细节——「断线恢复」的验收方式（见 P0 验收标准里「中断 60 秒后恢复」一条）
与回调签名校验的必要性（见「安全与合规 · 回调签名与重放」）。

官方 Go SDK <https://github.com/tencent-connect/botgo> 两种方式都支持。

### intents

订阅哪些事件由位掩码决定。**传了无权限的 intents 会直接断连**，因此 intents 必须随权限申请进度收窄。

| intent | 值 | 覆盖事件 |
|---|---|---|
| `GROUP_AND_C2C_EVENT` | `1<<25` | `C2C_MESSAGE_CREATE`、`FRIEND_ADD`、`FRIEND_DEL`、`C2C_MSG_REJECT`/`RECEIVE`、`GROUP_AT_MESSAGE_CREATE`、`GROUP_ADD_ROBOT`、`GROUP_DEL_ROBOT`、`GROUP_MSG_REJECT`/`RECEIVE` |
| `INTERACTION` | `1<<26` | 按钮点击 `INTERACTION_CREATE` |
| `MESSAGE_AUDIT` | `1<<27` | 主动消息审核结果 |
| `GUILDS` | `1<<0` | 频道基础事件 |
| `GUILD_MEMBERS` | `1<<1` | 频道成员事件 |
| `PUBLIC_GUILD_MESSAGES` | `1<<30` | 频道公域消息 |

后三项是默认可订阅的基础事件；其余特殊 intents 需要申请。
本方案不做频道场景，因此 `GUILDS`、`GUILD_MEMBERS`、`PUBLIC_GUILD_MESSAGES` 不订阅。

### 发送消息

- 单聊：`POST /v2/users/{user_openid}/messages`
- 群聊：`POST /v2/groups/{group_openid}/messages`

| 字段 | 说明 |
|---|---|
| `msg_type` | `0` = 纯文本（`content`）、`2` = Markdown（`markdown`，**需申请模板权限**）、`7` = 富媒体（`media`，`file_info` 来自 `/v2/groups/{group_openid}/files`） |
| `keyboard` | 内嵌按钮键盘 |
| `message_reference` | 引用回复 |
| `input_notify` | 输入中状态，`msg_type=6` |
| `msg_id` | 被动回复凭据，来自事件的 `d.id` |
| `event_id` | 被动回复凭据，来自事件最外层 `id`；支持 `INTERACTION_CREATE`、`C2C_MSG_RECEIVE`、`FRIEND_ADD`、`GROUP_ADD_ROBOT`、`GROUP_MSG_RECEIVE` |
| `msg_seq` | 去重序号。相同 `msg_id` + `msg_seq` 重复发送会失败 |
| `is_wakeup` | `true` 表示互动召回消息，与 `msg_id`/`event_id` 互斥 |

### 频率与时效

被动回复（用户先说话，机器人回）：

| 场景 | 有效期 | 可回次数 |
|---|---|---|
| 单聊 | 60 分钟 | 每条消息 4 次 |
| 群聊 | 5 分钟 | 5 次 |
| 频道 | 5 分钟 | 未记录 |

主动消息（机器人先说话）：

| 认证类型 | 单聊 | 群 |
|---|---|---|
| 企业认证 / 个人认证 | 10 QPS | 60 条/分钟 |
| 未认证 | 5 QPS 且 30 条/分钟 | 30 条/分钟 |

- 单关系维度：20 条/分钟。
- 每日上限：1000 条/用户、1000 条/群。
- 接口自身：100 QPS。

互动召回：用户主动对话后 30 天内分 4 个窗口（当天、1—3 天、3—7 天、7—30 天），每个窗口各可下发 1 条。

**用户可在客户端关闭「允许主动发送」。** 关闭后主动消息一律失败，
并通过 `C2C_MSG_REJECT` / `GROUP_MSG_REJECT` 事件通知。这一项决定了主动通知**不能**作为唯一送达手段。

常见错误码：

| 错误码 | 含义 |
|---|---|
| `40034100` | 主动消息频控 |
| `40034105` | 无权限 |
| `40034127` | 无 markdown 模板权限 |
| `40034128` | 被动回复超时或超次 |
| `40054004` | 无好友关系 |
| `40054005` | 消息被去重 |

### 平台侧限制

- **IP 白名单**：新机器人默认启用，只有白名单内的公网 IP 能连 WebSocket 和调用 OpenAPI。只作用于正式环境，沙箱不受限。
- **消息 URL 白名单**：机器人下发消息里的链接域名必须先报备，且需 ICP 备案。上限 20 条，每年可改 50 次。
- **OAuth 回调地址**：上限 10 条。
- **沙箱**：沙箱群 / 频道成员不得超过 20 人。
- **发布**：需提审上线；基本信息每月限改 5 次；指令面板上限 24 条，快捷菜单上限 12 条。

## 与本仓现状的三处硬碰撞

这三项不是实现细节，它们决定阶段顺序。**先读这一节再读方案**。

### 一、核心交易路径当前不可信

`TODO.md` 全局 P0 视图列出 17 项，其中第 1—10 项直接落在交易路径上，包括：

- 库存 `Reserve` 静默无操作（WHERE 比对未来版本号，永远命中 0 行）
- `CreateOrder` 返回假成功（用户看到「下单成功」但无订单）
- `CompleteOrder` 不落库
- `AddProductToCart` 必然失败（INSERT 缺 `shop_name`）
- 地址服务全线越权（SQL 无 user 归属校验）

影响：`/查订单` 这类只读指令依赖订单数据真实存在。在第 3、4 项修复前，
机器人查出来的结果可能与用户认知不一致，而 QQ 是比网页更强的「确认」渠道——
用户会把机器人的回复当作事实。**这会把一个后端缺陷放大成信任问题。**

因此 P1 的准入条件写成硬性依赖，见「P1 · 账号绑定与被动查询」。

### 二、域名未备案，链接类消息走不通

`.service-matrix.yaml` 在 `minio` 一项明确记录：`apikv.com` 未在阿里云备案，域名直连必被 ICP 拦截。
`gorse`、`minio` 均在该域名下。

平台要求下发消息里的链接域名先报备且需 ICP 备案。两项叠加的结果：

- 商品图片、订单详情页、支付页的链接**目前没有一个可用域名**。
- Markdown 消息里若带链接，报备阶段就会被拒。

P0 阶段的规避方式是内部通知不带外链，只带纯文本与错误摘要。
P2 的带链接通知必须等备案，见 [`issues/04`](./issues/04-正式环境资质与前置裁决.md) 的「备案主体与域名」。

### 三、IP 白名单要求固定公网出口

`.service-matrix.yaml` 记录：Kubernetes 节点是 `192.168.3.101-103`（内网）；
node1 是 `node1`，承载 Pangolin；node2 是 `node2`（阿里云，与 Kubernetes 集群无关）。

集群工作负载访问公网时的实际出口 IP **待确认**——需要实测，不能从拓扑推断。
[wiring.md](./wiring.md) §4.2 的调查结论更悲观：本仓没有任何真相源记载它，
且拓扑强烈提示它**不固定**（家用网段 DHCP，出网还依赖开发机上的代理）。

**这一项不因选 Webhook 而消失。** 采纳 Webhook 解决的是入站（走 Pangolin 的固定公网 IP），
出站仍要调 OpenAPI，仍受白名单约束。在实测出固定出口之前，
正式环境**发不出任何消息**——收得到事件、回不了话。

沙箱不受 IP 白名单限制，因此 P0 可以先在沙箱完成全部功能验证。
但注意：**沙箱免的是白名单，不是入站端点。** 采纳 Webhook 后，
即使在沙箱也需要先把 `qqbot.apikv.com` 那条 Pangolin 通路建起来
（两步操作与三条验收判据见 [`context/team/pangolin-tunnel.md`](../../context/team/pangolin-tunnel.md):160-171, 200-217）。
这是本方案有意接受的成本，取舍理由见「事件接入方式」。

## 分阶段方案

### P0 · 内部运维通知

**目的**：验证接入本身是否成立——鉴权、回调签名、事件收发、消息下发、频率控制。
不碰用户数据，不需要账号绑定，不需要备案，不依赖交易缺陷修复。

**范围**

- 新增 `qqbot` 服务，接通 Webhook 回调：`op=13` 回调地址验证 + 常规事件的 ed25519 签名校验。
- 订阅 `GROUP_AND_C2C_EVENT`。
- 在一个团队 QQ 群内响应两条只读指令：`/健康` 返回各服务健康状态摘要，`/帮助` 返回指令列表。
- 接收外部通知源（部署结果、告警）并推送到该群。

> **第一版不含任何由领域事件驱动的主动推送。**
> wiring-architect 的建议是第一版砍掉主动推送、只做被动回复，理由是事件流整条不存在
> （order 无 outbox producer、NATS `used_by` 为空、无 Inbox、无 DLQ），
> 这样依赖面能小一个数量级。本文采纳，并把界线画得更准一点：
>
> | 类型 | 触发源 | 第一版 |
> |---|---|---|
> | 被动回复 | 用户 `@` 机器人 | **做**（`/帮助`、`/健康`） |
> | 主动消息 · 运维通知 | 部署与告警系统直接调用 | **做**（发往内部群，**不经过事件流**） |
> | 主动消息 · 业务通知 | 订单、支付领域事件 | **不做**，留到 P2（需先建事件流） |
>
> 保留「主动消息 · 运维通知」这一类是有意的〔裁决 2026-09-01〕。
> 理由不是「顺手做了」，而是**踩坑时机**：
>
> 主动消息是平台约束最多的一条通道——认证类型决定配额、用户可单方面关闭、
> 有独立的审核结果事件、频控多维叠加。若 P0 只验证被动回复，
> 这一整组风险会推迟到 P2 才第一次暴露，**而那时它同时压着备案、过审、出口 IP 三个外部阻塞**。
> 那是最差的踩坑时机：问题混在一起，分不清是配额算错了还是白名单没配。
>
> 运维通知由部署与告警系统直接触发，不经过事件流，因此**不受 wiring 那条理由的约束**——
> 它那条理由的真实边界是「依赖事件流的主动推送做不了」，而不是「所有主动推送都做不了」。

**消息形态**：纯文本（`msg_type=0`），不带链接，不用 Markdown。
理由：Markdown 需要单独申请模板权限（错误码 `40034127`），链接需要域名报备，两项都是外部依赖。

**验收标准**

1. 沙箱环境下，机器人在群内被 `@` 后 5 分钟内返回 `/帮助` 结果，且回复携带正确的 `msg_id` 与递增 `msg_seq`。
2. 主动推送一条告警到群，返回成功；连续推送时不出现 `40034100`（频控）。
3. 服务中断 60 秒后恢复，期间的事件不丢失、不重复处理：
   验证平台对未成功回调的重投被正确接收，且重复投递被去重表拦住。
4. 服务重启后，同一事件不会被重复响应（幂等，见「消息幂等」）。
5. AppSecret 不出现在仓库、镜像与日志中；`scripts/verify-quick.sh` 通过。

**退出条件**：上述验收标准全绿，且连续运行 7 天无非预期断连。

### P1 · 账号绑定与被动查询

**准入条件（全部满足才可开工）**

- `TODO.md` 全局 P0 第 3 项（`CreateOrder` 返回假成功）与第 4 项（`CompleteOrder` 不落库）已修复并有测试。
- 存在一个可用于 OAuth 回调的域名（可与备案裁决合并处理）。
- P0 退出条件已满足。

**范围**

- QQ `openid` 与 Casdoor 身份的绑定与解绑。
- 只读指令：`/查订单`、`/物流`、`/搜商品`。
- 未绑定用户触发需要身份的指令时，返回绑定引导。

**P1 同样不含由领域事件驱动的主动推送**，全部功能都是用户先说话、机器人再回。
绑定成功提示也走被动回复（用户下一次交互时告知），不占用主动消息配额。
面向用户的主动通知统一留到 P2，前提是事件流已建成，见「前提假设 · 二」。

#### `openid` 的性质，以及由它决定的三件事

这是整个 P1 的地基。**`openid` 不是 QQ 号**，它的三条性质各自否决了一种看起来更省事的做法：

| 性质 | 后果 |
|---|---|
| **per-bot 维度**：`openid` 由「平台 × 机器人」共同确定 | 换一个机器人，同一个 QQ 用户拿到的是**另一个** `openid`。绑定关系与具体机器人强耦合，不能跨机器人复用 |
| **不可反查 QQ 号**：平台不提供 `openid` → QQ 号的映射 | 无法用 QQ 号去匹配平台已有账号。**不存在任何隐式识别路径** |
| **单聊与群是两个维度**：`user_openid` 用于单聊投递，`group_openid` 用于群投递 | 「在群里认识这个人」不等于「能在单聊里认出他」，两个维度要分别处理 |

由此产生三条硬性设计结论：

**1. 必须有一次显式的绑定动作，无法绕过。**
既然不能反查 QQ 号，就没有「用户一说话就知道他是谁」这条路。
用户必须主动完成一次绑定，把 `openid` 与 Casdoor 身份关联起来。
这不是产品体验上的取舍，是平台标识模型决定的——`/查订单` 在绑定前**没有任何办法**定位到平台用户。

**2. 绑定关系是领域真相，必须进 PostgreSQL。**
`.service-matrix.yaml` 的 `externals.redis` 写明：业务服务只放可丢缓存，
不得承载锁、幂等键或领域真相。绑定关系一旦丢失，全部用户掉绑且**无法重建**——
既没有 QQ 号可以反查，也没有第二份来源可以对照。
存储划分见「前提假设 · 三」。

**3. 换机器人 = 全量重新绑定。**
如果将来因为认证类型、场景或主体变更而启用新的机器人 AppID，
已有绑定关系全部作废。这一点要在选定 AppID 前想清楚，
它把「先拿个未认证机器人跑起来，以后再换企业认证的」这条路的代价显性化了：
代价不是重新配置，是让所有已绑定用户重做一次绑定。

**同一条性质还有一个容易漏掉的后果**（由 [wiring.md](./wiring.md) §9.3 指出）：
**沙箱与正式是两套绑定数据。** 沙箱期间积累的绑定关系不能迁到正式环境，
上线时是空表起步。做灰度或试点规划时要把这一项算进去，不要指望沙箱用户平滑过渡。

**群场景的标识对应关系待确认，但产品侧的应对可以先定。**
群内发言者的用户标识与单聊的 `user_openid` 是否为同一值，本文未核实
（「开放问题」中「群内发言者的用户标识与单聊 `user_openid` 是否为同一值」一条；
wiring.md §9.3 按「不是同一个命名空间」处理，
但它同样标注为未独立验证的 V13——**两份文档都没有验证过这一条**）。

在核实前按**两个独立维度**处理，绑定关系表为两者各留一列，不假设相等。
若最终确认两者确实不通用，会多出一条必须让产品侧知道的后果：
**用户在私聊里绑定过，机器人在群里 `@` 到他时仍然认不出他。**
对应的引导流是「群内提示 → 私聊完成绑定 → 回群继续」。
这条引导流在两种结论下都无害（若两者其实相通，它不会被触发），
因此可以先按需要它来设计，不必等 V13 有结论。

查询时**必须带场景维度一起查**，只按 `openid` 单键查会在跨场景时返回错误的人。

> **硬约束：在向平台确认之前，任何实现都不得依赖「两者不通用」这个前提。**
> 方向是单边的——`scope` 两列照存（存了不亏，两种结论下都正确），
> 但**不得**出现「因为群和单聊 openid 必然不同，所以可以省掉某个校验」这类推论。
> 前者在猜错时只是多存一列，后者在猜错时会漏掉一次归属判定。
>
> **⚠️ 别把交叉引用当成交叉验证。**
> 该结论最初出自本文作者的平台侧调研并标为待确认，经转述后在
> [wiring.md](./wiring.md) §9.3 被当作设计前提使用（该文标为待验证 V13）。
> 两份文档看似互相印证，实际**只有一个来源，且未经核实**。
>
> 尤其注意本节与 wiring.md §9.3 都写得相当具体——表结构、`scope` 维度、绑定流后果都列了。
> **那是「假设成立前提下」的推理严谨，不代表假设本身被验证过。**
> 具体不等于可靠：一条未经核实的前提，推得越细，读起来越像已经确认过。
>
> 双方现已各自标注来源，循环引用已拆除；但在实测之前它仍然只是一个假设。
> 建议验法（wiring.md 提出）：同一账号在私聊与群里各触发一次，比对 `openid` 是否相同。

**绑定流程**

前置条件：用户已在 QQ 单聊内与机器人对话，因此存在有效的被动回复窗口（60 分钟）。

1. 用户发送 `/绑定`。
2. `qqbot` 生成一次性绑定码，与 `user_openid` 一起写入绑定会话表，设置有效期。
3. `qqbot` 以被动回复返回一条带绑定码的提示，引导用户在 Web 端登录后输入该码。
4. 用户在 Web 端完成 Casdoor 登录并提交绑定码。
5. 平台侧校验绑定码有效且未使用，写入绑定关系，作废绑定码。
6. `qqbot` 在下一次交互时告知绑定成功。

**为什么用绑定码而不是 OAuth 跳转**：OAuth 跳转需要回调域名先备案并报备进 URL 白名单，
而绑定码只需要用户已在使用的 Web 端。备案完成后可以增加 OAuth 跳转作为更短的路径，
两者可以并存（OAuth 回调地址上限 10 条，容量充足）。

**第 4 步的提交端点与 Webhook 回调是两条不同的入站路径，不要混在一个端点上。**
绑定码提交来自浏览器、需要过网关鉴权（用户此时已登录 Casdoor）；
Webhook 回调来自腾讯服务端、带不了我们的凭据、靠 ed25519 签名自证。
两者的信任模型相反，合在一处会让其中一条被迫降到另一条的安全级别。
接线形态见 [wiring.md](./wiring.md) §3.2 与 §9.3。

**身份边界**：`qqbot` 自身**不是**用户身份的来源。它持有的是「哪个 `openid` 对应哪个平台用户」，
调用下游时必须走与 Web 端相同的授权判定路径，不得自行拼装可信身份头。原因见「安全与合规」。

**验收标准**

1. 绑定码在有效期内只能使用一次；重复提交返回明确错误。
2. 未绑定用户发送 `/查订单` 时，返回绑定引导，且不泄露任何订单信息。
3. 已绑定用户发送 `/查订单`，返回的订单**属于该用户本人**；用另一账号的 `openid` 无法查到他人订单。
4. 解绑后立即失效，`/查订单` 回到未绑定状态。
5. 被动回复全部在有效期内送达：单聊 60 分钟内、每条消息不超过 4 次；群聊 5 分钟内、不超过 5 次。超限时记录 `40034128` 并降级。

**退出条件**：上述验收标准全绿，且「返回的订单属于该用户本人」一条经过针对性越权测试
（用 A 的 `openid` 尝试读 B 的订单）。

### P2 · 主动通知与互动召回

**准入条件**

- 域名完成 ICP 备案，且已报备进消息 URL 白名单。
- 机器人已过审上线，正式环境公网出口 IP 已加入白名单。
- 认证类型已确定（决定配额，见「频率预算」）。
- P1 退出条件已满足。

**范围**

- 交易通知：支付成功、发货提醒，走单聊主动消息。
- 复购提醒：对 30 天内有过主动对话的用户，按互动召回窗口下发。
- 拒收处理：响应 `C2C_MSG_REJECT` / `GROUP_MSG_REJECT`，标记用户为「不可主动触达」。

**通知不得作为唯一送达手段。** 用户可以在客户端关闭「允许主动发送」，
关闭后主动消息一律失败。因此每一条交易通知都必须在站内消息中有对应记录，
QQ 通知只是加速触达，不承担送达保证。

**事件来源待定。** `.service-matrix.yaml` 记录 Kafka（`node1:30004`）与
NATS（`nats.nats.svc:4222`）的 `used_by` 均为空，本仓当前无任何业务接线；
`known_gaps` 也记录 Product/Order 未导入 outbox producer、无 consumer Inbox 表、无 DLQ。
因此 P2 依赖的领域事件是**需新建**，不是复用现有能力。
具体接线方式见 [wiring.md](./wiring.md)；本文只声明这是一项新建工作，不得按已有能力估算。

**验收标准**

1. 支付成功后，通知在约定时限内送达已绑定且允许主动发送的用户〔具体时限待确认〕。
2. 用户关闭「允许主动发送」后，系统在收到 `C2C_MSG_REJECT` 的下一次通知前停止对其发送，且不产生重试风暴。
3. 每日发送量不超过 1000 条/用户、1000 条/群；接近上限时按「频率预算」降级。
4. 互动召回每个窗口（当天、1—3 天、3—7 天、7—30 天）对同一用户下发不超过 1 条。
5. 同一业务事件重复投递时，不产生重复通知（幂等，见「消息幂等」）。

## 领域模型与数据

`qqbot` 服务独占一个 PostgreSQL schema，遵循本仓既有的「一服务一 schema」约定。
下面是概念模型，字段类型与约束在实现阶段按 `context/team/proto-design.md` 的要求推导。

### 绑定关系

记录 `openid` 与平台用户的映射。`openid` 的性质与由此产生的约束见
「P1 · 账号绑定与被动查询」的「`openid` 的性质，以及由它决定的三件事」，此处只列存储形态。

- QQ 侧标识：`user_openid`（单聊维度）、`group_openid`（群维度）。两列分别存储，不假设相等。
- 机器人标识：AppID。**必须显式存储**——`openid` 是 per-bot 维度的，
  不带 AppID 的绑定表在换机器人时无法区分哪些记录已失效。
- 平台侧标识：Casdoor 用户 ID。
- 绑定时间、解绑时间、当前状态。
- 主动发送许可状态：由 `C2C_MSG_REJECT` / `GROUP_MSG_REJECT` 事件维护。

一个平台用户可能在多个 QQ 场景中出现，因此映射是多对一，不是一对一。

**存储位置：PostgreSQL，不得放在 Dragonfly。** 绑定关系是领域真相，
且丢失后无法重建（不能反查 QQ 号，没有第二份来源）。依据见「前提假设 · 三」。

### 绑定会话

承载 P1 的一次性绑定码：绑定码、`user_openid`、创建时间、有效期、是否已使用。
绑定码必须一次性且有有效期，否则会成为账号劫持入口。

存储位置同样是 PostgreSQL。绑定码生命周期短，看起来适合放缓存，但它是安全凭据——
「一次性」这个性质要靠一次原子的「校验并标记已使用」来保证，
而矩阵禁止业务服务用 Dragonfly 承载锁与幂等键。

### 消息幂等

**这是本方案最容易被低估的一块。** 需要幂等的地方有三处，成因不同：

1. **入站事件重复**：Webhook 模式下，回调未在平台预期内成功返回时会被重投；
   平台也可能因其他原因重复投递。（若改用 WebSocket，`op=6` Resume 同样会补发断线期间的事件。）
   处理方式：按事件唯一标识去重，记录已处理事件。
2. **出站消息重复**：相同 `msg_id` + `msg_seq` 重复发送会失败（`40054005` 消息被去重）。
   处理方式：`msg_seq` 由服务按 `msg_id` 维度单调分配并持久化，不能用内存计数器——
   进程重启后内存计数器会回退，导致后续消息全部失败。
3. **业务事件重复**：P2 的领域事件在至少一次投递语义下会重复。
   处理方式：按业务事件标识去重，与出站消息的去重分开记录。

**实现方式：靠唯一约束，不靠「先查后插」。**
去重与「已发过」这类事实一律用数据库唯一约束表达，让重复写入直接失败并被捕获；
先 SELECT 再 INSERT 在并发下有窗口，等于把幂等退化成一次竞态。
[wiring.md](./wiring.md) §9.4 给了两张表的键形状建议（日配额按
`(scope, openid, quota_date)` UPSERT、召回窗口按 `(app_id, scope, openid, window)` 唯一约束），
与本文的存储划分一致。

三处的去重记录**全部放 PostgreSQL**。矩阵明确禁止业务服务用 Dragonfly 承载幂等键，
而「出站消息重复」那一项尤其经不起丢失：`msg_seq` 一旦回退，
后续消息会被平台判为重复而全部失败（`40054005`），
且这种失败在流量低时不会暴露，只在重启后集中出现。

### 频率账本

平台的配额是多维度叠加的（每秒、每分钟、单关系、每日、互动召回窗口），
本地必须有对应的计数记录才能在发送前判断，而不是发出去再看错误码。
理由：`40034100` 频控错误本身也消耗接口配额（接口自身 100 QPS）。

**不要按「频控计数器」一刀切选存储。判据是两条正交测试，任一不满足就落 PostgreSQL。**

> 判据取自 [wiring.md](./wiring.md) §9.4。此前本文与裁决都用「窗口长度」分类——
> **那只是代理指标**：它能解释结论，但解释不了为什么，也覆盖不了新情况
> （被动回复窗口计数就是被它漏掉的一类）。

1. **有没有外部权威拦住错误？** 平台会不会替你拒绝？
   有 ⇒ 我们的状态只是优化，可以放缓存；
   无 ⇒ **我们的记录就是唯一权威，属领域真相，必须进 PostgreSQL**。
2. **丢失后多久自愈？** 决定「被平台拒绝」这件事的损害有多大。
   秒到分钟 ⇒ 损害有界；小时到天 ⇒ 一次丢失毁掉整个窗口。

| 配额维度 | 窗口 | ① 外部权威 | ② 自愈 | 落点 |
|---|---|---|---|---|
| 单聊 10 QPS、群 60 条/分钟、单关系 20 条/分钟 | 秒～分钟 | 有：平台拒绝并返错误码 | 秒级滚过 | **Dragonfly** |
| **被动回复：单聊 60 分钟/4 次、群 5 分钟/5 次** | **5～60 分钟** | 有：超限返 `40034128` | ⚠️ **最长 60 分钟** | **Dragonfly**，须显式接受错窗 |
| 每日 1000 条/用户或群 | 24 小时 | 有：平台拒绝 | ❌ 不自愈 | **PostgreSQL** |
| 互动召回 4 个窗口各 1 条 | 最长 30 天 | ❌ **平台不拦** | ❌ 不自愈 | **PostgreSQL** |

只有**短窗口配额**（QPS、每分钟、单关系）与**被动回复窗口**两项允许放 Dragonfly。

**被动回复窗口是一个有代价的例外，不是规则的直接应用。** 按「任一条不满足就落 PostgreSQL」的字面，
它的测试②（最长 60 分钟不自愈）已经不满足，本该判去 PostgreSQL。
仍然放 Dragonfly 是一次工程取舍：它有平台拒绝作为外部权威（测试①满足），
且写入频繁——落 PostgreSQL 意味着**给每一条被动回复都加一次写**。
代价是必须显式接受「最长 60 分钟的错窗」，并对 `40034128` 单独计数告警。
把它记成例外而不是规则结论，是为了避免下次有人照着这一行去推别的配额。

**放缓存的短窗口配额与被动回复窗口，计数器不是权威。**
真正拦住超发的是平台自己的拒绝；我们的计数只是「避免把配额浪费在必然被拒的请求上」的优化。
这个定性必须写清楚——**否则下一个人会以为计数器是权威，进而在它之上建别的不变量**。

#### 落 PostgreSQL 的计数必须原子递增，不能读-改-写

Webhook 接收端是**多副本**的（无状态、需满足集群 suite-wide `maxSkew=1` 打散，
见 [wiring.md](./wiring.md) §5）。这让日配额计数多出一个与存储选型无关的失败模式：

两个副本同时推送 → 各自读到同一个旧值 `n` → 各自写回 `n+1` → **实际发了 2 条，账上只加了 1**。
已用量被算少，于是超发。这不是缓存问题，放在 PostgreSQL 里一样会发生——
**决定因素是写法，不是存储**。

必须用一次原子写完成，例如：

```sql
INSERT INTO qqbot.daily_quota (scope, openid, quota_date, n)
VALUES ($1, $2, $3, 1)
ON CONFLICT (scope, openid, quota_date)
DO UPDATE SET n = qqbot.daily_quota.n + 1
RETURNING n
```

**`RETURNING n` 不是可选的。** 它拿回的是自增之后的真值，判超限必须用它。
如果改成「先 `SELECT` 查余额判超限，再 `UPDATE` 加一」，两个副本会各读到同一旧值、
各自放行——**竞态又回来了**。自增与取值必须是同一条语句。

放 Dragonfly 的那两类同理：用 `INCR` 的**返回值**判超限，不要 `GET` 之后再 `SET`。

> 与「消息幂等」那节的「靠唯一约束」是**两个不同的问题**，不要混：
> 那里防的是**重复写入**（唯一约束让第二次直接失败），
> 这里防的是**并发递增丢更新**（唯一约束拦不住，因为两次写的是同一行的不同版本）。
> 两条都要做。

#### 为什么「安全降级」救不了日配额与互动召回

本文早前的论证是「把安全降级写成设计要求，读不到计数时按保守配额发送，
于是丢失只会少发」。**这条论证有一个前提没写出来：你得能检测到丢失。**
按 [`context/team/go-redis.md`](../../context/team/go-redis.md):49-57，
`redis.Nil` **是正常结果不是故障**，于是两个后果完全不同的事件在代码里长得一样：

| 事件 | 客户端看到 | 能否保守降级 | 实际方向 |
|---|---|---|---|
| Dragonfly 不可用 | 返回 error | 能 | 少发 ✓ |
| 键被淘汰或过期 | 返回 `redis.Nil` | **不能** | **多发** ✗ |

`redis.Nil` 与「窗口刚开始、一条还没发」读出来都是 0。
**你无法对一个自己检测不到的事件做保守降级**——这是本文原论证的漏洞。

而淘汰不是理论风险。`go-redis.md`:13 要求按故障域分实例
（Session `noeviction`、业务 Cache `allkeys-lru`、**限流实例独立**），
但同一段紧接着写明「**当前仍有单实例存量，迁移完成前不得把它描述为已隔离**」。
也就是说今天放上去就落在 `allkeys-lru` 的共享实例上，内存压力下会被静默淘汰。

**日配额必须进 PostgreSQL 的真正理由，是失败会外溢。**
本文「平台事实基线」已记：`40034100` 频控错误**本身也消耗接口配额**（接口自身 100 QPS）。
把这条和淘汰放在一起看：

- 分钟级窗口被淘汰 → 多发一个窗口的量 → 几十秒自愈，损害**限于该用户**；
- 日配额被淘汰 → 该用户当天按「全新 1000 条」重算 → 连续触发大量 `40034100`
  → 挤占 100 QPS 的接口预算 → **影响其他用户的正常发送**。

后者不是「这个用户多收几条」，是**一个用户的计数丢失拖累全体**。
这才是它不能放缓存的原因，比「24 小时不自愈」更根本。

#### 保守降级仍然是要求，但它管的是「不可用」

上面否定的是「保守降级足以让所有计数放缓存」，不是保守降级本身。
对放 Dragonfly 的短窗口配额与被动回复窗口，
**Dragonfly 返回 error 时必须按保守配额发送，不得按无限制处理**。

这一条不只是本文的建议，本仓已经写成规则：`go-redis.md`:86 明写
「Session、**限流计数**和锁不是普通缓存，Redis 故障时不能假装未命中后绕过安全或一致性约束」。

**两个分支必须分开写，而且两边都容易写反：**

| 读缓存的结果 | 怎么处理 | 写反的后果 |
|---|---|---|
| 返回 `error`（不可用） | **fail-closed，按保守配额发送** | 当成未命中放行 = 把「不可用」伪装成 `redis.Nil`，把唯一可检测的那半也丢掉 |
| 返回 `redis.Nil`（未命中或被淘汰） | **按「窗口全新」处理，接受可能多发**，并依赖平台拒绝 + 错误码告警 | 当成故障 fail-closed = **每个新窗口的第一条消息都发不出去**，功能直接瘫痪 |

第二行的写反方式尤其隐蔽：它看起来像是在「修复」淘汰问题，实际上把正常路径也堵死了——
`redis.Nil` 与「这个窗口刚开始」本来就不可区分，把它当故障等于把所有新窗口当故障。
**淘汰造成的多发只能靠错误码告警去发现，不能靠收紧读取路径去避免。**

**互动召回记录不是「接近幂等键」，它就是矩阵禁止放缓存的那一类。**
本文此前写的是「接近幂等键」，[wiring.md](./wiring.md) §9.4 纠正了这个措辞，纠正得对：

判据就是上面的测试①——**平台不会替你拦**。被动回复超限有 `40034128`、
主动消息超限有 `40034100`，平台都会拒绝；而互动召回窗口内重复下发**是合法请求**，
平台照发、用户照收。一旦没有外部权威，我们的记录**就是**领域真相，
而矩阵对领域真相的规定是硬的（`.service-matrix.yaml` 的 `externals.redis`）。

**注意理由的归属**：窗口长 30 天只是让后果更难看，**不是它必须落 PostgreSQL 的原因**。
即使召回窗口只有 5 分钟，只要平台不拦，它仍然必须落 PostgreSQL。
把原因错记成「窗口太长」，下次遇到一个短窗口但无人拦的配额就会判错。

还有一个把它当计数器才会犯的错误：对 30 天窗口套用「读不到就保守降级」
等于**永远不发召回**——那是功能失效，不是安全降级。

> 〔裁决 2026-09-01〕本节此前与 [wiring.md](./wiring.md) 待验证项 V12 存在分歧：
> 本文原主张「安全降级写成设计要求即可全放 Dragonfly」，wiring.md 主张「不能只放 Redis」。
> 结论是两边各对一半——**安全降级的论证只对短窗口成立**，不能一刀切覆盖全部维度。
> 按上面的两条正交测试重新划分后，两份文档口径一致。

## 指令与消息设计

### 指令集

指令面板上限 24 条，本方案分阶段共用 6 条，留足余量：

| 指令 | 阶段 | 需要绑定 | 说明 |
|---|---|---|---|
| `/帮助` | P0 | 否 | 返回可用指令列表 |
| `/健康` | P0 | 否 | 内部群限定，返回服务健康摘要 |
| `/绑定` | P1 | 否 | 返回一次性绑定码 |
| `/解绑` | P1 | 是 | 解除当前 `openid` 的绑定 |
| `/查订单` | P1 | 是 | 返回最近订单摘要 |
| `/物流` | P1 | 是 | 返回指定订单的物流状态 |

`/搜商品` 列为候选：它是唯一不需要绑定的业务指令，但返回结果天然需要商品链接与图片，
两者都压在域名备案上。备案完成前实现它只能返回纯文本商品名，价值有限。

### 消息形态的阶段约束

| 阶段 | `msg_type` | 按钮 | 原因 |
|---|---|---|---|
| P0 | `0` 纯文本 | 无 | Markdown 需申请模板权限，链接需域名报备 |
| P1 | `0` 纯文本 | 视权限而定 | 按钮需要 `INTERACTION` intent 与 `INTERACTION_CREATE` 处理 |
| P2 | `2` Markdown | 有 | 前提是模板权限已批准、域名已报备 |

在 Markdown 模板权限批准前，任何使用 `msg_type=2` 的代码路径都会收到 `40034127`。
因此消息渲染层要把「形态」做成可配置，而不是散落在各处的字符串拼接。

### 按钮

按钮点击产生 `INTERACTION_CREATE` 事件，需要 `INTERACTION` intent（`1<<26`）。
按钮回调可用 `event_id`（事件最外层 `id`）做被动回复。

按钮不得触发写操作，理由见「非目标」。可用于翻页、切换订单、跳转 Web 端。

## 频率预算与降级

把平台配额翻译成服务必须遵守的工程约束：

**发送前判定，不要依赖错误码事后补救。** 每条主动消息在发送前依次检查：
单关系维度 20 条/分钟 → 每日 1000 条/用户或 1000 条/群 → 认证类型对应的 QPS 或每分钟上限 → 互动召回窗口。
任一项不通过则不发送。

> **这一条与「平台拒绝是最后一道防线」不矛盾，两者是主路径与安全网的关系**
> （与 [wiring.md](./wiring.md) §9.4 口径一致）：
> **预检是唯一被允许的设计意图**；平台错误码的作用是**淘汰探测器与告警信号**，不是限流手段。
> 换句话说，你不能把 `40034100` 当成限流器用——它本身消耗接口配额；
> 但你**必须**对它计数告警，因为它是「本地计数被淘汰了」这件事为数不多的可观测信号之一。

**降级顺序**（从轻到重）：

1. 延迟发送：把消息推入队列，等待窗口恢复。适用于非时效性通知（复购提醒）。
2. 合并发送：同一用户短时间内的多条通知合并为一条。适用于批量状态变化。
3. 丢弃并记录：仅适用于可重建的通知（复购提醒）。交易通知不得丢弃——站内消息已有记录，
   但必须记录 QQ 侧未送达，供人工排查。

**被动回复的时效必须在代码里显式表达。** 单聊 60 分钟、群聊 5 分钟，
超时后 `msg_id` 失效并返回 `40034128`。任何异步处理（例如调用下游服务查询订单）
都必须在窗口内完成，否则要在窗口耗尽前先回一条「处理中」占用一次回复次数，
或改为主动消息（需要主动发送许可）。这是**设计约束**，不是异常处理。

## 安全与合规

### 凭据

AppID、AppSecret 与 Access Token **不得进入仓库**（AGENTS.md 硬规则 4）。

- 存放位置：Config Center（由同级仓 control-tower 的 config 服务承载）。
- 键位遵循本仓约定 `{service}/{env}/bootstrap.yaml`（`.service-matrix.yaml` 的 `conventions.config_center_key`）。
- 仓库内只写主机名与端口，凭据字段留空。
- Consul 只做注册发现，不存配置。

**Access Token 有生命周期，不是静态凭据。** 服务需要在过期前刷新，
并保证刷新期间已在途的请求不因换发失败。这一项在 P0 就要做对，否则会在长时间运行后才暴露。

### 回调签名与重放

Webhook 是当前推荐的接入模式（见「事件接入方式」），因此签名校验是**必须项**而非可选项：

- 平台先发 `op=13` 做回调地址验证，用 AppSecret 派生 seed 生成 ed25519 密钥，对 `event_ts` + `plain_token` 签名后返回。
- 常规事件同样需要 ed25519 签名校验，**校验失败直接拒绝**。
- 回调端口只允许 80/443/8080/8443。

**签名校验必须在 `qqbot` 进程内完成，网关帮不上忙。** 回调的可信性来自 ed25519 签名，
不来自我们自己的鉴权体系——它带不了我们的 JWT。
这与支付宝回调的处理完全同构：`payment` 的 `HandlePaymentNotify` / `HandlePaymentCallback`
在匿名清单里，可信性靠报文签名验证而非网关认证。接线形态见 [wiring.md](./wiring.md) §3。

AppSecret 同时是签名密钥的派生种子，泄漏等于任何人都能伪造平台回调。
即使将来改用 WebSocket（无入站端点，这一组风险不存在），也按同等强度保管。

### 身份边界

本仓已有一处同类缺陷可以直接借鉴教训。`TODO.md` 与
[`docs/todo/统一可观测性体系.md`](../../docs/todo/统一可观测性体系.md) 记录：
网关 jwt 中间件命中免鉴权白名单时直接 return，**不剥离入站头**，而 `behavior/identity()`
又把 `x-md-global-user-id` 当可信源，攻击者带该头即可冒名上报。

`qqbot` 必须避免复制这个模式：

1. **不新增免鉴权的网关入口。** 机器人不是浏览器客户端，它的调用应作为服务工作负载处理。
2. **不自行拼装可信身份头。** 按 [`docs/design/platform/rbac.md`](../../docs/design/platform/rbac.md)，
   control-tower 是 session owner 和入口授权点，负责剥离入站 `x-md-global-*` 并注入可信身份头；
   业务服务只消费这些头。`qqbot` 若绕过网关直接注入身份头，等于把整套授权判定架空。
3. **绑定关系不等于授权。** `openid` 映射到某个用户 ID，只说明「是谁」，不说明「能做什么」。
   数据归属校验仍由下游服务的 Repository 承担——rbac.md 明确指出，网关的 `permission denied`
   不能掩盖 service/repository 缺少 owner 条件，后者会造成 IDOR。

具体接线方式（服务工作负载身份如何取得、是否经网关）见 [wiring.md](./wiring.md)。
rbac.md 已记录「服务工作负载身份与 OpenFGA」属于未落地的迁移缺口，
因此这一项在 P1 准入时需要与 wiring 方案一并确认，不能假定已有机制可用。

### 用户数据

- `openid` 是每个机器人独立的标识，不能反查 QQ 号，本身不属于强 PII，但**绑定关系是**——
  它把 QQ 身份与平台账号关联起来。绑定表需要与其他用户数据同等对待。
- 日志中不得输出完整 `openid` 与绑定关系。本仓的日志脱敏当前存在缺陷
  （`TODO.md` 全局 P0 第 13 项：PII 脱敏形同虚设，Lua 不支持 `{n}` 量词），
  因此 `qqbot` **不能依赖管道侧脱敏**，必须在写日志前自行处理。
- 解绑后应清除绑定关系，保留必要的审计记录。

### 内容合规

- 主动消息有审核结果事件（`MESSAGE_AUDIT`，`1<<27`）。若订阅该 intent，需要处理审核不通过的情况。
- 下发消息里的链接域名必须在 URL 白名单内（上限 20 条，每年可改 50 次）。
  白名单是稀缺资源，配置在 Config Center 中集中管理，不要在代码里硬编码域名。

## 可观测与告警

按本仓既有约定接 OpenTelemetry。`qqbot` 需要额外关注的指标：

| 指标 | 用途 |
|---|---|
| 事件接收通道健康度 | Webhook：回调成功率与签名校验失败数；WebSocket：连接状态与重连次数 |
| Access Token 刷新成功率与剩余有效期 | 刷新失败会在过期时刻集中爆发 |
| 各维度频率配额余量 | 接近上限时提前降级，而不是等 `40034100` |
| 按错误码分类的失败计数 | `40034100`/`40034128`/`40034127`/`40054004` 各自对应不同的处理动作 |
| `40034100` 与 `40034128` **单独计数并告警** | 这两个码是「本地计数被静默淘汰」为数不多的可观测信号；预检正常时它们应当接近零，突然抬升即说明缓存侧出了问题 |
| 被动回复窗口内的处理耗时 | 超过窗口即失败，需要在超时前发现 |
| 主动发送许可被关闭的用户数 | 反映通知策略是否过度打扰 |

告警至少覆盖两项：事件接收通道中断、Access Token 刷新失败。
这两项发生时机器人完全不可用，且不会自愈。

**再加一项，理由是本仓已经踩过**：IP 白名单未配置时，平台返回的错误只出现在日志里，
界面无感知。企业微信告警接入踩过同一个坑
（[`docs/todo/统一可观测性体系.md`](../../docs/todo/统一可观测性体系.md)）。
把「白名单未配置」列进排查清单第一条，并对这类错误码单独计数告警。

## 微服务接线

服务如何注册、如何调用下游、部署形态如何，见 [wiring.md](./wiring.md)。

本文对接线提出的**要求**（不是方案）：

1. 出网 IP 必须固定且可加入平台 IP 白名单。**这是两种接入模式共同的前置条件**，
   不因选 Webhook 而消失——发消息必然要调 OpenAPI，而 OpenAPI 受白名单约束。
2. Webhook 接收端无状态、可多副本，需满足集群 suite-wide 打散的硬调度约束。
   （若将来改回 WebSocket，还需解决分片语义与单活协调，见 wiring.md §5。）
3. 凭据只能来自 Config Center，不得经环境变量明文注入镜像。
4. 不新增免鉴权的网关入口。
5. 调用下游时的身份与授权路径必须与 Web 端一致。

## 新增服务需要通过的仓库门禁

`qqbot` 是本仓的第 11 个后端服务，落地时会触发既有的一致性检查。

**权威清单在 [wiring.md](./wiring.md) §2.2**，那里逐条标了 structcheck 的断言位置与行号。
本文不复制那份清单，避免两份互相漂移。这里只记三件影响**排期与决策**的事：

1. **加一个服务比看起来贵：会一次性激活 14 道断言。**
   wiring-architect 读完全部 5 个 structcheck 测试文件后确认，
   把 `qqbot` 写进 `.service-matrix.yaml` 的 `services:` 段将同时触发 14 道断言，
   覆盖注册名唯一性、matrix 与目录双向一致、路由模板 dev/pre 双环境核对、
   `internal/pkg` 字节一致、四条部署入口全覆盖、工作负载身份基线等。逐条清单见 wiring.md §2.2。

   **其中最反直觉的一条值得单独拎出来**：`deploycheck_test.go`:609-647
   （`TestHelmLibraryArchivesUseEcommerceNodeSpread`）强制
   `helm/charts/qqbot/charts/library-0.1.0.tgz` 存在且与源模板字节一致——
   而 `AGENTS.md` 与 `.service-matrix.yaml` 都写明 **`helm/` 不是集群真相源、GitOps 当前是断的**。

   也就是说：**你必须在一条已知失效的部署路径上补齐产物，才能让门禁变绿。**
   这不是缺陷，是 `deployment_coverage` 刻意要求的全覆盖；
   合法的减负出口是在 `deployment_coverage.exceptions.helm` 里写明原因，但过期例外同样会被拦。
   **这是真实成本，要人来定，不要让实现者临场决定。**
2. **`gateway_prefix` 不能留空。** 即使 Webhook 回调不经网关（它带不了我们的 JWT，
   走网关没有收益），门禁仍要求每个服务有唯一前缀且在 dev、pre 两份路由模板里都有条目。
   wiring.md §3.2 给了三个方案与取舍。
3. **改路由模板要同 PR 升级 control-tower 依赖，而这条路当前是堵的。**
   wiring.md §3.3 实查发现：Go 模块能用的 `v` 前缀 tag 只到 `v0.1.1`，
   而发布 tag 已到 `0.2.8`，两套命名空间分开。这是一个**排期阻塞**，不是实现细节。

提交前仍需：更新 `TODO.md`（AGENTS.md 硬规则 3），跑 `scripts/verify-quick.sh`。
