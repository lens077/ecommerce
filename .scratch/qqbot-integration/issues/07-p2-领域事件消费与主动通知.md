## 范围

1. 消费「支付成功」「订单发货」领域事件。
2. 向已绑定且允许主动发送的用户下发单聊主动消息。
3. 拒收处理：响应 `C2C_MSG_REJECT` / `GROUP_MSG_REJECT`，标记用户为不可主动触达。
4. 发送前的多维度配额判定与降级。

互动召回（复购提醒）不在本单，见 [08](./08-p2-互动召回.md)。

## 硬性约束

**1. 主动通知不得作为唯一送达手段。**
用户可以在客户端关闭「允许主动发送」，关闭后主动消息一律失败。
每一条交易通知都必须在站内消息中有对应记录，QQ 通知只是加速触达，不承担送达保证。

**2. 发送前判定，不要依赖错误码事后补救。**
每条主动消息发送前依次检查：单关系维度 20 条/分钟 → 每日 1000 条/用户或 1000 条/群 →
认证类型对应的 QPS 或每分钟上限。任一项不通过则不发送。
理由：`40034100` 频控错误本身也消耗接口配额（接口自身 100 QPS）。

配额上限随认证类型变化，取值见 [04](./04-正式环境资质与前置裁决.md)。

**这几个维度的计数不放同一种存储。** 判据是两条正交测试，任一不满足就落 PostgreSQL
（① 平台会不会替你拦住错误 ② 丢失后多久自愈；完整判定表见 [spec.md](../spec.md)「频率账本」）：

- 单关系 20 条/分钟与 QPS：平台会拒绝、秒级自愈 → **Dragonfly**。
- **每日 1000 条/用户或群 → PostgreSQL**。24 小时窗口不自愈，
  且被淘汰后按「全新 1000 条」重算会连续触发 `40034100`，挤占 100 QPS 接口预算、
  **外溢影响其他用户**。

**搬到 PostgreSQL 解决的是「丢失」，没有解决「并发」。** 这两件事要分开做完。

本服务在 Webhook 模式下是多副本的。若用「先 SELECT 查余额 → 判超限 → UPDATE 加一」，
两个副本会各读到同一个旧值、各自放行、各自写回，**实际发 2 条而账上只加 1**，
已用量被算少进而超发。换成 PostgreSQL 不会改变这一点——**决定因素是写法，不是存储**。

必须用一条语句完成「自增并取回真值」，再用真值判超限：

```sql
INSERT INTO qqbot.daily_quota (scope, openid, quota_date, n)
VALUES ($1, $2, $3, 1)
ON CONFLICT (scope, openid, quota_date)
DO UPDATE SET n = qqbot.daily_quota.n + 1
RETURNING n
```

**`RETURNING n` 是关键**：它拿到的是自增之后的真值，用它判是否超过 1000。
少了 `RETURNING`、改用一次单独的 `SELECT` 去查，等于把刚消除的竞态又放回来。
超限时该条不发送，并按「降级顺序」处理。

放 Dragonfly 的短窗口计数同理，用 `INCR` 的返回值判超限，不要 `GET` 之后再 `SET`。

**3. 降级顺序**（从轻到重）：
延迟发送（非时效性通知）→ 合并发送（同一用户短时间内多条）→ 丢弃并记录。
**交易通知不得丢弃**——站内消息已有记录，但必须记录 QQ 侧未送达，供人工排查。

**4. 业务事件去重与出站消息去重分开记录，都放 PostgreSQL。**
领域事件在至少一次投递语义下会重复；矩阵禁止业务服务用 Dragonfly 承载幂等键。

**5. 消息里若带链接，域名必须已在 URL 白名单内。**
白名单上限 20 条、每年可改 50 次，是稀缺资源。域名配置放 Config Center 集中管理，
不要在代码里硬编码。

## 消息形态

若 Markdown 模板权限已获批，可切 `msg_type=2` + `keyboard`；未获批则继续用纯文本。
渲染层在 [03](./03-p0-内部运维通知.md) 已做成可配置，本单不应重写渲染层。

## 验收标准

1. 支付成功后，通知在约定时限内送达已绑定且允许主动发送的用户〔具体时限待确认，
   见 [spec.md](../spec.md) 开放问题里「交易通知的送达时限要求」一条〕。
2. 用户关闭「允许主动发送」后，系统在收到 `C2C_MSG_REJECT` 的下一次通知前停止对其发送，
   且不产生重试风暴。
3. 每日发送量不超过 1000 条/用户、1000 条/群；接近上限时按降级顺序处理。
4. 同一业务事件重复投递时不产生重复通知。
5. 未绑定用户的订单产生事件时，不发送、不报错、有计数。
6. 站内消息记录与 QQ 通知一致；QQ 侧失败时站内记录仍完整。
