购物车：让数量命令拥有完整语义

这一课练习另一种错误：写入条件没有满足，但后面的统计查询成功返回，于是调用方误以为更新成功。

项目现行分层是 service → biz ← data。本课不修改 proto；已批准的 cart_item_id 契约迁移是独立的兼容性任务。

1. 从「参数搬运」升级为命令

// service：proto 与身份 → 领域命令
UpdateQuantityCommand{
  UserID, CartItemID, Quantity
}

// biz：检查业务规则
Quantity ∈ [0, 999]
Quantity == 0  → Remove
Quantity > 0   → SetQuantity

// data：认证用户 + 条目 ID → 命中结果
UpdateOwnedItem(ctx, userID, itemID, quantity) (MutationResult, error)

当前实现的危险点不是「少了一个 helper」。use case 几乎原样转发，service 把 proto 变成请求，data 层又把 Quantity 遗漏到 sqlc 参数之外。接口越宽，调用者越容易把这类关联字段传错。

2. 写入结果必须先于统计结果

UPDATE cart.cart_item
SET quantity = @quantity
WHERE user_id = @user_id
  AND id = @cart_item_id
  AND @quantity > 0
RETURNING id;

-- Go：
changed, err := q.UpdateOwnedItem(...)
if err != nil { return err }
if changed == 0 { return ErrCartItemNotFound }

-- 需要总数时，再在同一事务内查询
count, err := q.CountCartItems(ctx, userID)
if err != nil { return err }
return MutationResult{CartItemQuantity: count}

统计值回答「现在有多少」，不回答「刚才那次写入是否命中」。若 quantity == 0 的契约是删除，就显式走删除命令，或者在一个明确的 SQL 命令中统一返回变更结果；不要靠「UPDATE 没命中但 COUNT 成功」推断。

3. 归属检查不是网关的替代品

service 可以从身份头解析 UserID，但 data 的条件仍必须包含 user_id = authenticated_user。网关的 RBAC 只回答「能否调用这个 RPC」，Repository 还必须回答「这条 cart item 是否属于当前用户」。

5. 最小实现顺序

  1. 先在 biz 定义命令、范围和领域错误。
  2. 再让 service 只做身份与 proto 转换。
  3. 修改 SQL，使更新返回明确的命中事实；0 行不能默认为成功。
  4. 数量为 0 的删除语义单独测试。
  5. 把 SQL 与归属、统计一致性放到真实 PostgreSQL 测试；不要使用 sqlmock 或 pgxmock。
查看项目中的直接线索

backend/services/cart/internal/service/cart.go 已读取 quantity，但 backend/services/cart/internal/data/cart.go 的更新参数没有传入它。backend/services/cart/internal/data/queries/cart.sql 还把 UPDATE 包在 CTE 里，却只返回后续 COUNT。这正是「写入事实」与「统计事实」混淆。

本课记住

接口应表达命令，不是字段搬运。

写入命中和统计数量是两个事实。

归属检查必须落到数据条件。
