库存预占：先保证整组，再谈重试

这一课只解决一个问题：一个订单包含多个 SKU 时，为什么「其中一项失败」必须让前面已经写入的项一起回滚。

本课对照项目的目标态 ReserveGroup。现有 inventory/internal/data/inventory.go 仍是未完成实现；课程中的伪代码不是可直接合入的补丁。

1. 先写不变量

  • available = on_hand - reserved - locked 始终成立。
  • 一组预占要么全部成功，要么一个也不改变。
  • 同一个 reservation_id 重放不能重复扣减。
  • 多个 SKU 要按统一顺序拿行锁，降低死锁概率。

事务只解决第一条业务边界的「一起提交或一起回滚」。它不会自动解决幂等、授权、死锁重试，也不会替你检查更新是否命中。

2. 正确的 module 形状

service  -- 只做 proto / 身份 / 错误码映射
   |
biz      -- ReserveGroup 命令与领域错误
   |
data     -- 一个 tx：查 reservation → 锁 SKU → 条件更新 → 写流水

外部 interface：
ReserveGroup(ctx, reservationID, payloadHash, items) (Result, error)

这是一个深 module：调用方只知道「提交一组预占」，不用记住事务、锁序、行数检查和流水写入的顺序。内部可以使用 sqlc 的 Queries.WithTx(tx)，但不能把这个内部规则泄露给调用方。

3. 一个失败路径

BEGIN
  读取 reservation_id
  若已是 reserved 且 payload_hash 相同：返回首次结果
  若 payload_hash 不同：返回 INVALID_ARGUMENT

  按 sku_id 升序锁住全部 stock 行
  对每行执行：
    UPDATE stock
       SET available = available - $quantity,
           reserved  = reserved + $quantity
     WHERE sku_id = $sku
       AND warehouse_id = $warehouse
       AND available >= $quantity
  检查 rows_affected == 1
  写 reservation_item 与 change_log
COMMIT

任意一项的条件更新影响 0 行，都返回缺货或冲突错误。不要先提交 A，再处理 B；也不要用 Redis 锁代替 PostgreSQL 的正确性锚点。

4. 小实验：你来判断事务边界

订单要预占 A=2 件、B=2 件。A 可用 5，B 可用 1。哪种执行者符合「整组原子」？

  2. 把所有读写统一到同一个事务 Queries。
  3. 把请求从单 SKU Reserve 收敛为目标态的 ReserveGroup。
  4. 用真实 PostgreSQL 验证第二项失败时第一项没有留下变化。

sqlc 的 WithTx 只会让绑定后的 Queries 使用事务；如果某个写入仍调用 pool 上的旧 Queries，它就不属于这次事务。PostgreSQL 的 FOR UPDATE 行锁通常持有到事务结束；多个对象必须统一锁序。

本课记住

事务是原子性，不是幂等性。

0 行更新不是成功。

锁序是接口的隐含约束，应藏在 module 内。
