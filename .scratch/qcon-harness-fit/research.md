# QCon Harness 工程实践：对 ecommerce 的适配研究

> 性质：研究建议，不是新规范、实施单或第二份进度表。未批准实施，未修改代码、规则、TODO 或部署。
> 取样对象：本次会话中的 ecommerce 工作树，包含研究开始前已有的未提交改动；不等于已提交或已部署版本。
> 结论：不引入新的 Agent 框架。先把既有交易正确性要求变成可执行的终态验证，再加固现有规则式 copilot 的执行边界；复用现有纠错与验收机制，不另建评测平台。

## 1. 阅读范围与证据等级

四场 QCon 页面已在前文取得议题介绍、演讲提纲、实践痛点、亮点和听众收益，本轮复用并逐项对照，没有重复抓取。它们是官方演讲提纲，不是 PPT、视频实录或可复现的实验报告。抓取尾部有截断标记，不声称网页每个字节均已读取。

另由一个只读研究子代理查核五篇官方扩展资料的相关正文。Anthropic 抓取存在长度截断，仅使用已见段落；MCP 两页用对应 Markdown 正文补读。没有读取或验证提纲提到的 OpenAI × Thrive Tax AI 案例，不将其作为独立佐证。

全文区分四种证据：

- **来源主张**：讲师提纲或厂商官方文章的叙述，不自动代表独立验证的效果。
- **本地源码事实**：在明确文件中观察到的实现，不自动代表运行时行为或部署状态。
- **本次执行事实**：实际执行的测试与退出结果，仅证明被测范围。
- **建议／待验证假设**：由资料与源码推导的方案；没有把它写成现有能力或已修复缺陷。

没有核查集群、线上流量、凭据、支付渠道或 DSH 的权限实现。支付实现继续保留给用户，不能因为研究建议而扩大 Agent 授权。

## 2. 四场原文细读

### 2.1 Cherry Studio：业务 Harness 的价值是交付契约，不是增加编排器

来源：[从通用 Agent 到业务 Harness：画边界，而不是画路径](https://qcon.infoq.cn/2026/shanghai/presentation/7306)。

原文的完整结构是：工具调用、通用 Runtime、垂直业务 Harness 三层；模型与工具的小循环嵌入目标、澄清、Spec、动态 DAG、执行、验证的大循环。它特别区分「源码已实现」「企业端到端已验证」「商业结果已验证」。

比「动态 DAG」更值得采纳的是三个具体要求：

1. 输入契约、业务状态、权限、责任人和验收标准须明确，不能只展示工具调用过程。
2. 人的注意力优先放在目标和验收，而不是逐步遥控执行；但目标改变和高风险动作仍需接管。
3. 一次性现场经验要转化成可复用规则、工具或验收证据，而不是不断增加应用数量。

300 多家门店对账的案例很能说明边界：Agent/OCR 读取、归一、匹配和归集证据；稳定的销售额、扣点、日期规则转成确定性脚本；财务确认由人负责。提纲同时说明，单份演示的 5–10 分钟和约 0.14 元模型费用不是生产 SLA，也不是完整交付成本。不能拿它估算本项目工期或 ROI。

**对本项目的取舍**：复用已有实现单的验收标准与完成自检，不新增 DAG 服务。现有 copilot 只有固定句式和受控页面动作，动态规划尚无必要。Skill/MCP/Hook 可以帮助划分控制点，但它们不是天然的安全等级：实际强度取决于工具暴露范围、服务端授权、宿主执行和可否绕过。

### 2.2 B 站：约束、定位、验证、度量，不能缩成「再加门禁」

来源：[当代码不再稀缺：大型工程 AI 狂欢下的确定性底座](https://qcon.infoq.cn/2026/shanghai/presentation/7317)。

提纲将问题拆成四类：架构规则进入 Format/AST/编译/测试；通过工程关系定位上下文；提供交付证据；从代码量、Token 和采纳率转向是否可安全合并。同时明确讨论 Harness 腐化和失败方案止损。

这不是「文档越少越好」：代码适合承载结构性事实，设计文档仍需解释业务语义、取舍与尚未实现的目标。把所有文档删除，会丢失为什么取消订单后迟到付款不能复活订单这类信息。项目已有 `context/`、设计文档、结构矩阵的分工，应继续保持。

**对本项目的取舍**：先检查现有验证是否覆盖真实故障，而非增加规则数量。订单保存方法返回 nil、库存更新没有可靠事务证据时，即使格式、编译和结构检查全绿，也不能视为交易已交付。已有完成自检可以承载证据，不需要新的通用「交付证书」平台。

**证据局限**：该提纲没有给出可复算的完整成本、样本量或收益数据；不能把「敢不敢合并」直接当客观 KPI，应落实为具体状态断言与已执行验证。

### 2.3 飞猪：可撤回性决定自动化上限，但不替代授权

来源：[模型与代码的边界思考：飞猪旅行 Agent 的落地实践](https://qcon.infoq.cn/2026/shanghai/presentation/7280)。

原文比「决策归模型、执行归工程、表达归产品」更具体：模型提方案；票种组合由求解器计算；创单与支付不注册为工具；房型真实标识不进入模型；卡片由代码使用当轮检索结果构建；终止依据行为而非模型自述。Judge 提取事实，代码按规则算分。

需要保留三个限制：

- **可撤回不等于已授权**。提交可以撤销，但本仓仍要求用户授权；读取敏感信息没有写副作用，也仍需要访问权限。风险判据不能替换 AGENTS 的授权约定。
- **隐藏真实 ID 不等于授权**。未来若给模型临时候选引用，执行时仍需验证候选是否来自本次查询、是否属于当前用户与会话、报价是否过期、资源权限是否仍有效。
- **代码打分不等于事实正确**。如果 Judge 提取错了，确定性映射只会稳定地产生错误分数。事实证据、Unknown 和人工校准仍不可省略。

**对本项目的取舍**：checkout v2 已设计服务端报价、身份绑定、幂等、fencing、组原子库存和补偿机制。不要借 Agent 绕过它。当前 copilot 继续不注册交易写动作；以后若引入模型，只允许其提出受约束候选，不能让模型构造金额、订单主体或支付事实。

### 2.4 快手：自进化是受控变更闭环，不是自动改规则

来源：[复杂业务 Agent 的持续进化：快手电商导购的 Harness Loop 实践](https://qcon.infoq.cn/2026/shanghai/presentation/7231)。

原文要求轨迹关联模型、Prompt、Tool、配置与知识版本；从规划、工具参数、上下文／记忆、执行恢复、模型约束、多域整合六类定位失败；根据根因修改对应层，再做回归、多次运行、跨场景退化检查和灰度。它明确承认自动归因可能导致错误优化，仍需人工审核。

最值得借用的是「先归因，再选择修复层」：SQL 约束错误不靠改 Prompt；超时后动作继续不靠多写一句「及时停止」；测试把错误行为当标准时，应先修评估器。

**对本项目的取舍**：在既有问题单中记录失败证据、归因和对应回归即可。六类可以作为分析提示，不必机械引入新分类规范。项目已有 Session 反传、规则变更人工裁决和门禁 canary，不应再建 `.learnings/`、自动规则晋升或新的进度系统。

轨迹也不等于可安全重放。交易复现应使用隔离数据库、固定输入和必要的替代依赖，不能把线上创单、扣款、退款再执行一次。copilot 当前还明确禁止持久记录用户原句，不能照抄快手的全量输入记录方式。

### 4.1 copilot 的具体待验证风险

`executor.ts` 的 `withTimeout` 用定时器拒绝 Promise，但没有取消传入的底层 `runOne`；`CopilotProvider.tsx` 的 finally 清理运行状态，却没有在那里中止对应 controller。逐字输入和动画依赖的是该 controller 的 signal。

因此存在「外层显示失败／回到 idle，旧动作仍继续执行」的代码级风险。现有超时测试只检查错误和步骤序号；显式 abort 测试不等于超时取消测试。

这是静态分析结论，**未运行针对性复现**。不能称为已复现线上故障，更不能声称已修复。应先补一个能显示超时后仍有迟到 DOM 变化的用例；若不能复现，则调查调度和上下文，不为假设硬改实现。

## 5. 推荐方案与顺序

### A. 第一优先：把交易 P0 做成「真实终态」回归，而非新 Harness 工程

**对应现有任务**：TODO 的库存预占／释放、订单假成功与持久化、地址归属。不是新建一份同名待办。

先选一个最小切片，例如库存预占。按既定契约完成真实数据库验证，同时单独阻断订单未实现路径的假成功。不要把库存、订单、支付一次性绑成大改造；支付接口协作与实现仍由用户主导。

建议的验收分层：

| 层次 | 必须证明的事 | 不能拿来替代它的证据 |
|---|---|---|
| 未实现路径 | 返回明确的非成功；无业务订单／完成事件等伪结果 | 日志写了 save、RPC 返回 200、模型说已完成 |
| 库存更新 | 固定库存与扣减量得到正确余额；条件更新零行不能报成功 | stubRepo 返回预设成功 |
| 原子性 | 后续明细或流水写入失败，前面的库存变更也回滚 | 只验证最后一个函数返回 error |
| 并发性 | 竞争预占不能使库存越界，成功记录与库存变化一致 | 单线程 happy path、编译通过 |
| 幂等与恢复 | 按现行接口兼容策略及 checkout v2 的阶段设计，证明重复与迟到请求不会产生额外副作用 | 未经契约迁移就把旧接口 AlreadyExists 改成新 reservation 语义 |
| 身份归属 | 用户 A 操作 B 的资源被拒，且数据无变化 | 前端隐藏按钮、模型不输出真实 ID |

**最小工程投入**：先核对并补齐首条真库回归所需的最小测试辅助，落点沿用规范指定的 `backend/pkg/testutil`。不假定它已存在，也不为十个服务预建完整测试平台。使用真实 migration；测试数据库必须隔离，不能指向共享 dev/prod。镜像、依赖版本在实施时现查，不照抄手册里旧运行环境快照。

**执行边界**：真实 SQL 测试不带 `-short`；带 `-short` 的 skip 是机制验证，不是业务通过。CI 的资源预算与当前 Runner 验收仍有限制，先验证一个服务的资源开销，不默认在所有 push 上启动全量数据库测试。

**停止扩张条件**：切片已经能够复现并挡住对应错误，就不顺手补无关 getter、覆盖率或其他服务用例。依赖尚未实现时明确阻断，不用 mock 成功掩盖缺口。

### B. 与 A 同步：复用现有完成自检，补证据，不建新证据平台

在对应实现单已有的「完成自检」中说明：验证对象、命令、实际运行的具名用例、结果／skip、关键终态、证据所属代码版本。工作树不干净时注明包含哪些本地修改，不能只用 HEAD 代表被测版本。

可复用的思路是：

```text
失败场景 -> 所属层归因 -> 最小修改 -> 同场景反例回归
        -> 相关既有用例 -> 完成自检记录证据 -> 人决定交付
```

不是每个环节都需要 Agent，也不是新建状态机服务。对 SQL、权限、状态迁移使用确定性断言；对开放式语义才考虑人工或模型辅助判断。

门禁本身改动时沿用现有 canary，验证「有效输入可过、对应坏输入会被拒」；不要只检查脚本存在。失败归因可采用会议的六类思路，但不把每个 bug 都升级成跨项目硬规则。

**验收**：同一份实现单能定位到该故障的红／绿证据和实际运行范围；未执行与环境阻塞明确记录；没有第二份进度表。单位成本先观察本地实测的验证时间、返工和人工复核时间，不承诺厂商案例的提升幅度。

### C. 现有助手的独立小切片：先做「真的停止、真的完成」

保持 `@ecommerce/copilot` 的无 LLM、无新后端定位。借鉴飞猪的行为终止和 Anthropic 的 outcome 评测，而不是复制旅行导购系统。

建议依次验证并修复：

1. **超时取消**：超时后终止该次运行中仍可取消的动作，清理等待和确认状态；不得继续产生迟到输入或点击。不能撤销的导航／网络效果需要读回确认，不能把超时解释成「一定没发生」。
2. **运行隔离**：旧运行的迟到完成、finally 或 summary 不应清除或覆盖新运行；以运行身份和信号约束交接，而不是依靠显示文本。
3. **结果判据**：动作序列结束与业务结果确认分开。沿用现有页面状态读取能力，为具体动作核对后置条件；结果未知就标明未知，不兜底宣称业务成功。不规定必须增加一个通用 verify 框架，先在一个动作上证明需求。
4. **未来写动作的准入**：当前不为验证机制而注册发货、退款、改价、支付等动作。届时按已有设计分别检查确认对象、参数、页面变化导致失效，以及服务端资源授权；确认原语存在不等于这套机制完整落地。

最小回归集合应覆盖：超时后推进计时器无新增副作用；显式停止不执行后续步骤；新运行不受旧运行迟到完成影响；动作触发但后置条件未满足时不宣称成功；既有 13 个包内测试不退化。实施时还需按具体 UI 变更跑真实浏览器旅程，jsdom 通过不能代替浏览器验收。

如要记录运行证据，只保留必要的动作名、运行 ID、步骤／终态、耗时、原因码和版本。默认不落用户原句、商品文本、地址、token 或原始 DOM；不新增遥测后端。具体记录需要可证明的排障需求，不能为了「轨迹资产」先采集全部数据。

**优先级**：这是现有助手的正确性增强，可作为独立小任务；不应挤占交易 P0，也不以此名义引入 Agent OS。

### D. 条件成熟后再做：受约束的模型意图解析

重新评估的触发条件应是固定句式确实阻碍真实任务，并且已有重复使用、未命中或人工处理成本的证据；不能因为 QCon 讨论 Agent 就提前升级。涉及用户原句的取样需另行设计授权和隐私边界。

届时最小试点仍应是一个只读场景，例如商品搜索条件解析：模型输出有限 schema 的提议，程序验证参数和允许动作，服务端返回当轮权威商品事实，页面负责展示。资源引用限定在当次结果和用户／会话内，过期即重新检索；模型不提供身份、权威价格或支付事实。

试点应与规则基线比较任务完成、越权／幻觉拒绝、人工兜底、时延和费用。只有质量改善且预算可接受才保留；否则回退规则路径。模型不确定时澄清或拒绝，不自动扩大工具权限。

## 6. 不采用项

| 方案 | 当前不采用的理由 | 重评条件 |
|---|---|---|
| 新 Agent 平台、动态 DAG、多 Agent 导购 | 当前 copilot 是固定行为；交易底层尚有 P0；强依赖链不适合靠并行增加复杂度 | 已有真实跨域开放任务，单一执行器的瓶颈经过测量 |
| 强化学习、向量记忆、自动规则进化 | 没有本次核实出的训练需求；规则本来就要求人工裁决 | 有足够失败样本、可靠评估、预算与明确收益假设 |
| 新增 LLM-as-Judge 作为交易门禁 | 当前关键结果可直接检查；评分事实仍会误判 | 出现确定性规则难判、人工容量不足的开放式输出 |
| 全量轨迹存储和线上副作用重放 | 隐私、存储和错误重放风险；违背 copilot 不记录原句的现有边界 | 有具体排障需求，并先实现脱敏、访问控制和隔离重放 |
| 用「可撤回性」替代授权列表 | 风险分类与权限是不同维度；可回滚操作也可能未经授权 | 不适用；只能作为补充的风险分析维度 |
| 为补「MCP 中间层」而包装全部业务接口 | 协议不会自动提供安全隔离；增加旁路反而扩大攻击面 | 真实外部工具集成需求及明确宿主、服务端授权设计 |
| 重建 `.learnings/` 或演进日志归档 | 既有人工沉淀、Git 与决策记录已经分工；TODO 明确不恢复形式性归档任务 | 按既有 flywheel-audit 的触发条件重新评估，不因本文直接变更 |
| 删除 E3 的「先估计、最小执行、失败扩张」 | 「画边界」不是否定有用的执行策略；安全边界与可调整策略可并存 | 只有真实失败证据证明某条策略有害时才小步调整 |
