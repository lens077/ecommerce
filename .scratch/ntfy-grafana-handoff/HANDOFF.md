## 5. 没有解决什么

### 仍然存在的运维目标缺口

- **CNPG 备份与恢复能力**：上次只读观测到 `pg-main` 的可用备份时间和恢复点为 0；Cluster 未配置 backup/plugin，未返回 Backup/ScheduledBackup 对象。本轮只是把这一事实展示清楚，没有创建备份、配置归档或做恢复演练。
- **真实终端送达**：本轮未向真实 topic 发测试消息，也未验证手机订阅、终端收到、故障确认后通知、恢复通知和退避周期的完整行为。
- **独立外部 dead-man**：同一集群内的自监控不能证明集群或 ntfy 全故障时仍有人收到告警。
- **观测覆盖**：宿主 watchdog/资源、容器实际 CPU/内存/磁盘、Backup CR 状态、Vector 部分指标和若干服务专属指标尚未完整接入。
- **试运行预算校准**：20 条/小时是待观察的预算，不是已由长期基线证明的故障阈值。
- **历史告警正文**：详情页取当前实例；实例恢复或移除后不提供历史 annotations 存档。
- **prompt 标记原因**：没有材料，没有诊断结论。

### 交付和测试仍有边界

- 多仓存在大量混合未提交/未跟踪改动；没有提交、推送或发布可复现版本。
- `verify-context.sh` 上次失败 3 处引用：`scripts/test-doc-sync.py`、`scripts/test-env-check.py`、`backend/pkg/gorse/live.go`。文件存在但当时未被 Git 跟踪，来自其他工作；没有擅自 add 或修改它们。
- `verify-triage.cjs` 依赖当前存在的 `CNPGNoBackupEver`，备份修复后该测试会因前提消失退出；它不是通用的全部告警 E2E。
- 全部基础设施「链接带的每个筛选参数都生效」未逐个验证。生成器的类目告警表按 group 过滤，并不按页上所有对象变量过滤；部分页只消费特定变量。不能把 CNPG 一条成功链路泛化为所有告警路由正确。
- `build_main()` 读取既有工作台 JSON 再生成，不是完全独立的单向源生成。`--check` 能防部分漂移，但不能证明从零重建不依赖旧 JSON。
- 截图和 job 输出是阶段性证据，临时目录会清理；不是长期验收档案，也不是实时健康状态。

## 6. 最没有把握的是什么

**最没有把握的是：告警从真实故障到用户终端、再到可恢复处置，是否已经可靠闭环。** 当前最强证据集中在「页面能查、原文能读、CNPG 路径能跳」，不在「生产故障时一定能收到、备份一定能恢复」。

| 把握程度 | 内容 | 降低不确定性的办法 |
|---|---|---|
| 高 | 已展示的告警原文、精确实例定位、公网查询修复、最终源码/页面一致 | 保留现有回归，并在每次部署后复跑真实页面。 |
| 中 | 当前七页覆盖了已接入的主要集群对象/数据库/CDC/采集信号 | 用实际服务清单逐项核对指标及对象过滤；不以页面数量代表覆盖率。 |
| 低 | host-watchdog、AM、bridge、ntfy、手机在故障/恢复/重试中的端到端行为 | 在获准隔离主题上演练，并由终端收件证据确认。 |
| 低 | 数据库可恢复性、外部故障域覆盖、前序凭据变更的长期一致性 | 独立恢复演练、外部 dead-man，以及单独的凭据来源一致性检查。 |
| 无法判断 | 原 prompt 为何被标记违规 | 恢复原始 prompt、报错/分类、请求 ID 与服务侧证据；不得从标题反推原因。 |

还有一个已知语义问题应核对：`CNPGBackupStale` 当前表达式未排除 timestamp=0，所以「从未有备份」也会被解释成「备份过期」；`CNPGNoBackupEver` 的说明写成指标没出现，但实际也覆盖指标存在且值为 0。**这影响告警解释/重复，不等于可以隐藏无备份风险。** 本次交接只记录，未修改规则。

## 7. 下一步怎么做：回到最初目标，不再先堆面板

### P0：先复核真实备份缺口，确认恢复目标

1. 用当前 kube context 只读核对 CNPG Cluster、Backup、ScheduledBackup、归档配置及指标，确认上次观测是否仍成立。
2. 和用户明确 RPO、RTO、保留周期、备份目的地及故障域。已有 Silo 不等于合格的独立备份：单集群、单盘/单实例需单独评估。
3. 提交最小备份方案与隔离恢复方案；获得该范围部署授权后再实施。
4. 完成标准：存在成功备份、有效恢复点、可验证 WAL 链，并在隔离目标恢复且核对数据。只看到 Backup 成功不算恢复能力完成。

### P1：闭合告警送达与降噪行为

- 使用独立 test topic/身份/状态，覆盖 firing、持续确认、重复抑制、恢复、发送失败重试和重启后状态保留。
- 分别记录规则触发、AM 接收、bridge 决策、ntfy 接受、终端收到，不能用其中一层代替全部。
- 建立位于不同故障域的 dead-man；验证集群和主通知服务失效时的告警通路。
- 用 24–48h 以上实际基线校准提醒预算，而不是提高阈值来消除红色。

### P2：修正已发现的规则解释与对象过滤边界

- 将「从未有备份」与「曾有备份但已过期」语义拆清，保留持续提醒关联；先写零值/缺失/正值测试再改表达式与文案。
- 核对 `current_alerts()` 类目表与页面对象选择器的关系：要么按所选对象过滤，要么在标题上明确「全类目」。
- 扩展链接 E2E 至 Kubernetes、CDC、采集/网络告警；覆盖聚合告警缺 Pod、实例已恢复、非法变量、空列表、权限失败。
- 将测试对生产特定故障的依赖改成隔离 fixture/受控环境，不能为了测试让生产继续没有备份。

### P3：按风险补采集，不按面板数量补图

先宿主 watchdog 与磁盘/实际资源，再 Backup CR 与恢复证据，再高价值服务专属指标。每个新来源都要求可用 series、缺失检测、可行动规则与明确排查入口。

### P4：整理可交付版本

按任务切分混合 diff，协调其他会话处理文档门禁引用，再做源码/生成物/部署对账。提交与推送须另有授权；不要 `git add -A`。

若用户真正仍要排查「prompt 标记」，单独建立支线恢复证据；不要继续把运维建设当成对该问题的答案。
