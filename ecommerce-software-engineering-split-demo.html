  • 服务拓扑、路由、配置键变化：更新服务矩阵及其结构性验证。
  • 实现进度变化：更新项目指定的进度真相源，不以聊天记录替代。
  • 修改 Agent 上下文、设计索引、STACK 或门禁脚本时，按仓库现有规则执行上下文验证；门禁脚本本身变更还应运行对应 canary（具体命令以当前 AGENTS.md 为准）。

03 · Harness 与 AI Agent 工程规范（已按 AGENTS.md 核验）

以下内容直接来自根目录 AGENTS.md（commit 6037246e）与 context/harness-framework/，是仓库真实执行的规则，不是建议稿。

3.1 八条硬规则（不可跳过）

#规则要点
1以真相源为准规范看 context/（入口 context/INDEX.md），拓扑看 .service-matrix.yaml；找不到知识 ≠ 没有约束，先读 docs/design/ 与 TODO.md
2写/改 proto 前必须先读设计文档并为每个字段推断出校验约束（context/team/proto-design.md）
3提交前先问：涉及哪个 TODO 项涉及就先更新 TODO.md；提交信息走 Conventional Commits，commitlint 钩子强制校验
4不要把凭据写进仓库密码/密钥只存 Config Center 与本地环境（K8s 经 Secret 挂载）；Consul KV 已退役，Consul 只做注册发现
5踩到坑要沉淀区分「模式性教训」（写进 context/）与「一次性 diff」；改 harness 门禁时必须在改动处写明触发它的具体事故
6不可逆动作需要授权，授权后直接执行git commit / push、MR 合入、kubectl apply/delete、helm、docker push、workspace 外写入。用户明确要求即视为授权，不二次确认；删数据、force push、改 prod 鉴权等仍需先说明影响
7全自动模式不询问权限，但仍询问实质性选择被硬性安全边界阻止时直接报告阻塞，不伪装成业务选择
8解决问题优先，不堆工作量写测试只写能验证本次改动或挡住 bug 复现的测试；禁止覆盖率凑数、顺手扩张

3.2 反直觉约定（读代码不易发现）

  • 前端用 vite-plus（vp）覆盖 dev/build/test/lint/fmt/git 钩子，没有 husky/biome/eslint/prettier；commitlint 由 frontend workspace 承载（根目录无 Node workspace）。
  • 进度真相源 TODO.md 唯一；架构真相源 docs/design/ 按微服务分目录。
  • 网关和配置中心不在本仓，由同级仓 control-tower 承载；backend/structcheck import 其 routes 核对路由，改路由模板必须同 PR 升级对 control-tower 的依赖版本。
  • 部署清单两份真相源（helm/ 与 deploy/{base,overlays/prod}）必须逐字段等价，scripts/verify-deploy-parity.sh 强制；两份都写 KYAML（值一律双引号、结构靠 {} []），scripts/verify-kyaml.sh 阻断。
  • okteto up 前必须现查 ArgoCD 归属；纳管时先关自动同步，否则开发容器会被 GitOps 干掉。

3.3 执行策略 E3（先估计 → 最小执行 → 失败才扩张）

  • 动手前先估计规模并说出来，最多一次廉价探测：L1 单文件局部修改 / L2 少数文件跨文件修改 / L3 仓库级重构（警惕 re-export、别名、网关接线、Config Center 键这类 grep 看不到的间接引用）。
  • 按估计走最小路径，改完立即跑最便宜的适用验证；只有验证变红才扩大范围，一次扩一级。
  • E3 不豁免硬规则（proto 前读设计文档仍必读），也不反向加码「先通读代码库」。

3.4 消费边界（用户给的是目标，不是空白支票）

  • 派 subagent 前先说出数量和理由；单轮超过 3 个或子代理再派子代理，先问用户。
  • 每次扩张（新 subagent、检索扩大、切更贵模型、第 2 次重试）回复里说一句，不静默。
  • 只读调研 >20 次仍未汇总、连续两轮 cacheReadTokens=0、同一检索重复执行等告警出现即停下报告。
  • 任务结束按 usage 报请求数、token、subagent 数与超预期原因（「小票」制度）。

3.5 Agent 约束与交付报告

  • 证据：不得声称测试通过、部署成功或安全边界成立，除非有对应命令输出或可信观测证据。
  • 生成代码：先改源契约 / 源 schema 再运行生成器；禁止手改生成产物掩盖源定义问题。
  • 破坏性操作：必须遵循第 6 条授权流程；subagent 永久不得执行任何不可逆动作（拿不到用户授权上下文）。
  • 失败报告：测试失败、环境不完整或检查未执行时，写明失败项、原因、影响和剩余风险；放行以「命令真绿」为准，不以模型自报为准。

3.6 验收锚点（提交前必跑，来自 AGENTS.md 原文）

scripts/verify-quick.sh                          # 默认入口：后端链+前端并行
cd backend && go build ./... && go vet ./...     # 编译 + 静态检查
cd backend && go test -count=1 ./structcheck/... # 改 .service-matrix.yaml/加删服务后必跑
scripts/verify-kyaml.sh && scripts/verify-deploy-parity.sh  # 改部署清单后必跑
cd backend && go test -short ./...               # 后端测试（CI 用 -short）

scripts/ 目录实测存在 11 个 verify-* 脚本（quick / context / context-canary / kyaml / deploy-parity / http-boundary / secrets / release-local / repowise / doc-sync / public-ips）。verify-context.sh 是 main 上唯一必需的 CI 检查；核心改动 push 前做异构双审（两个只读 subagent 分走不同模型族审 diff）。

pnpm workspace + vite-plus（vp），2026-03-18 从单体前端迁来（迁移提交 75f57beb）。版本统一由 pnpm-workspace.yaml 的 catalog 管理。

4.1 应用与共享包（实测清单）

app端口说明启动

4.2 共享包边界（12 个，实测）

api（Connect transport、拦截器、错误归一化）、configs、constants、copilot（页内助手）、i18n、icons、lantern（共享模型与 token）、perf（Web Vitals 经网关 telemetry.v1 上报）、tauri（桌面胶水）、tracker（埋点上报 behavior 服务喂 gorse）、ui、utils。

分包原则：被两个以上 app 用到且不含业务语义才进 packages/；只有一个 app 用的东西留在那个 app 里——提前抽包换来的是每次改动都要跨两个目录。

4.3 app 内四层（沿用自旧单体前端）

目录职责能否持有状态
conf静态声明：环境地址、常量纯静态，编译时确定
utils纯逻辑计算：格式化、加密无状态
hooks逻辑复用：封装请求、表单逻辑有状态但不共享（每组件独立）
页面组件组合领域模块与 UI业务页面按领域组织，避免巨型组件

该分层适用于 consumer / merchant / admin；desktop 是 Rust 壳不适用，consumer-next 用 Next.js 的 app/ 目录。

4.4 API 与类型安全

  • 前后端共享契约以 Protobuf 为准（packages/api 承载 Connect transport）；请求、响应、枚举和字段约束在源契约中维护，禁止手改生成产物。
  • 统一认证凭据、错误归一化、超时和取消机制；不要在每个页面重复实现拦截器。
  • 不得将客户端隐藏按钮视为授权控制；服务端仍须执行资源级和业务级授权。
  • 购物车、价格、库存、订单状态等关键业务数据以服务端结果为准；前端乐观更新必须可回滚且不能成为业务事实来源。

4.5 前端验收（AGENTS.md 锚点，已核验）

vp run -F <app> dev          # 按需启动单个 app；desktop / consumer-next 见 4.1 表

git 钩子由 vp 配置装在 frontend/.vite-hooks/（见 frontend/README.md）；commitlint.config.mjs 也在 frontend workspace 内。仓库没有 husky / biome / eslint / prettier。

05 · 后端工程化规范（已按 backend/ 实测核验）

以契约先行、领域边界清晰、数据所有权明确、错误可观测和变更可验证为核心。

5.1 分层职责

层职责禁止的耦合
biz领域结构、业务规则、领域错误和用例所需的抽象不直接依赖 HTTP / Connect 传输对象、具体 SQL 驱动或全局配置单例
data数据库、缓存、搜索、事件、对象存储等外部适配器不承载跨领域业务编排；不能绕过领域规则写数据
service协议层到领域层的转换、输入协调、响应映射避免把完整业务逻辑堆积在 RPC handler
serverConnect / gRPC 服务注册、Fx 装配、生命周期和依赖注入避免在启动装配层隐式执行业务写操作

已核验：backend/services/ 下 10 个服务（address / behavior / cart / inventory / merchant / order / payment / product / search / user），每个服务 internal/ 含 biz、conf、data、server、service、tests（order 另有 eventbus）；技术栈实测 go.mod：connectrpc.com/connect v1.20.0、go.uber.org/fx v1.24.0、pgx/v5 v5.10.0、goose/v3 v3.27.3、otelconnect、connect validate，服务目录含 sqlc.yaml 与 buf 配置。

5.2 契约与错误处理

  • Protobuf 是前后端 API 契约的主要来源；字段验证规则应在 schema 中表达，并运行项目指定的 Buf lint / breaking 检查。
  • API 变更按兼容性策略执行：优先增加可选能力，避免重用字段编号或改变已有字段语义。
  • 错误应区分输入校验、未认证、无权限、资源不存在、冲突、限流、依赖故障和内部错误；不得把内部堆栈、SQL、密钥或敏感标识返回客户端。
  • 外部调用需有明确超时和取消传播；重试必须依据操作幂等性设计，不得对支付或订单写操作盲目重试。

5.3 数据库与一致性

  • 每个服务对其拥有的数据负责；跨服务业务协作通过公开契约 / 事件进行，不以跨服务直接读写数据库替代服务边界。
  • SQL 变更使用仓库既定迁移工具，审查升级与回滚策略；生产迁移前评估锁、数据量、兼容窗口和恢复方式。
  • 订单金额、库存、支付状态、幂等键、领域锁等关键事实必须由可靠持久化机制约束；缓存不能成为这些数据的唯一事实来源。
  • 若使用事件最终一致性，应定义事件 ID、schema 版本、幂等消费、重试、死信与重放流程；未启用的事件链不能写成已投产能力。
  • sqlc 生成文件与 SQL 源文件需保持可再生成；先改源 SQL / schema，再运行生成和测试。

5.4 配置与依赖注入

  • 配置必须明确来源、必需项、默认值、敏感级别和启动失败行为；不得将缺失的关键安全配置静默降级为弱默认值。
  • 配置中心、数据库等启动依赖应有健康检查、超时和可诊断错误；不允许未经设计的隐式 fallback。
  • 通过 Fx 或项目指定的依赖注入模式管理生命周期；启动、关闭和资源释放行为必须可测试。
  • 服务注册与发现：已核验 Consul KV 已退役不再存配置，Consul 只做注册发现（context/project/ecommerce/config/experience/consul-kv-retired.md）；配置统一走 Config Center，集群里 config-center 命名空间是遗留标签，镜像实为 control-tower-config。

06 · 测试策略与质量门禁

测试金字塔、契约检查、端到端验证与发布证据必须对应不同风险，不能用单一“测试通过”覆盖全部质量判断。

6.1 测试层级

层级主要目标示例验收要点

单元测试验证局部业务规则与边界条件Go testing、Vitest覆盖关键分支、异常输入和回归案例

契约测试验证 schema 与消费者兼容性Buf breaking、生成代码一致性变更符合兼容策略且生成物无漂移

6.2 E2E 规范

  • 优先使用隔离的测试环境和专用测试账号；测试数据必须可识别、可清理。
  • 涉及真实生产站点时，必须得到明确授权，避免创建真实订单、支付、发信或不可逆业务数据。
  • 禁止只检查 HTTP 200 或页面存在；要断言关键状态变化、错误路径和权限边界。
  • 测试必须可重复运行，明确重试策略；重试不得掩盖真实不稳定性。
  • 生产 E2E 流量应使用可审计的机器身份 / 标记，并在分析系统中通过可靠规则区分；不要只依赖 User-Agent 伪装或可被用户伪造的单一请求头。

6.3 门禁设计规则

  • 每条强制规范都映射到自动化检查或明确的人工审查清单。
  • 门禁失败默认阻断合并 / 发布；例外必须有负责人、理由、到期时间和补救任务。
  • 门禁脚本必须有正向与负向 canary：合格样例应通过，故意违规样例应失败。
  • 避免“永远成功”的占位检查、忽略失败的 shell 管道和不受控的 continue-on-error。
  • 测试结果、覆盖率和安全扫描报告应与具体 commit / 制品 digest 关联。

07 · CI/CD、制品与 GitOps 交付（关键事实已核验）

实测事实（.github/workflows/ 与 AGENTS.md）：
  • workflow 清单：backend.yml、frontend.yml、service-ci.yml、context-gate.yml、deploy-consistency.yml、supply-chain-pr.yml、frontend-release.yml、edgeone-pages.yml / edgeone-pages-consumer-next.yml、registry-bench.yml。
  • 区分门禁与发布：push/MR 有轻量/代码门禁；发布镜像才由裸 semver tag X.Y.Z 推到 github 触发。「全部 CI 只由 tag 触发」是已漂移的旧说法。
  • verify-context.sh（context-gate）是 main 上唯一必需的 CI 检查（GitHub + GitLab 同名 job）。
  • 部署清单两份真相源：helm/（values.yaml = pre 基线 + values-prod.yaml）与 kustomize 裸 manifest（deploy/{base,overlays/prod}），scripts/verify-deploy-parity.sh 强制逐字段等价。
  • 网关与配置控制面在同级仓 control-tower（services/gateway + services/config），不在本仓。

7.1 推荐交付流水线

Pull Request
  → 变更范围识别
  → 格式 / lint / 类型 / 静态检查
  → 单元测试 / 契约检查 / 结构门禁
  → 构建与依赖安全检查
  → 合并到受保护分支
  → 按受控版本规则构建不可变制品
  → 生成 SBOM / 漏洞报告 / 签名与证明
  → 推送制品仓库
  → 更新 GitOps 期望状态
  → ArgoCD 同步
  → 部署后健康检查与冒烟测试
  → 观察、回滚或完成发布

这是建议的目标流程。公开资料显示部分组件已存在，但业务 GitOps 归属和发布闭环仍需核验，不能视为已完整实现。

7.2 CI 与 CD 的职责边界

  • CI 负责验证源码、构建不可变制品、生成元数据和证明；CD 负责将已验证制品推进到环境。
  • 镜像使用不可变 tag 或 digest；生产部署应可追溯到源码 commit、构建工作流、SBOM 和签名结果。
  • GitOps 仓库中的期望状态应由受控自动化更新；禁止 CI 成功后绕过审查直接在集群中手工修改资源并把它当作长期状态。
  • ArgoCD 的 Synced / Healthy 只说明相应 Application 的同步 / 健康状态，不代表所有业务服务已被纳管，也不等于业务 E2E 成功。
  • 回滚应恢复已知可用的版本或声明式配置；数据库变更需要独立的兼容与恢复计划。

7.3 供应链安全

  • 固定依赖版本并通过 Renovate 等自动化工具提出可审查的更新。
  • 构建时生成 SBOM，并按策略执行漏洞扫描；明确严重级别、豁免审批和到期时间。
  • 制品签名应验证签名身份、来源工作流和制品 digest；只检查“签名存在”不足以建立信任。
  • 发布凭据使用最小权限、短期凭据或 OIDC（若平台支持），禁止将长期密钥写入仓库。
  • 验证 workflow 权限、第三方 Action 版本固定、分支保护、环境审批与发布权限。

阶段证据失败处理

08 · 安全工程规范

8.1 身份认证与授权

  • 认证回答“是谁”，授权回答“能做什么”；前端路由守卫不能代替后端授权。
  • 网关可集中处理会话验证、入口路由与可信身份传递，但业务服务仍须验证其领域数据所有权和关键业务权限。
  • 可信身份头必须由受信任入口清理并重建；服务端不得盲信外部客户端提供的用户 ID、角色或租户头。
  • 资源授权必须考虑对象级访问、商家租户隔离、管理员权限和跨租户越权场景。
  • 认证体系存在迁移路径时，文档必须写清当前机制、目标机制、兼容范围、移除条件和验证计划。

8.2 数据与密钥

  • 敏感配置不得提交到 Git；示例文件只能包含占位符或明确无效的示例值。
  • 生产凭据使用 Secret 管理方案，限制读取主体并定期轮换；日志和错误报告禁止泄露凭据。
  • 按最小权限配置服务账号、数据库角色、CI token 和云端角色。
  • 支付、个人信息、会话和订单数据应按业务必要性最小化收集、传输与保留。
  • 备份加密并定期演练恢复；“备份任务成功”不等于“数据可恢复”。

8.3 网络与运行时

  • 入口、服务间和数据层访问按最小权限开放；默认拒绝策略需有可验证的允许规则与故障排查方法。
  • 网络策略应验证实际 Pod 标签、端口、身份和依赖关系；不能只凭策略资源存在就认定隔离有效。
  • 对外 API 设置合理的请求体限制、超时、速率限制和滥用防护；写操作重试与限流要考虑幂等性。
  • 容器使用非 root、最小基础镜像、只读文件系统（兼容时）和受限 capabilities；例外必须说明原因。

8.4 安全验收

  • 检查仓库无真实凭据、私钥和生产配置泄漏。
  • 验证未认证请求、越权请求和跨商家访问均按预期拒绝。
  • 验证镜像来源、签名和漏洞策略在发布链路中真实阻断违规制品。
  • 验证服务间网络策略既允许必需流量，也拒绝非授权流量。
  • 验证备份恢复、凭据轮换和应急访问流程有可执行记录。

09 · 可观测性、运行与容量验证

9.1 三大信号

  • 日志：结构化、带请求关联 ID；避免输出敏感数据；明确保留和采样策略。
  • 指标：关注请求量、错误率、延迟分位数、资源饱和度、队列积压和业务关键指标；控制标签基数。
  • 链路：跨网关与微服务传播 trace context；为关键依赖调用记录耗时与错误，采样策略需兼顾成本和排障价值。

9.2 告警与故障响应

  • 告警应关联用户影响、严重级别、仪表盘、排查手册和责任边界。
  • 告警通知必须验证端到端送达；规则存在或 Alertmanager 健康不等于通知闭环完成。
  • 发布后观察错误率、延迟、资源与关键业务指标；达到回滚阈值时执行预先定义的回滚程序。
  • 故障复盘记录触发条件、影响、检测时间、恢复时间、根因证据和可验证的改进任务。

9.3 容量声明边界

不得仅凭 Kubernetes、微服务或缓存等技术选型宣称系统可支持百万 / 千万级用户或请求。容量结论必须绑定固定数据集、压测脚本、资源配额、延迟与错误率、瓶颈分析和故障恢复证据。
