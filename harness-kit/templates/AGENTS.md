## 硬规则（不可跳过）

1. **以真相源为准**：规范看 `context/`（入口 `context/INDEX.md`）。现搜、推测、记忆与之冲突时以真相源为准；
   **找不到对应知识 ≠ 没有约束**，先读 `TODO.md`，结论沉淀回 `context/`。
2. **不可逆动作需要用户授权——但授权一旦给出就直接执行，不要二次确认**。
   哪些算：`git commit`、`git push`、分支/MR 合入、部署、发布制品、仓库之外的写入与删除。
   用户这轮明确要求做这件事，或明确放宽后续同类动作，就算授权；**此时直接做**，不要复述风险再问一遍。
   「帮我实现 X」「修好这个 bug」不构成授权；授权不跨范围升级（apply 到 dev ≠ apply 到 prod，commit ≠ push）。
   仍需先说明再做的例外：用户没要求、且会丢数据或影响线上的动作。
   subagent 永久不得执行其中任何一项：它拿不到用户的授权上下文。
3. **不要把凭据写进仓库**。密码/密钥只存在凭据服务与本地环境，仓库里只写主机名和端口。
4. **踩到坑要沉淀**：区分「模式性教训」与「一次性 diff」，前者写进 `context/`。
   改动 harness 本身（本文件的硬规则、门禁脚本、CI 门禁）时，**在改动处写清触发它的具体事故**——
   规则能从代码读出来，理由不能，没理由的规则半年后会被凭据直觉改回去。
5. **解决问题优先，不要为了堆工作量去写测试**。唯一正当理由是「能验证这次改动」或「能挡住这个 bug 复现」。
   优先跑既有验证；交付时如实说明测了什么、没测什么，不用测试数量替代「问题是否解决」。
6. **全自动模式不询问权限，但仍询问实质性选择**：有 `Full Auto` 标记时直接执行，不拿权限确认打断；
   多个都合理、会实质改变结果的互斥选项仍用交互式选择。

## 门禁

```bash
harness/bin/harness check        # 全量：链接/路径/frontmatter/索引/预算/进度源/文档责任/敏感数据
harness/bin/harness check fast   # 快检集合（pre-commit 用）
harness/bin/harness canary       # 门禁的门禁：证明每项检查真的会红
```

门禁的判据是「它红过吗」，不是「脚本在不在」。新增/修改检查后必须补 canary 探针，
否则 canary 的元断言会红。每项检查验什么、怎么放宽，见 `harness/README.md`。

## 反直觉约定

> 技术栈、目录结构不在这里复述——读代码自明。

- 进度真相源：`TODO.md`（**唯一**）——其他文档出现任务复选框会被 `PROGRESS-SRC` 拦下；
  示例请放进代码围栏。
- **环境按需查询，文档只留契约与查法**：目标、代码、运行观测分开；故障证据不能当稳态基线。
  版本号与「装没装」不写进文档，写查法（`command -v`、`go version`）。
- 门禁的扫描范围由 `harness.config.sh` 决定；新增目录要显式加进 `HARNESS_DOC_ROOTS`，否则等于没接门禁。
