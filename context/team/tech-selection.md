# 技术选型：上游状态类结论的盘点纪律

> **触发事故（2026-08-20，Silo）**：技术雷达 §10.6 以「MinIO 上游归档、无人修 CVE、风险已兑现」定稿
> MinIO→SeaweedFS 迁移，三轮异构对抗评审无一方发现：集群 node2 实跑镜像 `pgsty/minio`
> 正是社区延续分叉 Silo（`pgsty/silo`）的前身——分叉当时已存在 10 个月、专门回补上游停发的
> CVE 修复、发布了 drop-in 迁移文档。复审记录见 [docs/TECH-RADAR.md](../../docs/TECH-RADAR.md) §10 复审附记。

**症状**：选型文档写着「上游已归档 / 无人维护 / 无人修 CVE」，但集群里实跑的镜像来自非官方
namespace（`pgsty/minio` 而非 `minio/minio`）——「无人修」与部署现实自相矛盾，评审过程没有发现。
主论据被削弱，近零成本的止血选项（同谱系镜像切换回修复线）被整体漏掉。

**关键陷阱：「上游死了」是一个让人停止调查的结论**。拿到它就归档议题，不会再问
「死了之后生态怎么回应」；同时盘点习惯只记「什么软件、什么版本」，把镜像来源当成部署细节。
两个习惯叠加，恰好把「自己已经跑在延续分叉上」这种自证信息挡在视野外——线索一直躺在
compose 文件和 `.service-matrix.yaml` 里。

**根因**：现状盘点缺一个必答项——「跑的是谁的 build」。非官方 namespace 本身就是最强线索：
说明有人在维护一条非官方发行线，而且你已经在依赖它。

**修复**：[docs/TECH-RADAR.md](../../docs/TECH-RADAR.md) §10 复审附记（2026-08-20）：论据降级、
Silo 收编 🟡 备选位、存量止血项待拍板；本文件固化下述规则。

## 规则：定稿前必查三件套

凡选型结论依赖「上游归档 / 停更 / 换许可证 / 被收购」这类上游状态判断，定稿前必查，缺一不得定稿：

1. **跑的是谁的 build**：`docker inspect` / compose / helm values 里的镜像
   registry + namespace + tag（@digest）。与官方 namespace 不一致时必须解释来历。
2. **该 namespace 的组织现状**：是谁在维护、还发不发版、发版里有没有安全修复（GitHub API
   实测 stars / 推送时间 / release，不凭印象）。
3. **社区回应**：搜 `<project> fork maintained / successor`。上游死亡后 3–12 个月是延续分叉
   出现的典型窗口；评审日期离上游死亡越近，越要主动搜。

## 边界：查到分叉 ≠ 采用分叉

延续分叉先回答两个问题再谈角色：延续型（保留原许可、回补修复）还是换证型；单厂商还是有
基金会/多方治理。年轻单厂商分叉不得承载灾备等「不做会出事」层；先进观察位，以持续维护时长
与 CVE 响应时效换信任（翻盘条件的写法参照 TECH-RADAR §10 复审附记）。
