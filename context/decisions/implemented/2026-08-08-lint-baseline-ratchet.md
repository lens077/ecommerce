# 决策：静态检查用基线棘轮，而不是"清完存量再开门禁"

## 问题

存量告警多 → 不敢把 lint 设成阻断门禁 → 告警继续涨，是个死结。`TODO.md` 长期挂着「CI 门禁未接入，48 条 warning 未清」，
卡了很久；2026-08-08 实测发现这 48 条早就清干净了（`vp lint` 与 `go vet` 均 0 告警），但因为没人敢确认，门禁一直没开——
**过期的债务记录本身就是阻塞**。更深一层：只要"这是历史问题"这句话由跑检查的人（或 AI）说了算，任何门禁都能被口头豁免。

## 决策

`scripts/lint-baseline.sh`（`check` / `snapshot` / `list` 三模式）：基线里的失败集合 A，当前失败集合 B，
**只有 B − A（新增）阻断**。基线按采集器分文件冻结在 `.lint-baseline/`：`go-vet.txt`、`revive-exported.txt`、
`vp-lint.txt`、`knip.txt`（`CHECKERS` 变量可只跑其中几个）。finding 归一化为「checker + 文件 + 规则 + 摘要」，
**丢掉行号列号**，否则文件顶部加一行注释就会让下方所有告警变成"新增"。

**反向棘轮**：基线条目被修好后 `check` 失败并要求刷新基线，防止基线只增不减、变成永久免罪符。
接线：`service-ci.yml` 每次 CI 跑 `check`；`backend/Makefile` 的 `lint-baseline` 目标前后端一起跑。
配套 `scripts/harness-scars.sh` 把三处放行集中显形（接在 `deploy-consistency.yml`、`make deploy`、`make deploy-status`），
让"软门禁"留下的伤疤有个面板，而不是散在各处静默。

采集器与上游输出格式耦合，格式一变就恒绿（解析 0 条 ≠ 0 条告警）——`vp lint` 改 miette 画框后 vp-lint 采集器
静默失效过一次（2026-08-26 注错红测才暴露）；因此 `run_vp-lint` 带「汇总行报 N 条 vs 解析 0 条」的失聪自检，
脱钩时产出 `PARSE-FAILURE` 哨兵行强制变红。**改采集器后必须注错复测**（注入 `debugger` → rc=1，还原 → rc=0）。

## 考虑过的替代方案

- **先清完存量再开硬门禁** — 就是那个死结：清存量没有截止时机，门禁永远"下次再开"；而且实测存量早已为零，
  阻塞的是过期记录而非告警。
- **门禁只报不拦（软门禁）** — "这是历史问题"的口头豁免仍然成立，且软门禁的放行会散落各处；
  棘轮把"是不是历史问题"的裁决权交给基线文件，`harness-scars.sh` 再把剩余的软放行集中显形。
- **基线带行号** — 更精确，但任何上方改动都让下方告警整体变"新增"，基线一天就失效；丢行号是刻意的。
- **基线只增不减** — 会慢慢变成永久免罪符；反向棘轮强制"修好就刷"，基线才是当前存量的真实快照。

## 后果

- 新增告警在 CI 阻断；存量告警可见（`list`）但不阻断，修一条就得刷一次基线（`snapshot` 后 `git diff` 逐条确认）。
- 采集器是脆弱点：上游格式变更会让棘轮恒绿，必须靠失聪自检 + 注错复测守住；这项成本换来的是不用等存量清零就能开门禁。
- 四态验证钉住行为：注入 `debugger`/`eval` → 阻断（exit 1）；`snapshot` 冻结 → 放行但打印伤疤；
  删掉问题不刷基线 → 反向棘轮报错（exit 1）；刷新基线 → 全绿。
