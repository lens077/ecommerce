# 决策：文档契约与运行观测分离

## 问题

2026-09-26 复核发现：`local-env.md` 同时写公网 OTLP 未接线和已接线；`live-facts.md` 与 runbook 仍宣称已删除的 `[LIVE-FACT]` 门禁生效；`TODO.md` 写业务命名空间为空，但只读查询返回业务 Deployment；`TECH.md` 将观测存储外置目标写成现状。过期的不只是日期，也包括文档自己的权威声明。

现有链接、路径、代码摘录门禁只能证明各自的机械条件。`affects:` 已能查影响，但不会阻断未评估的代码变更。给全文刷新日期、强迫每个代码提交随便改一份 Markdown，都不能证明语义一致，反而鼓励制造无意义文档。

参考上游 Harness 的生成区精确检查、配置来源窄规则与固定 base/head 的变更范围工具；前两类检查已接入上游 doc-sync 链，变更范围工具本身不判断文档是否同步。本仓采用这些原则，不引入上游依赖或照搬整套检查。

## 决策

- TECH 保存目标、约束和验收边界；TODO 只留缺口。环境手册保存选择方法、来源、查法和踩坑，不维护节点/VIP/版本/组件安装数量的第二份清单。
- 本机工具要求从 `backend/go.mod` 与 `frontend/package.json` 生成到环境手册的唯一受管块；离线 `--check` 精确比较。
- 环境查询默认只看本机；集群、GitOps、观测和路由按显式分区查询，固定 context、设置超时、只输出白名单字段。未知不是不存在；一次 Ready 不是长期健康。不自动缓存、不写仓库。
- 复用 frontmatter `affects:`，仅 `doc-sync: required` 的文档参与差异阻断。比较工作树、暂存区或固定 base/head；相关文档要有非空白、非注释正文变化，或代码提交为准确文档写 `Doc-Impact: none <文档路径> | <具体理由>`。
- required 文档的旧、新映射共同检查，不能删元数据规避同次变更。生成区仍须精确一致，理由不能豁免生成校验。CI 不读取开发凭据、不连接集群、不依赖同级仓。

## 考虑过的替代方案

- **每个代码提交必须改任意 Markdown**：无关文档或改日期即可过；本仓允许代码与对应文档在同一推送中分组提交，逐提交强制配对会破坏现有工作流。
- **恢复 `[LIVE-FACT]` 日期正则并归档全部快照**：只证明写了日期，不证明事实正确；旧机制已因推动文档膨胀被删除，不恢复。
- **CI 连全部环境并持续重写文档**：凭据、网络、权限和集群故障会污染确定性门禁，还会把故障态固化为稳态。
- **全量语义索引或每次双模型审查**：对已知的版本、路径、来源漂移成本过高，且不能替代真实环境验收。复杂语义保留给变更审查。

## 后果

- 配套测试覆盖工具缺失、超时、非零退出、空成功、畸形响应、白名单脱敏、生成区漂移与文档责任变更。
- 文档责任检查用隔离 Git 历史验证代码独改、无关文档、空白/注释变化被拒；准确文档或理由放行；未暂存文档不能替暂存代码放行；旧理由不能覆盖后续代码提交。
- 既有 `verify-context` 与 canary 保持原强度；生成器异常退出也须变红。新检查接入 commit-msg 和双远端轻门禁，运行态不进入 CI。接线不等于远端已执行或分支保护已配置。
- 首批 required 文档为 TECH、local-env、live-facts；并非全仓覆盖。手写正文变化与理由仍需审查，门禁不保证自然语言语义零漂移。
- 路径检查仍按 Git 索引判定：新增引用与文件应一起暂存。不以放宽路径门禁处理未暂存工作，验证时可用独立索引，不修改用户索引。
- 运行查询不自动缓存，避免维护 TTL、缓存失效与第二份状态文件；同一任务可复用结果，但安全条件或环境变化后必须现查。
