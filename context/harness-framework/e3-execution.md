# E3 执行策略：任务多大，就花多大功夫

`AGENTS.md` 的「执行策略」与「消费边界」两节是常驻精简版；本文是它们的完整解释、
与本仓机制的对接、以及护栏 hook 的配置与再验证方法。E3 管「读多少」，
下文「消费边界」节管「花多少」，两者互补。

## 出处

arXiv:2607.13034《Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware
Reasoning and Execution》（Yin & Feng，2026-07，代码已开源）。论文把 agent 的
「先读全仓求稳」量化为 ACRR（实际成本相对最小充分轨迹的冗余比），关键实测结论：

- 冗余在**最简单的任务上最严重**：模拟基准里 max-context-first 策略在单文件小改上
  的 ACRR 是 22 倍，在仓库级重构上反而只有 5 倍。
- E3 与最强基线同为 100% 成功，但省 85% 成本 / 91% token / 92% 被读文件；
  换成故意打破估计器关键词的措辞后成功率仍 100%，成本只涨 8.7%——效率来自
  「乐观起步 + 验证兜底」这个**架构**，不依赖估计有多准。
- 真模型（gpt-4o 编辑真实库）上收益温和得多（比 ReAct 省 4% token、比
  「be thorough」提示省 18%），但**反面结论最硬**：被指示「先读全部再动手」的
  agent 在最难任务上三跑全败（步数耗尽 / 改错 / 撞限流）。过度阅读不只是慢，
  会把自己读进失败里。
- 论文里 E3 在真模型上就是 12 行 system prompt（`llm_case/prompts.py`），无需代码。

## 策略三步

1. **Estimate**：动手前一步估计任务规模并明确说出来。最多一次廉价探测——
   本仓查拓扑**必须**用 `.service-matrix.yaml` 而不是 grep（既有硬约束，恰好也是
   最便宜的探测）；查规范走 `context/` 索引。规模分三档：
   - **L1** 单文件局部修改；
   - **L2** 少数文件的跨文件修改；
   - **L3** 仓库级重构——警惕 grep 看不到的间接引用点：re-export、别名、
     网关 `discovery:///<name>` 接线、Config Center 键、helm values 这类配置耦合。
2. **Execute**：只读预计要改的文件，不为局部修改通读代码库。改完立即跑
   「命令与验收锚点」里**最便宜的适用命令**（改前端 → `pnpm ready`，改后端 →
   `go build ./... && go vet ./...`，动 matrix → structcheck）。
3. **Expand**：只有验证变红才扩大范围，一次扩一级（再 grep → 追依赖/import →
   读下一个最相关文件），复用已有发现，不推倒重来。措辞听起来局部但探测命中
   多处时，主动降置信、直接按高一级处理——这是论文估计器防翻车的关键规则。

**E3 不豁免硬规则**：runbook §0.1 按改动类型的必读路由、proto 前先读设计文档，
都属于「最小路径」的一部分，不是可以省掉的上下文。

## 按规模路由开销（E3 与 effort/model 路由正交，可组合）

| 估计 | plan mode | 子代理 | reasoning effort（Codex: `model_reasoning_effort`） |
|---|---|---|---|
| L1 | 不开 | 不派 | low |
| L2 | 不开 | 不派 | medium |
| L3 | 值得开 | 值得派 Explore/并行审查 | high |

判据同源：估计既然已经做了，就顺手驱动这些开关，不要 L1 任务开满配。

## 过度阅读护栏 hook（仅 Claude Code）

实测 2026-09-08：原脚本未在已检查的 Claude 目录、备份和相关 Git 历史中找到，已按本文记载的行为重建并接入 Claude 全局配置，不宣称恢复了原件。源码保存在仓库，用户目录只保留 symlink，避免重装后再次丢失。完整依赖状态见 [工具清单](../../docs/agents/skills.md)。

- **源码**：[scripts/e3-overread-guard.py](../../scripts/e3-overread-guard.py)；`~/.claude/hooks/e3-overread-guard.py` 链接到它。
- **接线**：`~/.claude/settings.json` → `hooks.PreToolUse`，matcher `Read|Edit|Write|MultiEdit|NotebookEdit`；命令为 `/usr/bin/python3 /Users/lens/.claude/hooks/e3-overread-guard.py`，timeout 为 5 秒。原有模型配置、插件和 TokenTracker Hook 保留；接线前已在 `~/.claude/backups/` 备份设置。
- **行为**：同一会话在首次编辑调用前，完整 Read 第 6 个不同文件时拦下该次 Read（exit 2），重发即放行，每会话最多提醒一次。带 limit 或非首页 offset 的读取不计数，相对路径按 Hook cwd 规范化去重。
- **编辑边界**：PreToolUse 只能看到编辑意图，不能确认修改成功；任一匹配的编辑调用到达护栏后，本会话后续不再提醒。它不代替审批、沙箱或项目必读规范。
- **状态与故障**：状态位于 Python `tempfile.gettempdir()` 下的 `e3-guard-<SHA256(session_id)>.json`，权限 0600；文件锁保护并发读写，不跟随符号链接。输入损坏、状态损坏或不可写时在 stderr 报诊断并放行，不把辅助提醒变成永久阻塞。
- **适用范围**：同一 session_id 的读取共享计数；不同 session_id 隔离。纯研究和子代理探索可能合理地需要更多上下文，提醒明确允许重试。这次只接入 Claude，未向 DSH 或 Codex 注册此 Hook；两者仍可读取 AGENTS.md 的 E3 文本规则。
- **验证**：9 个独立回归测试通过，覆盖阈值、重试、局部读取、四种编辑工具、会话隔离、并发、坏输入/状态和符号链接。通过全局配置中的真实命令，用隔离的临时 session 得到退出码 `0,0,0,0,0,2,0`；没有启动付费模型会话。新建 Claude 会话后再确认 Hook 生效。
- **再验证方法**（改完 hook 必须重跑，见「静默失效要实测」的教训）：
  ```bash
  SID="test-$$"
  for i in 1 2 3 4 5 6; do
    echo '{"session_id":"'$SID'","tool_name":"Read","tool_input":{"file_path":"/f'$i'"}}' \
      | python3 ~/.claude/hooks/e3-overread-guard.py; echo "file$i -> exit $?"
  done
  # 期望：file1..5 -> exit 0；file6 -> exit 2 且 stderr 有提醒
  # 再验证编辑后静默：先喂一条 tool_name=Edit，再喂新 Read，应 exit 0
  ```

## 预期管理（防止半年后有人把这套删掉或加码）

- 别指望论文标题的 85%：那是对机械最坏基线的数字。真模型实测收益是个位数到
  两成 token，主要落在大仓库与深耦合任务上。这套东西的价值一半在省，
  一半在**防**——防「求稳式通读」在难任务上把步数和限流预算烧光。
- 反过来也别加码：**不要**在任何指令文件里写「先通读代码库」「be thorough」
  「read everything first」这类措辞，论文实测它们又慢又更容易失败。
- Expand 依赖便宜的验证器。锚点命令跑不了的环境里（比如裸机脚本仓库），
  E3 退化成 Estimate-only，此时宁可估保守一级。

## 消费边界：Agent token 成本治理

### 触发事故

产品同学体验 DeepSeek Harness 时，让 Agent 分析「如何做一个 DSH 插件」，输入只有几十个
token，模型是 GPT-5.6 Sol。不到 5 分钟，花掉 1000 元。展开执行链路：

- 输入约 1964 万 token，输出约 13 万 token；
- 启动了 12 个 subagent，存在重复检索、上下文被反复整份携带；
- 用量记录里 `cacheReadTokens` 每一次都是 0——缓存完全没生效，用户全程无感知。

技术原因（为什么 12 个 subagent、为什么缓存失效）各有各的修法，不是本节主题。本节记录
的是它暴露的产品事实：**用户只提了一次需求，Agent 在后台自主完成了数百次付费决策，
用户既看不见，也没有机会在成本迅速扩大时再次确认。**

### 两层授权

Agent 的自主性包含两层授权，市面上多数产品认真设计了第一层，第二层还没当一等公民：

| 授权 | 允许它做什么 | 本仓已有机制 |
|---|---|---|
| 执行授权 | 读文件、调工具、改代码、拆任务 | 硬规则 6（不可逆动作）、硬规则 7（全自动模式）、沙箱与审批 |
| 消费授权 | 调用多少次模型、启动多少代理、运行多久、花多少钱 | 此前只有 E3「L1/L2 不派子代理」一条侧面约束 |

用户同意 Agent「完成这个任务」，不等于给了一张没有上限的空白支票。传统聊天产品一问一答，
用户对成本规模有直觉；Agent 产品用户看到的是一个任务，系统跑的是一张动态生成的执行图——
深度、分支数、每步用什么模型、携带多少上下文都不由用户决定，却共同决定账单。

### 六环节闭环

一个完整的 Agent 成本闭环至少围绕六个环节。每个环节分两栏：**产品侧**是 harness /
GUI 应提供的机制（DSH 尚未实现，属于设计输入）；**agent 侧**是本仓 agent 现在就能靠
自律做到的，已浓缩进 `AGENTS.md`「消费边界」节。

#### 1. 事前控制：先让用户决定上限

回答的不是「这次大概多少钱」，而是「无论任务后来多复杂，最多允许花多少」。模型只决定
单次调用单价，不决定调用次数；同一模型调 3 次和 265 次、一个 Agent 自己做和递归起
12 个 subagent，不是一个量级。

- **产品侧**：在「用哪个模型」之外允许设置单次任务最高金额、最长运行时间 / 最大轮数、
  最多 subagent 数、是否允许自动切换到更贵的模型、到达阈值后是提醒 / 暂停 / 直接停止。
  这些是工程参数，不该直接扔给普通用户；更自然的方式可能是几档预设（保守 / 标准 /
  放开），具体档位要 A/B 才知道——这一点尚未想清楚，也未实操。
- **agent 侧**：派 subagent 前先说出数量和理由；单轮超过 3 个、或子代理再派子代理，
  先问用户。L1/L2 任务不派子代理这条从 E3 继承，现在是消费边界的一部分，不再是建议。

#### 2. 提前感知：开始前尽量说「可能会花多少」

执行路径动态变化，不可能精确报价，但「不可能精确」和「什么都不说」之间有很大空间。
低置信度的估算也比没有强，样本多了会越来越准。

- **产品侧**：先做一次低成本的任务分类（简单问答 / 只读调研 / 方案设计 / 代码修改 /
  新功能开发 / 全仓重构），结合同类任务历史 P50 / P90、当前模型价格、仓库规模和预计执行
  策略，给出费用区间。**展示金额、时间和风险，不展示 token**——token 不是钱，用户感知
  不到。同时列出主要成本因素：模型单价高、上下文大、预计多轮工具调用、任务会拆成多个
  子任务。冷启动阶段直接说「低置信度估算，明显偏离会主动告警并暂停询问」。运行后的重新
  估算可以改「预计最终费用」，**不能自动改用户设的上限**。
- **agent 侧**：E3 的规模估计（L1/L2/L3）就是最粗的任务分类，估计时顺带说一句预计会
  读几个文件、是否需要子代理。

#### 3. 过程可见：不该只看到一个旋转的「正在思考」

至少回答四个问题：已经花了多少、离上限还有多少、Agent 当前在做什么、按当前速度最终可能
花多少。例如：

```
已使用：¥4.20 / 上限 ¥10
当前阶段：检索代码结构
运行中 Agent：主 Agent 1 个，subagent 2 个
当前预估总费用：约 ¥6～¥8
费用高于同类任务中位数，主要因为检索结果较大
```

- **产品侧**：渐进式披露——默认展示金额、时间、阶段、风险；专业用户展开看每个 Agent 的
  消耗、模型与调用次数、输入 / 输出 / 推理 token、缓存读写、工具返回体积、重试和重复探索。
  费用曲线突然变陡时，不能只把 ¥2 刷新成 ¥8，要把执行变化和费用变化连起来：新起了
  subagent、检索范围从单目录扩到全仓、工具返回超预期、上下文增长过快、多次失败重试、切到
  更贵模型。
- **agent 侧**：每次扩张动作在回复里说一句，不静默。扩张包括：新派 subagent、检索范围从
  目录扩到全仓、切更贵模型、同一步第 2 次重试。

#### 4. 主动告警：Agent 知道过程，就该判断消耗是否合理

这是这次事故带来的最重要的一层思考。传统费用告警只看「超过固定金额」；Agent 系统掌握
大量过程信息——和上一轮比哪些内容没变、当前模型和价格、已起多少 subagent、工具返回
多少、是否在反复重试、每一步有没有拿到新信息——所以它不只能算「花了多少」，还能判断
「花得是否符合正常执行过程」。

**信号一：预估与实际明显偏离。** 持续比较实际花费是否已达预估数倍、消耗速度是否突然
变快、按当前速度是否即将突破预算。只读调研通常 10～20 次 LLM 请求，已经跑了 80 次还没
进入汇总阶段，本身就是告警信号。

**信号二：Cache 命中不符合预期。** 系统能看到最终发给模型的输入，也能估算其中多少是与
上一轮相同的稳定前缀：

```
预期 Cache 命中比例 ≈ 可复用稳定前缀 token / 本次输入 token
```

这次事故正是每轮零命中——按输入结构约 80% 是可复用前缀，服务端却连续返回 0%。可能
原因：提示词结构意外变化、历史上下文被重写、Cache 没正确开启、网关或 SDK 没完整透传
usage、当前渠道不支持缓存。当时若对这个偏差告警，事故不会发生；而且这件事在产品发布前
测试就能完全测出来。两个前提：已确认模型和渠道支持 Cache 且已开启；用量遥测可信，能
区分 Cache 读取、写入和普通输入。否则 `cacheReadTokens = 0` 只是待排查的遥测信号，
**不能凭一次 0 值就停任务**。

- **产品侧**：在 usage 管道上做这两类信号的连续比较，异常时说明原因并暂停询问。
- **agent 侧**：以下任一出现即停下报告，不自行继续——请求数超出同类任务经验上限（只读
  调研 >20 次仍未汇总）、能看到 usage 时连续两轮 `cacheReadTokens=0` 而输入含大段稳定
  前缀、同一检索重复执行、上下文被整份重复携带。「连续两轮」是为了避开单次 0 值的误判。

#### 5. 随时可控：用户能停，也能改执行方式

告警的价值不只是让用户知道出事了，还要能立即采取行动。运行中的 Agent 至少允许：暂停、
立即停止、查看已完成结果、缩小任务或检索范围、禁止继续创建 subagent、切到更经济的模型、
追加一档固定金额或时间、保存状态稍后继续。三条设想：

- **「继续」不等于永久解除限制。** 用户在告警里选继续，产品要明确告诉他增加的是什么——
  再加 ¥5、再跑 10 分钟、再允许 20 次请求。一次继续只进入下一档边界，不能让任务从此
  无限运行。实现起来可能比较困难。
- **停止之后不再产生新消耗。** 第一原则是立即停掉所有模型请求、工具调用和 subagent
  派发；系统不能为了「收尾」又默认起一轮模型调用。见过 Codex 主 Agent 停了、subagent
  还在跑的情况。
- **结果可见。** 已完成的子任务结果、代码改动、已确认的事实与证据、可恢复的检查点，都
  应在运行过程中持续记录；停止后只读取并展示现有状态，不再产生新的模型费用。
- **agent 侧**：用户说停就停，包括已派出的 subagent（`interrupt_agent` / `job_kill`）；
  停后不为「收尾」再起新调用，直接报告已有结果。

#### 6. 账单可解释：「小票」要清晰具体

任务完成、中止或到达上限后，不只给一个总金额。用户需要知道：实际花了多少、开始前预计
多少、钱主要花在哪些阶段、为什么高于或低于预期、起了多少 Agent、是否重试或升级模型、
完成了什么还有什么没完成。例如：

```
本次任务总费用：¥7.42（预计 ¥2～¥5）
LLM 请求：43 次
token：总量 / 缓存命中 各多少
Agent：主 Agent 1 个，subagent 2 个
主要消耗：代码检索 46%、方案生成 31%、结果校验 18%
高于预估的原因：检索范围扩大、发生两次失败重试
当前结果：方案已完成，兼容性验证尚未完成
```

普通用户看金额、原因和结果；专业用户展开 token、模型、Cache 和每个 Agent 的明细。
小票不只服务用户，也服务下一次预估：每次任务的真实数据反过来建立各任务类型的
P50/P90/P99、各模型的单位任务成本、预估与实际的偏差、哪些步骤最容易异常消耗、哪些告警
真的省了钱。账单可解释既是事后审计，也是下一次「提前感知」的输入。

- **agent 侧**：任务结束按能看到的 usage 报请求数、总 / 缓存 token、subagent 数、超预期
  的原因、完成与未完成。看不到 usage 就如实说看不到，不编数字。

### 回到案例：如果当时有这六个环节

用户选执行模式并设单次上限（事前控制）→ 系统展示同类任务费用区间和潜在风险（提前
感知）→ 用户看到已用金额、运行中 Agent 数量和最新预估（过程可见）→ subagent 快速增加、
上下文持续膨胀或 Cache 命中与预期明显不符时，系统主动说明异常（主动告警）→ 用户查看当前
结果、停止、缩小范围或追加一档预算（随时可控）→ 无论完成还是停止，都拿到已有结果和一张
成本小票（账单可解释）。

这套机制不保证每个任务都便宜，也不该阻止用户在高价值任务上主动多花钱。重要的是：即使
用户愿意花 1000 元，也应该是在知道为什么、看见过程并明确同意之后，而不是 5 分钟后才从
账单里发现。

### 预期管理

- 这不是一套验证过的最优标准答案，是一次事故后的产品层思考，六环节都还没实操过。
  产品侧设计落地时按实测调整，不要把本节当规格书。
- 用户不是来买 token 的，买的是结果和确定性。token 只是计费单价；用户关心的是最终按
  清晰透明的价格结算，就像买菜不关心单价小数点、关心小票对不对。
- 成本控制不是财务功能，也不只是 token 优化问题；它是一套产品权限设计，也是一份用户
  信任协议。第一次用你的 Agent 产品 5 分钟花了 1000 块的用户，大概率不会再用。
- agent 侧约定与产品侧机制的边界：agent 靠自律能做到「说出来、停下来、报出来」，做不到
  「算准了、拦住了」——后者必须靠 harness 在 usage 管道和调度层实现。不要因为 agent
  遵守了本节就以为成本问题解决了。
