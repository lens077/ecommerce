## 核心心智

把 AI 工作流拆成五个闭环，每个闭环是一个**隔离会话**，靠交接而不是靠共享上下文串联：

| Loop | 角色 | 关键约束 |
|---|---|---|
| 0 | 你（协调） | 只做放行/打回决策，不亲自干活 |
| 1 | 设计 + 设计评审 | **必须是两个隔离会话**——评审方不继承设计方的自我合理化 |
| 2 | 实现 | 只认锚点命令的退出码，不认自己的口头「没问题」 |
| 3 | 验收评审 | 又一个 fresh 会话，跨模型族互查（执行用 codex、审查用 claude） |
| 4 | 审计（每 N 轮） | 回看各 loop 记录：设计是否系统性出错、验收有没有放水 |

两条贯穿始终的原则：

- **异构是刻意的**：执行者与审查者用不同模型族，失败模式不同才能互查盲区。
- **审查者永远新开会话**，不要 resume 设计者的会话——一旦继承上下文，
  「loops watching loops」就退化成自己审自己。

分档使用：小改动 / 单功能根本不用多闭环，一个会话里 `/adversarial-review` +
`go test` 就够；只有核心模块、或要并行铺开多个功能闭环时才值得付协调开销。

## 三个必须盯死的陷阱

这三条与具体编排工具无关，是本文最值得留下的部分：

1. **别让「互发消息」替代锚点。** 一堆 agent 互相说「我这边 OK」是古德哈特的温床。
   放行的唯一依据是**命令真绿**和 `/adversarial-review` 的 CONFIRMED，
   不是任何 agent 的口头背书。消息传递只送信，不产生事实。
2. **验收门要靠机器判定，不靠编排工具。** 编排工具拦不住实现方去改验收标准；
   拦它的是一道独立的、机器可判定的检查。这根桩不立，整套失效。
   （当年的形态是冻结节点哈希校验，现已删除；原则仍成立。）
3. **入网 = 完全授信的安全面。** 多 agent 互联时，一个被 prompt-injection 的 peer
   能驱动/杀死别的 agent。只在自己这台机跑，别随便 relay 入网别的设备；
   跨机 token 当 SSH key 保管。
