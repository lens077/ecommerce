# 子代理派发约定

> E3 已回答「**何时**派子代理」（L3 才值得，见 [e3-execution.md](e3-execution.md)）。
> 本文回答「**怎么**派」。出处：腾讯技术工程《靠 10 个优化点把 Multi-Agent 工作流成本降
> 50%以上》（2026-08）的 3.1.3 / 3.2.2 节，对照本仓 2026-08-21 复盘后固化为三条硬约定。
> 成本模型一句话：主会话是**生命周期最长的 context**，进了主会话的每个字节都会在
> 后续每一轮被重复计费；子代理跑完即销毁，历史滚雪球在它那里被切断。

## 约定一：子代理只回结构化摘要，原始 payload 不回流主会话

- 探索/调研/读大文件类委派，返回值必须是**结论 + 关键引用（`file:line`）+ 不确定性**，
  不得把整段文件内容、全量测试输出、原始 API 响应贴回主会话。
- 需要跨 Agent 传递的完整材料**写成文件**（`docs/design/`、`.scratch/<slug>/`），
  主会话与下游只传路径——「上游收集一次，文档传递」，不要让每个 Agent 各自重新发现同一份信息。
- 对照数据：文章实测把 MCP 原始 payload 从主会话移入子代理后，单轮 input token -38.4%。

## 约定二：按角色裁剪能力

- 评审/探索类子代理**只读**：不给写文件与执行不可逆命令的任务描述，prompt 里明说
  「只输出发现，不做修改」。这同时是 AGENTS.md 硬规则 #6 的要求——subagent 永不执行不可逆动作。
- 不需要的外部工具面（MCP/浏览器/网络）不要带：能力面越窄，Schema 与无关上下文越少，
  行为也越可预测。派发 AgentTeams 成员时同理，角色描述限定其工具使用范围。

## 约定三：按角色分层模型

- 规则性强、推理要求低、**轮次多**的角色（格式审查、逐条核对、修复循环）用低成本模型路由；
  设计/架构/对抗评审保持主模型。轮次越多的角色，分层的收益被放大得越多（文章实测 -64%）。
- DSH 的 subagent/workflow/AgentTeams 均支持 provider/model 覆盖；只在**明确要求或本文
  这类既定约定**下使用覆盖，不要临场即兴换模型。

## 反模式（见到就纠正）

- ❌ 子代理把 300 行文件原文贴回来「供参考」——违反约定一，主会话从此每轮多付这 300 行。
- ❌ 为 L1/L2 任务派子代理「更保险」——违反 E3，多付一整份系统提示词还引入交接损耗。
- ❌ 两个无数据依赖的委派串行发起——应同一轮并行发起（少一轮就少一次历史重复打包）。
- ❌ 下游 Agent 重新加载上游已加载过的 Skill/知识——读上游写好的文档即可。
