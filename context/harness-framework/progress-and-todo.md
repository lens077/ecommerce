# PROGRESS.md 与 TODO.md 的分工

两份文档记的都是「进度」,但口径不同、读者不同,**不可互相替代,也不可只更新一份**。

## 分工

| | `TODO.md` | `PROGRESS.md` |
|---|---|---|
| 定位 | **进度真相源**:功能粒度的实现对照与待办 | 完成度**评估视图**:阶段规划、百分比、评估口径 |
| 粒度 | 每个 RPC / 每个缺口,附 `file:line` 证据 | 每个服务一行,给出完成度数字 |
| 冲突时 | **以它为准** | 是 TODO.md 的汇总,与之冲突说明它过期了 |
| 更新时机 | 每次改动、**提交前必须**(AGENTS.md 硬规则) | 每次改动同步;完成度数字变化时说明订正原因 |

## 硬性要求

1. **每次改动两份都要更新**。只更新 TODO.md 不更新 PROGRESS.md(或反过来)会让两份文档
   在下一次评估时对不上,读者无法判断该信哪份。
2. **声称「已完成」前先回扫代码**。「proto 已定义且 handler 已挂载」不等于「可用」——
   返回假成功或 panic 的方法按**未实现**计。这条口径写在 PROGRESS.md 表头,不得放宽。
3. **完成度只能按证据订正,且订正要留痕**。下调不代表功能倒退,而是此前数字虚高;
   订正依据逐条附 `file:line`。

## 为什么有第 2、3 条

2026-08-06 的对抗评审(`ADVERSARIAL_REVIEW_20260806.md`)发现 PROGRESS.md 多处
「已实现/已联调」与代码不符——`CreateOrder` 返回假成功而前端已接线、`Reserve` 静默无操作、
`ApproveApplication` 的 SQL 没有 WHERE——整体完成度虚高 9 个百分点。
根因是混用了「接口已挂载」和「调用会成功」两种口径。这两条规则就是那次教训的沉淀。
