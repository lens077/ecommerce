# Self-Refinement —— 让纠错变成资产

LLM 没有跨会话记忆。但**每一次用户纠正，都是一个信号**：说明 AI 的默认行为和本项目的真实约束之间有偏差。

不沉淀，下个会话、下个模型、下个人还会犯同一个错。

本文管**单次纠错**；单次看是偶发、放在一起才显形的慢变量（同一失效模式反复出现、
知识库方向漂移、门禁悄悄失效），由 [flywheel-audit.md](flywheel-audit.md) 的方向性审计兜底。
审计里的「Session 反传」还负责打捞**没被当场抓住**的教训——会话里讲过、
但第 ④ 步没发生的那类，只存在于 transcript 里（08-26 首轮实测即捞到一条）。

## 闭环

```
① 用户纠正了 AI 的某个做法
        ↓
② 判断：这是「模式性教训」还是「一次性 diff」？
        ↓ （模式性）
③ 按 knowledge-layering.md 判定该写哪一层
        ↓
④ 主动向用户提议沉淀，得到确认后写入 context/
        ↓
⑤ 下次同类场景，AI 从 context/ 读到并主动引用
   → 新会话 / 新模型 / 换 AI 工具都受益
```

第 ④ 步的**「主动提议」**很关键。AI 不应该等用户说"记一下"才记，而应该在识别到模式性教训时主动问：
「这条要沉淀到 `context/team/xxx.md` 吗？」

## 模式性 vs 一次性 —— 怎么判

| | 模式性教训（沉淀 ✅） | 一次性 diff（不沉淀 ❌） |
|---|---|---|
| 定义 | 下次遇到同类场景**还会重犯** | 这一次的具体改动 |
| 例 | 「MUI 的 sx spacing 会 ×8，要用 sp[] 字符串」 | 「把这个按钮的 padding 从 16 改成 8」 |
| 例 | 「JWT 校验要留 leeway，否则时钟偏移导致死循环」 | 「把 leeway 从 60s 调到 90s」 |
| 例 | 「proto 字段必须推断校验范围」 | 「这个 max_len 应该是 128 不是 64」 |
| 检验 | 能写成一句**普适的规则** | 只能描述成**这一处的修改** |

**一个实用的自检**：如果这条知识只能写成「把 X 改成 Y」，那是一次性 diff；
如果能写成「凡是遇到 A 场景，就要 B」，那是模式性教训。

## 沉淀时的纪律

1. **先查重** —— 已有文件覆盖了就更新那个文件，不要新建重复的
2. **写清楚 Why** —— 只写「要这么做」，下次遇到边界情况时无法判断能否变通
3. **记下关键陷阱** —— 尤其是「第一直觉会指向哪个错误方向」
4. **发现旧知识是错的就删掉** —— 过期的知识比没有知识更危险
5. **不写凭据**

## 已知的失效模式

- **知识库膨胀**：什么都沉淀 → 检索成本上升 → 没人（和没有 AI）看 → 等于没有。
  严格执行模式性判断，宁缺毋滥。
- **口径漂移**：同一约束在两处、逐渐分叉。只写一处，其余用链接。
- **文档腐化**：代码改了知识没改。沉淀的知识要引用**稳定的东西**（约束、原理），
  少引用**易变的东西**（行号、具体数值）。其中「链接失效 / 文件没进 INDEX / 格式漂移」
  这几个**能机械判定的子类**已由 `scripts/verify-context.sh` 兜底（CI 每次 push 都跑）；
  内容层面的过期仍然只能靠人和 AI 在读到时修。

## 教训存档

沉淀到这一层的**复盘长文**放这里——判据是「它讲的是 AI 协作机制本身怎么失效的」，
而不是某条具体规则该怎么写。典型形态：某个门禁/钩子长期静默失效、某类知识长期没人读、
某个约定被反复凭直觉改回去。

放这里而不是放规则文件里，是因为规则文件要保持可扫读；复盘的价值在**过程与误判路径**，
篇幅天然更长，混进规则正文会稀释规则本身。写法沿用 experience 的四段
（症状 / 关键陷阱 / 根因 / 修复），但不受 `verify-context.sh` 的 experience 格式门禁管辖
（那条只扫 `*/experience/*.md`）。

改的是 harness 硬规则、门禁脚本或 CI 门禁本身时，除了在这里存档，
还要按 AGENTS.md 硬规则 #5 往 `evolution-log.md` 追加一条带具体事故的记录。

### 案例：commitlint 钩子曾经九个月一次都没生效

> 2026-08-24 从 `context/team/git-commit.md` 迁入。它讲的是**校验工具装完没验证**这一类
> harness 失效，不是 git 提交规范本身，留在规则文件里会稀释规则。

从 2025-11-04 搭起到 2026-08-02 修好，**中间的全部提交都没被校验过**，前端后端都是。
层层叠叠断了五处，任何一处单独存在都足以让它失效：

1. `.husky/commit-msg` 的**全部内容**是一行

   ```
   echo "pnpm exec --no – commitlint --edit $1" > .husky/commit-msg
   ```

   这不是钩子，是**创建钩子的那条安装命令被原样粘进了它本该创建的文件里**。每次提交它
   只是把自己重写一遍，然后退出 0。**从建立那天起就没调用过 commitlint 一次**——这是
   起点，后面四条都是在它之上叠的。
2. 它写出来的那行本身也是坏的：`–` 是全角连字符 U+2013 不是 `--`；`--no` 又是 pnpm 11
   已废弃的 exec 参数。
3. `@commitlint/cli` 从未出现在任何 `devDependencies` 里。
4. 前端的 `.commitlintrc.cjs` 的 `rules: {}` 是空的，也没有 `extends` —— 零规则。
5. 2026-03-19 前端迁移到 vite-plus、删掉 `frontend/.husky/` 时，`vp config` 看到已有值
   `frontend/.husky/_` —— 不等于 `.husky`、也不以 `.husky/` 开头 —— 守卫触发，打印
   skipping 后放弃接管。于是 `core.hooksPath` 一直指着一个**已被删除的目录**，
   git 对此不报错，只是静默地一个钩子都不跑。

**教训：校验类工具装完必须用一条故意写错的输入验证它真的拦得住。**
「配置文件存在」不等于「规则在跑」——静默失效的门禁比没有门禁更危险，因为它给了一种
虚假的安全感。这条对第 1 层尤其致命：文件在、可执行位在、`git commit` 也确实调用了它，
唯独它什么都没做。

这条判据在 2026-08-24 又兑现了一次：`.freeze/` 冻结验收集机制脚本、CI、CODEOWNERS
三处接线都正确，却从未放进过任何一组真实冻结集，`verify-freeze.sh --all` 恒返回 rc=0，
而 AGENTS.md 一直称它是「main 上唯一必需的 CI 检查」。同一种失效换了个壳：
**门禁的存在性 ≠ 门禁的有效性，要验的是「它红过吗」。** 该机制已整套删除。

## 本框架自身的演进

`context/` 目录结构本身也适用这套规则。发现分层判据不好用、experience 模板缺一段，
就改 `context/harness-framework/` —— 框架自身的演进就是 Self-Refinement 的活样本。
