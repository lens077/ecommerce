# Self-Refinement —— 让纠错变成资产

LLM 没有跨会话记忆。但**每一次用户纠正，都是一个信号**：说明 AI 的默认行为和本项目的真实约束之间有偏差。

不沉淀，下个会话、下个模型、下个人还会犯同一个错。

## 闭环

```
① 用户纠正了 AI 的某个做法
        ↓
② 判断：这是「模式性教训」还是「一次性 diff」？
        ↓ （模式性）
③ 按 knowledge-layering.md 判定该写哪一层
        ↓
④ 主动向用户提议沉淀，得到确认后写入 context/
        ↓
⑤ 下次同类场景，AI 从 context/ 读到并主动引用
   → 新会话 / 新模型 / 换 AI 工具都受益
```

第 ④ 步的**「主动提议」**很关键。AI 不应该等用户说"记一下"才记，而应该在识别到模式性教训时主动问：
「这条要沉淀到 `context/team/xxx.md` 吗？」

## 模式性 vs 一次性 —— 怎么判

| | 模式性教训（沉淀 ✅） | 一次性 diff（不沉淀 ❌） |
|---|---|---|
| 定义 | 下次遇到同类场景**还会重犯** | 这一次的具体改动 |
| 例 | 「MUI 的 sx spacing 会 ×8，要用 sp[] 字符串」 | 「把这个按钮的 padding 从 16 改成 8」 |
| 例 | 「JWT 校验要留 leeway，否则时钟偏移导致死循环」 | 「把 leeway 从 60s 调到 90s」 |
| 例 | 「proto 字段必须推断校验范围」 | 「这个 max_len 应该是 128 不是 64」 |
| 检验 | 能写成一句**普适的规则** | 只能描述成**这一处的修改** |

**一个实用的自检**：如果这条知识只能写成「把 X 改成 Y」，那是一次性 diff；
如果能写成「凡是遇到 A 场景，就要 B」，那是模式性教训。

## 沉淀时的纪律

1. **先查重** —— 已有文件覆盖了就更新那个文件，不要新建重复的
2. **写清楚 Why** —— 只写「要这么做」，下次遇到边界情况时无法判断能否变通
3. **记下关键陷阱** —— 尤其是「第一直觉会指向哪个错误方向」
4. **发现旧知识是错的就删掉** —— 过期的知识比没有知识更危险
5. **不写凭据**

## 已知的失效模式

- **知识库膨胀**：什么都沉淀 → 检索成本上升 → 没人（和没有 AI）看 → 等于没有。
  严格执行模式性判断，宁缺毋滥。
- **口径漂移**：同一约束在两处、逐渐分叉。只写一处，其余用链接。
- **文档腐化**：代码改了知识没改。沉淀的知识要引用**稳定的东西**（约束、原理），
  少引用**易变的东西**（行号、具体数值）。

## 本框架自身的演进

`context/` 目录结构本身也适用这套规则。发现分层判据不好用、experience 模板缺一段，
就改 `context/harness-framework/` —— 框架自身的演进就是 Self-Refinement 的活样本。
