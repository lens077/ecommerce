0.3.4 容器复核：mawk 与硬链接

0.3.4 的验证分两层：正则语义在容器内用 mawk 实跑，硬链接分支在同一次运行里核对 inode。 两者都在 Docker 29.9.3 / Debian 12 / ext4 named volume 上完成，不是只看 macOS 的 BSD awk。

检查证据
mawk 下的三种标题层级 mawk 1.3.4 实跑：## 证据 + 未打标行 → rc=1 且输出含 [EVIDENCE]； ### 证据 同样 rc=1；# 证据 → rc=0。0.3.3 的结果是 h2=1 / h3=0 / h1=1， 0.3.2 则三者全为 0（静默通过）。
结束标记等价 ## 证据 + 打标行 + #### 子节 + 未打标行：0.3.3 因 ^#+ （h1–h6）提前收段判 rc=0， 0.3.4 的 ^#?#?# （h1–h3）判 rc=1，与原意一致。
文件系统确实不支持写时复制 stat -f -c %T /work → ext2/ext3（ext4 族）； cp --reflink=always → failed to clone ...: Operation not supported； GNU cp -cR → invalid option -- 'c'，因此 kit 退到下一档。
实际进入硬链接分支 bash -x trace：+ cp -al .../template/. .../clean-template/； probe-isolation 输出「源码树硬链接复用」。不是只看「跑绿了」。
硬链接与断链落点 template/backend/go.mod 与两个沙箱同名文件 inode 相同、链接数 21； AGENTS.md、harness.config.sh、context/team/INDEX.md、 .git/index 在模板与各沙箱 inode 各不相同、链接数 1。
原地写是否污染模板 跑完 git -C template status --porcelain 为 0 行；canary-isolation 只出现在 aux-isolation 沙箱，模板与其他 mutation 沙箱都没有。
git 是否跨沙箱串味 各沙箱 .git/index 独立；在一个沙箱里 git commit 后， 模板与另一个沙箱的 HEAD、git log 都不变。
并行是否互踩 探针 4 个一批并行，19/23 全过；mut-DEAD-LINK 与 mut-FORMAT 的 git status 各自只含自己的改动。

容器是 Docker Desktop 的 linux/arm64 Linux VM，不是 GitHub runner 本身； ext4 与 runner 相同，但内核、IO、缓存和资源限制不同。容器里还显式装了 perl 以提供 shasum（GitHub ubuntu runner 自带，最小镜像不一定有）。因此这次消掉的是 「硬链接分支未实测」与「mawk 下语义未验证」两项不确定性，不等于「CI 首次真实 runner 已验证」，后者仍在第四节。

0.3.3 → 0.3.4：一次「修错换错」的回归

0.3.3 修 mawk 区间量词时，把 EVIDENCE 的起点写成了 ^##? （h1–h2，原意是 h2–h3）， 结束标记写成了 ^#+ （h1–h6，原意是 h1–h3）。两处都不是笔误级别：起点变化让 ### 证据 不再命中、# 证据 反而命中。

LyraPass 与 palcommerce 在升级后各自独立发现了同一现象。0.3.4 用 mawk 可用的等价写法 ^##?# （2–3 个 #）与 ^#?#?# （1–3 个 #）恢复原语义，并在 canary 里加了 h2 命中、h3 命中、h1 不命中的三输入断言；结束标记另做等价性核对。ecommerce 本身的证据段是 h2， 修复前后都命中；按 glob 复查，21 篇经验文档里没有被 0.3.3 漏掉的 h3 证据段。

给所有仓库的教训：为了兼容性改写正则，必须用等价性断言证明语义未变，否则就是拿一个错换另一个错。 这次两个仓库能发现，是因为它们在升级后仍逐条看门禁输出；只跑「绿了没有」不会暴露这类静默错判。

等你拍板

1. 六个分支的 push 与合并顺序

  • 选项 A：先 push + 合并 ecommerce，再按 ToDo / LyraPass / Scorpius / palcommerce 顺序，Libra 最后。 后果：kit 源头先稳定，返工最少；但整体最慢。
  • 选项 B：六仓并行提 MR。后果：快；若 kit 需要返工，五个仓要跟着改。
  • 选项 C：只 push 不合并。后果：先让 CI 跑起来，保留回退空间。

2. hooks 安装时机

  • 合并前装：本地提交立即受门禁约束，但可能与各仓现有钩子冲突。
  • 合并后装（建议）：不阻塞接入；风险是合并前本地提交没人拦。
  • 不装：完全依赖 CI，提交反馈更慢。

3. CI 首次真实 runner 验证

  • 先提 PR：只跑 doctor + check，最安全；canary 留到 push 默认分支。
  • 直接 push 默认分支：一次跑全量，但失败会影响主分支。
  • 暂不验证：模板保持「未在真实 runner 跑过」的状态。

0.3.4 已在 Linux ext4 容器里用 mawk 跑过完整 canary，硬链接分支与 mawk 语义都不再是空白； 但容器不是 runner，首次真实执行仍需单独确认。

4. .gitleaks.toml 放行条目

  • 全部保留：接入最省事；风险是真实凭据被误豁免。
  • 逐条复核后收窄（建议）：安全；需要你花时间看每条豁免的对象。
  • 全部删除再跑 check：最严格；会暴露历史夹具，可能要补新豁免。

5. Libra 根 AGENTS.md

  • 用接入分支版本：harness 段完整；可能丢主工作区的业务约定。
  • 用主工作区版本：业务约定保留；可能丢接入说明。
  • 人工合并（建议）：两边都保留；成本是一次逐段核对。

6. ToDo DECISIONS.md 34 项

  • 合并前逐条收口：决策记录干净；需要你判断 19 个未勾项。
  • 先合并、后收口：不阻塞接入；未勾项会继续留在主分支。
  • 转为 TODO：保留未决事项；会增加 TODO.md 条目。
