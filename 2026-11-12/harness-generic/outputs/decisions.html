一、分支、提交与仓库边界

D1 用独立分支 + 每阶段一次提交，而不是直接落在 main 或压成一个提交

阶段 0提交策略

备选
  • 直接提交到 main：省事，但漂移修正与新增 kit 混在主线历史里，回退粒度粗。
  • 全部压成一个提交：干净，但「文档修正」与「新代码」无法分别回退。
  • 按阶段一提交（选定）。
选择
新建 harness/generic-kit，四个阶段各一次提交；main 保持干净。
理由
文档修正（低风险）与新增 kit（新代码）影响面不同，分开提交后可以只回退其中一个； 审查者也能按「漂移修正 → kit → 文档 → 决策文档」的顺序读。
影响面
四个提交：f1e97bcb、3a69f7d9、6814a20c、ce2f7925（另加本 HTML 的提交）。
改判
想合成一个提交：git rebase -i main 后把后三个 squash 进第一个；想回退某阶段： git revert <hash>。均不影响 main。

二、kit 的形态与技术选择

D3 kit 用 vendor 目录 + lock 摘要，而不是子模块或包管理器

阶段 2形态

备选
  • git submodule：升级路径清晰，但离线/内网环境常拉不到，门禁会因「拿不到子模块」而失效。
  • npm/pip 包：需要 registry 与网络，且引入包管理器依赖，违背「零第三方依赖」。
  • vendor 复制 + harness.lock 记录版本与每个文件的 sha256（选定）。
选择
整个 harness-kit/ 目录随宿主仓库提交；harness.lock 记录版本与摘要。
理由
门禁是必需品，不能因为外部仓不可达而失效；lock 让「本地改过 kit」可被发现（doctor 报 drift）， 兼顾可审与可升级。
影响面
harness-kit/bin/harness 的 init 写 lock、doctor 校验 lock； 升级流程 = 替换目录 + 跑 harness/bin/harness init（只刷新 lock，不覆盖已有文档）。
改判
要换子模块：删 harness-kit/，加 .gitmodules，并改 bin/harness 里 KIT_ROOT 的推导（harness-kit/lib/config.sh:6）。改完跑 harness/bin/harness doctor && harness/bin/harness canary。

D4 配置用 bash，不用 YAML / TOML

阶段 2形态

备选
YAML（需解析器，标准库没有）、TOML（Python 3.11 才有 tomllib，且 bash 侧还要再解析）、 bash 变量（选定）。
选择
harness.config.sh，由 lib/config.sh source 并给默认值。
理由
「零第三方依赖」是硬约束，YAML 要么引第三方、要么自写不可靠子集；本项目配置项全是字符串/数字/列表。
影响面
配置是可执行代码：只放在自己的仓库里，不要 source 来路不明的配置（此风险已写在 harness.config.example.sh 头注释与 README.md 的约束段）。
改判
要换 YAML：在 harness-kit/lib/config.sh 增加一个用 Python 标准库解析的最小编译层 （注意标准库没有 YAML，需自己写子集或允许一条第三方依赖），再跑 canary 确认探针仍能开关检查。

阶段 2检查取舍

备选
把 ecommerce 的 18 个 tag 全部搬进 kit；或只搬「与项目事实无关」的那部分（选定）。

D15 gitleaks 默认 required（已决）

阶段 2已决

备选
required（缺工具即红，选定）；optional（缺工具只跑内置特征）；off。
选择
默认 required，fail-closed：没装 gitleaks 就红，不允许「工具没装所以这层静默跳过」。
理由
原方案默认 optional，理由是新项目接入时未必装工具。但 optional 的失败形态是 「看起来跑了、历史扫描其实没跑」——与本仓反复出现的门禁静默失效同型。接入期因未装工具而红是 预期行为：它把「装工具」变成一次明确的接入动作，而不是一条永远没人看的提示。
影响面
harness-kit/lib/config.sh 默认值、harness-kit/harness.config.example.sh （即 init 生成物）、harness-kit/bin/harness doctor 的提示、 docs/onboarding.md 第 3 步、docs/adaptation.md 的 SECRETS 节。
改判
接入期确实装不了工具时，在 harness.config.sh 显式写 HARNESS_GITLEAKS="optional"（doctor 会提示当前是降级状态）， 不要写 off——那会把内置明文特征一起关掉。安装入口： https://github.com/gitleaks/gitleaks#installing。 要改回默认 optional，先证明「接入失败率高到必须让门禁容忍缺工具」， 并在本页新增一条决策记录写明反例。

映射结论
一一对应进 kit（7）：DEAD-LINK、FRONTMATTER、SKILL-REF、BUDGET、PROGRESS-SRC、 ORPHAN（原 INDEX-COVERAGE）、PATH-REF 的通用版本。
kit 缺失、本次补齐（6）：INDEX-LINE、FORMAT、EVIDENCE、AFFECTS、RETIRED、SELFCHECK。

不丢判定的证据
scripts/verify-context-canary.sh 覆盖全部 17 个启用 tag（kit 12 + 适配层 5）， 每个 tag 至少一个注错探针断言 rc=1 且 tag 正确；新增的 6 项另各配一个正样本， 证明不误杀。元断言「每个启用 tag 至少一个探针」继续生效。
影响面

D21 收尾版 0.3.1：逗号行号、canary 成本、CI 时机（已决）

阶段 7已决收尾

背景
五仓全部升到 0.3.0、零本地补丁后，ToDo 与 palcommerce 报告同一类边界： PATH-REF 只剥单段行号，docs/subsystems/core.md:1149-1164,1196-1223 这类逗号多段引用被整串当成文件名误报。同时大仓 canary 每个探针复制一遍已跟踪文件树， ToDo 本机 5–6 分钟；CI 模板又在每个 PR 上跑 canary。
选择一：PATH-REF 剥逗号多段
把剥离正则扩成 :[0-9]+(-[0-9]+)?(,[0-9]+(-[0-9]+)?)*$， 并加 path-ref-comma-ranges 自检（修前红、修后绿；0.3.2 扩展为 path-ref-line-forms 并保留四种行号形态）。
被推翻的备选
① 把所有含 : 的 token 一律跳过——会放过真实的「文件名 + 冒号」路径， 判定被削弱；② 只剥到第一个冒号——仍会留下 ,1196-1223，误报照旧； ③ 让宿主把这些引用写进基线——把 kit 的判定缺陷转成每个仓的维护债。
选择二：canary 模板一次、探针硬链接复用
模板构建一次；每个探针用 cp -al 整树硬链接， 再把探针会原地写的路径（.git、配置、基线、AGENTS.md、 context/、docs/、扫描根）断开硬链接换成真拷贝； 加 probe-isolation 自检验证注错不改模板。
被推翻的备选
① 每探针 cp -a 整拷贝——数据量不变，省不掉 I/O； ② 只依赖 APFS clone（cp -cR）——Linux CI 与非 APFS 盘退回整拷贝， 等于没改；③ 所有探针共用一个沙箱、跑完清理——探针会追加内容且留下新文件， 清理无法保证回到干净基线，隔离性靠人守；④ 连文档树也硬链接——一次 append 会污染模板与后续探针。
选择三：CI 时机
PR/MR 只跑 doctor + check； push 到默认分支（main）或打 tag 才跑 canary。两个平台模板同步改， 理由与改回方法写进 docs/adaptation.md。ecommerce 自己的 scripts/verify-context.sh 行为不动。
被推翻的备选
① 每个 PR 都跑 canary——成本随「探针数 × 仓库体积」增长，且探针测的是 kit 判定， 不是这次业务改动；② 直接删掉 canary——门禁有效性重新变成无人验证； ③ 只在 nightly 跑——main 可以在门禁未被证明的情况下合入。
版本
0.3.1（patch）：一处判定缺陷修复、一处性能改造、CI 模板策略，没有新增检查语义。

D22 性能版 0.3.2：PATH-REF 消除逐 token fork（已决）

阶段 8已决性能

背景
LyraPass 实测：125 个 md、11,005 个反引号 token，PATH-REF 一项 39.5s， 占整个 check（44s）的 90%；time -p 的 sys 远大于 user。原因是剥行号写在 while read 循环里，每个 token 起一次 sed，成本随 token 数线性增长，属 fork 放大而非真实计算。
选择
把剥反引号与剥行号合并进同一条 sed，每个文件一次； 判定语义原样保留：path:12、path:12-34、 path:12-34,56-78、path:12,34-56，以及中段/结尾 * 的跳过规则都不变。
实测（本机 macOS/APFS，只跑 PATH-REF）
  • 2000-token 合成样本：7.41s / 7.60s → 0.24s / 0.26s； sys 4.93s → 0.11s，user 1.87s → 0.13s。
  • ecommerce：40.07s → 1.75s / 1.76s。
  • LyraPass：46.36s → 1.07s / 1.45s（该仓自报旧值 39.5s，量级一致）。
  • ecommerce 与 LyraPass 上新旧实现的输出逐字节 diff 为空，rc 相同。
被推翻的备选
① 用一次 awk 重写整条提取——BSD awk 没有 match(s, re, arr)， 要手写反引号扫描，收益与「一条 sed」相同但更易错；② xargs 批量调 sed——仍需按 token 调度，且要处理含空格/特殊字符的 token； ③ 跳过行号剥离或让宿主写基线——削弱判定，把 kit 缺陷转成各仓维护债； ④ 只在大仓关掉这项检查——等于放弃对「文档指向不存在文件」的拦截。
防退化
新增 path-ref-fork-count 自检：PATH 垫片包住 sed/awk 统计外部进程调用次数。4 个文件、1200 个 token 的样本上 实测 11 次，上限 32；旧实现是 1211 次。断言不测墙钟，只测调用次数，因此慢机器/慢 CI 不会假红；又因为「每 token 一次」会直接冲到 1200+，回归必红。 另加 path-ref-line-forms 覆盖四种行号形态与中段/结尾通配。

0.3.2（patch）：只改实现与自检，不新增检查、不改判定，也不需要宿主改基线或探针。
