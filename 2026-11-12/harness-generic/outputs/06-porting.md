# 移植步骤与验收

目标：新仓接入后，**门禁在干净树上绿、在注入违规时红**，且新人 `git clone` 一台机器就能跑起来。

## 顺序原则

**先把 canary 跑红，再接 CI。** 反过来做的话，你会在「CI 看起来绿」的错觉里接入一个恒绿检查。
源仓两次事故都发生在「先接线上、后补元评测」的路径上。

## P0：核心三件（最划算，不碰发布链）

**目标**：结构门禁 + 元评测 + 一键入口可用。

- 范围：`verify-context.sh`（按 `05-scripts/adapt-points.md` 外提常量）、`path-refs.py`、`verify-context-canary.sh`、
  三份空基线、`Makefile` 的 `gate` 目标。
- 验收：
  1. 干净树上 `gate` 绿；
  2. canary 对**每个启用 tag** 至少一条红探针；
  3. 删掉任一检查代码后对应探针转红；
  4. `release` / `deploy` 相关文件 diff 为空。
- 风险：低。唯一真实风险是「探针集合手抄」——必须从启用 tag 列表生成。
- 成本：约 1 份配置 + 3 个空文件 + 1 次常量替换。

## P1：安全门禁 + 分发入口

**目标**：凭据与敏感信息在提交时就被拦；hook 换机器仍生效。

- 范围：`.gitleaks.toml` + pre-commit 暂存扫描 + CI 同名 job；`make hooks` 幂等安装
  （或统一 `core.hooksPath`）；commitlint + commit-msg（若采纳提交规范）。
- 验收：
  1. 故意提交一个假密钥 → 本地被拦、CI 被拦；
  2. 新克隆的仓库执行一次 `make hooks` 后，钩子生效（用一个非法 commit message 验证）；
  3. 删除 `.git/hooks/` 下所有文件再跑 `make hooks`，仍能得到一致结果（幂等）。
- 风险：中。**不要**同时保留两套钩子安装方式；两套互抢就是源仓九个月静默失效的成因。
- 注意：`git commit --no-verify` 会绕过 pre-commit——所以 CI 侧必须有同名 job，不能只靠钩子。

## P2：文档责任与剩余检查

**目标**：改代码不改文档会被拦。

- 范围：`verify-doc-sync.py`（按仓重写规则表）、`[SKILL-REF]`（先统一 skills 表列序）、
  `[RETIRED]`、可选 `[EMBED]`。
- 验收：
  1. 改核心模块但不改归属文档 → 提交被拒，报错指向具体文档；
  2. 带「历史陈述」横幅的段落仍放行（防误伤既有内容）；
  3. canary 覆盖新增的每个 tag。
- 风险：高。会拦提交，规则表写错会误伤日常开发。
  **上线前必须**：先在分支上跑一周「只告警不拦截」，确认误报率为 0 再转拦截。

## P3：第三仓 onboarding

**目标**：新仓接入 = 1 份配置 + 3 个空基线 + 1 次生成，半天内完成。

- 范围：把 P0 的产物抽成模板目录（本目录即雏形）；提供 `harness init` 脚本做占位符替换 + 基线初始化；
  用 `harness.lock`（sha256）记录模板版本，升级走显式命令一次性 diff。
- 验收：
  1. 新仓首日 `gate` 绿、canary 绿；
  2. 升级模板时能用一次 diff 审完，无需逐行对照；
  3. 两仓的检查集差异可以由配置 diff 解释，不靠记忆。
- 风险：低。

## 形态选择：模板仓 + vendor，而不是发布成包

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 独立包（npm/pip） | 升级自动 | 引入安装失败面；门禁缺依赖就失效；bash 造生态成本高 | 否 |
| 纯复制 | 零依赖 | 三仓后必然漂移（源仓现状已可见） | 否 |
| 模板仓 + `scripts/harness/` vendor + lock | 零依赖、可 diff、可独立回滚 | 升级需显式执行 | **推荐** |

## 通用 vs 适配的边界（落地检查表）

放进通用核心（语义不改）：围栏配对、基线引擎（含反向棘轮与陈旧行）、路径存在性判定、
豁免精确性、`[DEAD-LINK]`/`[ORPHAN]`/`[FRONTMATTER]`/`[PATH-REF]`/`[BASELINE]` 判定、canary 执行器与假阳性守卫、
fail-closed、软门禁显形。

必须由各仓配置：扫描根、层名、预算、基线路径、豁免、退役术语、生成物目录、文档责任规则表、
skills 注册表列位、验证命令、CI provider 与 job 名、hook 挂载方式、安全 allowlist。

**不属于任何一层**（各自仓库自己维护）：服务名、端口、集群地址、领域术语、
`control-tower` 这类同级仓依赖规则、KYAML 与部署双清单（只有采纳该结构的仓才需要）。

## 第三仓复制成本估算（按文件数，不按时间）

- 必改：`harness.config.sh`（1 份）、三份基线（3 个空文件）、`AGENTS.md` 占位符（约 12 处）
- 需重写：canary 探针清单（按启用 tag 生成）、`verify-doc-sync` 规则表（若启用）
- 可原样：`path-refs.py`、canary 执行器、`harness-scars.sh`、`verify-quick.sh` 骨架
