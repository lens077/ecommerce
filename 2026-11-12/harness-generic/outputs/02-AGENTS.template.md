## 硬规则（不可跳过）

1. **以真相源为准**：规范看 `{{CONTEXT_DIR}}/`（入口 `{{CONTEXT_DIR}}/INDEX.md`），
   结构事实看 `{{FACT_TABLE}}`。现搜、推测、记忆与之冲突时以真相源为准；
   **找不到对应知识 ≠ 没有约束**，先读 `{{DESIGN_DIR}}`（入口 `{{DESIGN_DIR}}/README.md`）与 `{{TODO_FILE}}`，
   结论沉淀回 `{{CONTEXT_DIR}}/`。
2. **改对外契约前必须先读设计文档**：{{CONTRACT_KINDS}}（如 proto / OpenAPI / 消息 schema / 数据库迁移），
   并为每个字段推断出校验约束。见 `{{CONTRACT_DOC}}`。
3. **提交前先问：这次改动涉及哪个 {{TODO_FILE}} 项？** 涉及就先更新它（完成/部分完成/改目标/删除），不涉及就不动它——
   它只记 TODO 项与状态；已完成项的过程记录直接删掉，不另设归档目录。提交信息走
   `{{COMMIT_CONVENTION}}`，由 `{{COMMITLINT_HOOK}}` 强制校验。见 `{{COMMIT_DOC}}`。
4. **不要把凭据写进仓库**。密码/密钥只存在 {{SECRET_STORE}} 和本地环境，仓库里只写主机名和端口。
5. **踩到坑要沉淀**：区分「模式性教训」与「一次性 diff」，前者写进 `{{CONTEXT_DIR}}/`。
   见 `{{CONTEXT_DIR}}/harness-framework/self-refinement.md`。
   改动 harness 本身（硬规则、门禁脚本、检查项、CI 门禁）时，**在改动处写清触发它的具体事故**——
   规则能从代码读出来，理由不能，没理由的规则半年后会被凭直觉改回去。
6. **不可逆动作需要用户授权——但授权一旦给出就直接执行，不要二次确认**。
   - **哪些算**：`git commit`、`git push`、分支/MR 合入、部署（`{{DEPLOY_COMMANDS}}`）、
     发布制品（`{{PUBLISH_COMMANDS}}`）、workspace 之外的写入与删除。
   - **什么算授权 → 算了就动手**：用户这轮明确要求做这件事，或明确放宽后续同类动作。**此时直接做**，
     不要复述风险再问「确认吗」——重复确认拖慢工作，还让用户对提示麻木。
   - **什么不算**：「帮我实现 X」「修好这个 bug」不构成授权；授权也**不跨范围升级**。
   - **仍需先说明再做的例外**：用户没要求、且会丢数据或影响线上的动作。
   - subagent 永久不得执行其中任何一项：它拿不到用户的授权上下文。
7. **全自动模式不询问权限，但仍询问实质性选择**：环境或会话标记为 `Full Auto` 时，用已有能力和审批机制直接执行，
   不拿权限确认打断用户。若被硬性安全边界阻止，不得绕过，直接报告阻塞。多个会实质改变结果的互斥选项仍用交互式选择。
8. **解决问题优先，不要为了堆工作量去写测试**。唯一正当理由是「能验证这次改动」或「能挡住这个 bug 复现」。
   - **该写的照写**：修 bug 补一条能复现它的回归测试；改核心逻辑或边界条件补断言。
   - **不要写的**：覆盖率凑数、断言 getter/setter 或框架行为、照抄实现的镜像测试、只换无关字段的表驱动样例；
     也**不要顺手扩张**——要求修 A 就别给 B、C 补测试。
   - **优先跑既有验证**；交付时如实说明测了什么、没测什么。

## 执行策略：E3（先估计 → 最小执行 → 失败才扩张）

动手前先估计任务规模并说出来，最多一次廉价探测（查一次 `{{FACT_TABLE}}` 或一条 grep）：

- **L1** 单文件局部修改 · **L2** 少数文件跨文件修改 · **L3** 仓库级重构（警惕 re-export/别名/间接引用点）
- 按估计走最小路径：只读预计要改的文件，不为局部修改通读代码库；改完立即跑锚点里**最便宜的适用验证**
- 只有验证变红才扩大范围，一次扩一级（再 grep → 追依赖 → 读下一个最相关文件），复用已有发现，不推倒重来
- 措辞像局部但探测命中多处时，降置信、按高一级处理
- 规模驱动开销：L1/L2 不开 plan mode、不派子代理、低 reasoning effort；L3 才值得。正确性是硬约束
- E3 **不豁免**硬规则；也**不要**反向加码写「先通读代码库 / be thorough」

## 消费边界：用户给的是目标，不是空白支票

- **事前**：派 subagent 前先说出数量和理由；单轮超过 3 个或子代理再派子代理，先问用户
- **过程**：每次扩张（新 subagent、检索扩到全仓、切更贵模型、第 2 次重试）回复里说一句，不静默
- **告警**：请求数超同类经验上限（只读调研 >20 次仍未汇总）、同一检索重复执行、上下文整份重复携带 →
  停下报告，不自行继续
- **可控**：用户说停就停，包括已派出的 subagent；停后不为「收尾」再起新调用
- **小票**：任务结束报请求数、总/缓存 token、subagent 数、超预期原因、完成与未完成
